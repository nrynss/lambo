## New findings

### F-R2-1 (P2) — The write gate validates each concept against the contract of the moment, so a **restamp** still walks the session into the exact terminal state round 1 called fatal — and the gate's own doc asserts the property that fails

- **Evidence:** `enforce_concept_vector_widths` re-reads `sessions` per `FlushStep::Concepts`, so each concept is checked against whatever contract is durable *at its step*. Because `SetEmbedding` is a `plan_flush` barrier, a batch can legally interleave stamps and upserts such that **every concept matches the contract at its own moment** while the *final* durable contract disagrees with vectors written earlier in the same batch. `set_embedding`'s quarantine cannot save it: the `UPDATE concepts SET embedding = NULL` fires only when the previous contract was `embedding_kind IS NULL AND embedding_dim IS NULL` (`sqlite.rs:1956-1966`), so a value→value restamp quarantines nothing.

  Reproduced from an external crate through the public `GraphStore` trait — one `flush`, no direct SQL (PROBE 3):

  ```
  === PROBE 3 (ATTACK): RESTAMP inside ONE batch, all widths locally valid ===
    [1] flush ACCEPTED
    [2] durable contract dim = Some(3); concept vector widths = [Some(4), Some(3)]
    [3] vector_candidates_checked -> backend: concepts.embedding for 43773589-… decodes to 4 dimensions but session restamp-one-batch declares 3
    [4] vector_candidates (frozen) -> backend: concepts.embedding for 43773589-… decodes to 4 dimensions but session restamp-one-batch declares 3
  ```

  Batch: `UpsertNode(Interaction)`, `SetEmbedding{dim:4}`, `UpsertNode(Concept{4-wide})`, `SetEmbedding{dim:3}`, `UpsertNode(Concept{3-wide})`. Also reproduced split across two sequential flushes (PROBE 4 — the shape an operator would actually produce), same outcome. Repro crate: `lambo = { path = "<worktree>", default-features = false, features = ["store-sqlite"] }`, `build_store(StoreConfig { kind: Sqlite, path: Some("sqlite::memory:"), vector_dim: None })`, `init_schema()`, the batch above, then `vector_candidates_checked` / `vector_candidates`.
- **Impact:** This is round 1's F-R1-1 terminal state, unchanged in every consequence: session-wide (`select_session_vectors` returns on the first bad row, so the good concept is unreachable too), durable, permanent until someone edits the row by hand, and fatal to both `recall::candidates::gather` and `hybrid::derive`, which propagate rather than degrade. The severity is P2 rather than P1 for the same reason round 1 gave: the `Graph` tier guards every in-tree writer thoroughly — `stamp_embedding` calls `ensure_compatible` on an existing contract (`graph.rs:793`), `replace_embedding_without_vectors` refuses while any vector remains (`:809`), `replace_embedding_with_operator_override` refuses a width change (`:843`), and `Memory::build` hard-errors on `stored.dim != live.dim` (`memory.rs:659`). So this needs an out-of-tree caller building a `MutationBatch` directly — which is exactly the surface the gate was installed to secure and exactly the surface round 1 used. What makes it blocking rather than a footnote is that the new code asserts the opposite. `sqlite.rs:1670-1672`: concepts before a stamp *"are validated against the contract that was durable when they were written, **which is the same contract a reader would have interpreted them under**"* — false precisely in the restamp case, where the reader interprets them under the new contract. And the commit message: *"so it can never become the fatal mismatch"*. The claim is stated more strongly than the code earns, which is round 1's blocking criterion.
- **Required remediation:** Either close it — make `set_embedding` quarantine (or re-validate) on **any** width change rather than only over a NULL contract, which is a one-predicate change to the existing `UPDATE` and would also make PROBE 3/4 refuse or self-heal; or state the residual honestly — say that the gate closes the width-mismatch shape but that a contract restamp can still orphan earlier vectors, and that the read path's session-wide refusal remains the only line of defence there. Add a test in the shape of `vector_write_gate_reads_the_contract_each_step_sees` for the restamp ordering, since that test currently covers only the two orderings that pass.

### F-R2-3 (P3) — `check_vector_compatibility` is still structurally vacuous for SQLite *with* a pin, and three shipped sites say the pin fixes it — contradicting the two sites that get it right

- **Evidence:** With a pin set, `store.vector_dimensions()` **is** the pin (`build_store_with_vector_dim:626`, `cfg.vector_dim.or(vector_dim)`). The new pin check at `resolve.rs:134-144` returns `Err` whenever `pinned != embed_dim`, and it runs **before** `check_vector_compatibility(store.vector_dimensions(), embed_dim)` at `resolve.rs:145`. So `check_vector_compatibility` receives `(Some(pin), embed_dim)` only on the paths where `pin == embed_dim`: it is `x == x` with a pin exactly as it was without one. Three shipped sites claim otherwise:
  - `store/mod.rs:497-499` (`StoreConfig::vector_dim` doc): *"That is the **only thing that makes** `check_vector_compatibility` non-vacuous for SQLite"*
  - `store/mod.rs:604-605` (`build_store_with_vector_dim` doc): *"the pin is what gives it something real to compare"*
  - `dev-diary/lambo-for-mooshik/B-postgres-store.md` §B4: *"the pin is what makes the check non-vacuous"* — now handed forward to the next workstream as settled semantics

  Meanwhile the two sites that describe the same property correctly are `resolve.rs:39-46` (*"The check that bites on that path is the explicit pin comparison in `resolve_backends`"*) and `lambo.example.toml:32-33` (*"unless you set `store.vector_dim` above, it reports THIS number back and the comparison is vacuous"*). The new test is itself honest — it asserts the no-pin case *"cannot fail — the vacuity the finding names"* — so the code and the test are right and only the prose is wrong. Related and smaller: the commit message and the B note both say the refusal fires when the pin *"disagrees with the embedder's **real output width**"*. For `bge_m3` it does not: `dimensions()` returns `self.dim` from config, and `resolve.rs:122` has already proven `embed_dim == embedder_cfg.dim`, so the pin check compares two config numbers. (The evidence transcript shows this directly — step 6 reports *"the configured embedder emits 768"* while BGE-M3 emits 1024 and would fail at runtime.) For `FixtureEmbedder` the width genuinely is the output width.
- **Impact:** Documentation only; behaviour is correct and fails closed. Much lower harm than round 1's version of this finding, because the operator-visible property — *a pin/embedder disagreement is refused at process resolution* — is now **true**. What is wrong is which function performs it, in three places including one handed to workstream B as inherited semantics, while two other places in the same commit say the opposite. Round 1 blocked on four sites asserting a property no code path could exercise; this is the same genre at a third of the scale and with the substance fixed.

### F-R2-4 (P3) — The pin refusal is kind-agnostic, but `StoreConfig::vector_dim`'s doc says Cockroach ignores the key, and on a vector-less store the refusal message is false

- **Evidence:** `resolve.rs:134-144` has no store-kind guard. `StoreConfig::vector_dim`'s doc says *"Cockroach **ignores** it: `VECTOR(n)` is parsed out of its own DDL"* (`store/mod.rs:501-502`) and the B note repeats *"Cockroach already ignores the key"* — true for *reporting*, false at the resolution boundary, where a stale pin refuses a Cockroach resolve too. Worse on `MemoryStore`, which has no vector column at all, reports `vector_dimensions() == None`, and never persists a vector (PROBE 8):

  ```
  memory + pin 768  -> REFUSED: config: store.vector_dim is pinned to 768 but the configured
                       embedder emits 1024 — refusing to resolve: the pin asserts what this
                       database already holds, so serving with a different width would write
                       vectors no reader can interpret (…)

  ```

  On `MemoryStore` there is no database and no vector will be written anywhere, so every clause of that explanation is false on the path that emits it.
- **Impact:** Fails closed, so no corruption — and arguably catching a stale pin is desirable. But it is undocumented behaviour on two of the three store kinds, contradicted by the field's own doc on one of them, with an error message that misdescribes what would go wrong. An operator who pinned a width and later switched to `kind = "memory"` for a quick local run gets a refusal citing vectors that store cannot hold.
- **Required remediation:** Either scope the check to width-agnostic adapters (skip it when `store.vector_dimensions().is_none()`, and let a real DDL authority speak for Cockroach as the doc says it does), or keep it kind-agnostic and say so in the field doc — dropping "Cockroach ignores it" and adding what a pin means on a store with no vector column.

### F-R2-5 (P3) — The evidence README misattributes the display-score difference to per-concept-type scaling

- **Evidence:** `evidence/mooshik-f-sqlite-bge/README.md:72-75`: *"the displayed recall scores… pass through the leg merge and **per-concept-type scaling**, which is why 0.5706 shows as 0.29 for an `Entity` and 0.5823 shows as 0.49 for a `Logic`."* There is no concept-type term in the recall final score. It is `daemon_score * w_daemon + query_relevance * w_query` (`config.rs:75`) with defaults `w_daemon = w_query = 0.5` (`config.rs:85-86`). That arithmetic explains the numbers without any type term: the flat floor `0.5 * 0.5 = 0.25` (all three baseline rows), and `0.5706 * 0.5 = 0.285 → 0.29`. The 0.49 is not a type effect at all — a 0.012 cosine difference cannot produce a 0.20 score difference — it needs a **daemon** contribution of ≈0.40, which the concept plausibly accrued from the *earlier* query in the same sequential run returning it.
- **Impact:** Explanatory prose in an evidence file, and none of the load-bearing claims depend on it — the cosines, the rankings, the margins, the above/below-floor verdicts and the `RECENT_SCORE` mechanism are all verified exactly. But the gloss attributes a score difference to the wrong mechanism, and it does so in the one document whose entire purpose is claim precision, in the finding that was about overclaiming.
- **Required remediation:** Replace "per-concept-type scaling" with the daemon/query mix and its default weights, and note that the daemon leg accumulates across the run's sequential queries — which is the honest and more interesting explanation.

## Positive observations

- **The gate is at the right choke point, and I could not get around it any other way.** Three statements in the adapter write `concepts.embedding`; one is the gated `upsert_concepts`, one is `set_embedding`'s quarantine to NULL, one is a test's direct SQL. All three write entry points funnel through `upsert_concepts`, and the gate runs *before* any encoding so a refusal leaves the transaction empty — which the test asserts rather than assumes, by checking `load_session` returns `SessionNotFound` after the refusal and that the session is still usable afterwards.
- **The barrier contract is true by construction, not by luck.** `plan_flush`'s catch-all `barrier =>` arm means `SetEmbedding` cannot silently stop being a barrier if someone adds a variant — the property the gate depends on is structural, and `batch.rs` already had a test (`every_non_upsert_variant_is_a_barrier`) pinning it.
- **The no-contract acceptance is genuinely safe, and I attacked it three ways.** Pre-stamp write, clear-then-stray-then-restore, and a stray under a cleared contract all end with the vectors quarantined and the read path returning an empty pool rather than an error. The reasoning in the doc is correct for the case it covers; the gap is the adjacent case it does not mention.
- **The multi-session cache holds.** The obvious attack on a per-session memoization — hide a violation behind a different session's cached width — is refused (PROBE 6).
