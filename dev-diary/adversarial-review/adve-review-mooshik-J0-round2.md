## New findings

### J0-R2-1 (P2) — the new fixture pins the gauge semantics but not the `ts` dependency the same commit documents; deleting the sort passes the gate

- **Evidence:** `scripts/observability/verify.sh:150-153`. The heredoc writes the `queued: 9` heartbeat (`ts` `…09:00:10`) **before** the `queued: 3` one (`…09:00:20`), so file order and stamp order agree. Applying M3 to `_ledger.py:234` — `for hb in sorted(self.heartbeats, key=lambda r: r["ts"], reverse=True):` → `for hb in reversed(self.heartbeats):`, i.e. the `ts` sort deleted outright — yields `queued:   3` and **`ALL CHECKS PASSED`, 40 ok / 0 FAIL**. The same commit adds seven lines at `_ledger.py:41-49` arguing that this exact dependency is "the strongest of the four" and that "a wrong 'newest' heartbeat has `header()` call a ledger with a known backlog complete, silently and without erroring". The fixture's own comment (`verify.sh:147-148`) claims it "pins `queued_lines()`'s sort direction and its newest-not-maximum semantics at once" — true as literally worded (M1 proves the direction *given* a stamp sort) but it does not pin that a stamp sort happens at all, which is the half the docstring is about.
- **Impact:** the gate hole is exactly the one the newly-written register warns about. A refactor that switches to file order — the natural simplification, since `load()` reads lines in order and "the last heartbeat" reads like "the last line" — is invisible to the gate and silently wrong the moment `load()` is handed more than one path, which is the trigger `_ledger.py:48-49` names. No behavioural exposure in the shipped binary (this is the Python kit, and a manual gate), which is why this is not blocking.
- **Remediation:** swap the two heartbeat lines inside the heredoc so the **newer** beat (`…09:00:20`, `queued: 3`) is written **first** and the older/larger one last, and add half a sentence to the rationale comment saying that file order and stamp order are deliberately opposed. Zero new assertions, zero new lines. **Verified (M6):** with the lines swapped, the correct implementation is 40/40 `ALL CHECKS PASSED`, and M3 produces two failures (header numeric + `--json`). One heartbeat's `uptime_secs` ordering is unaffected — `restart_times()` sorts by `ts`, so no spurious restart appears.

### J0-R2-3 (P3) — the register list at `_ledger.py:41` names `binaries`, which does not sort by `ts`; the new prose hardens that into "the four"

- **Evidence:** `_ledger.py:41-42`: *"**String sort is timestamp sort** (`Ledger.sorted_calls`, `restart_times`, `binaries`, `queued_lines`)"*, and `:45`: *"`queued_lines` is the strongest of **the four**"*. `binaries()` (`:206-218`) iterates `self.heartbeats` **unsorted**, keys a counter on `(version, git_sha)`, and returns `sorted(..., key=lambda t: -t[2])` — heartbeat count descending. `ts` appears nowhere in the function and the tuples it yields carry no stamp; ties fall back to `dict` insertion order, i.e. file order, which is still not a `ts` dependency.
