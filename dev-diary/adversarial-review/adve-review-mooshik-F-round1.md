## Findings

### F-R1-1 (P2) — The public write path accepts the exact corruption the read path was built to detect, and one such row now fails the whole session's recall

- **Evidence:** `select_session_vectors` (`src/store/sqlite.rs:1319-1327`) carries the comment *"Direct SQL is the only way to produce these — the write path encodes through the shared codec — which is exactly why the read path cannot trust the width."* That is false. `GraphStore::flush` is a public trait method, `MutationBatch` / `Mutation` / `Node` / `Concept` are public types, and no SQLite write path validates `Concept.embedding.len()` against the session contract — `concept_binds` (`sqlite.rs:1722-1733`) only encodes, and `set_embedding` (`sqlite.rs:1789-1828`) quarantines legacy vectors only when the *previous* contract was NULL. Reproduced from an external crate against the public API, one flush, no SQL:

  ```
  capabilities            = Capabilities(VECTOR_SEARCH)
  vector_dimensions()     = Some(1024)

  [1] flush of a 3-wide vector into a dim=4 session: ACCEPTED
  [2] load_session OK: 2 concepts, widths [Some(4), Some(3)]
  [3] vector_candidates_checked -> Backend("concepts.embedding for f6748d79-… decodes to 3 dimensions but session poison declares 4")
  [3b] vector_candidates (frozen) -> Backend("concepts.embedding for f6748d79-… decodes to 3 dimensions but session poison declares 4")
  [4] recall gather -> Backend("concepts.embedding for f6748d79-… decodes to 3 dimensions but session poison declares 4")
  ```

  Repro: crate with `lambo = { path = "<worktree>", default-features = false, features = ["store-sqlite"] }`; `build_store(StoreConfig { kind: Sqlite, path: Some("sqlite::memory:") })`, `init_schema()`, one `MutationBatch` containing `UpsertNode(Interaction)`, `SetEmbedding{dim:4}`, `UpsertNode(Concept{embedding: Some(vec![1.,0.,0.,0.])})`, `UpsertNode(Concept{embedding: Some(vec![1.,0.,0.])})`, then `vector_candidates_checked` / `vector_candidates` / `lambo::recall::candidates::gather`.
- **Impact:** Three things compound. (a) The blast radius is the whole session, not the bad row: `select_session_vectors` returns on the first mismatch, so the *good* concept becomes unreachable via the vector leg too. (b) `recall::candidates::gather` deliberately propagates (`recall/candidates.rs:88-91`, "swallowing a real backend failure into empty candidates would silently poison recall"), so recall fails outright — and `hybrid::derive` propagates non-`Capability` store errors as well (`hybrid.rs:597`), so the session also becomes un-writable through hybrid derive. (c) The state is durable and permanent until someone edits the row by hand. Cockroach cannot reach this state at all: `VECTOR(1024)` in `migrations/cockroach/001_init.sql:49` refuses a wrong-width insert at write time. So F2 converted an unenforced invariant — `Concept.embedding`'s own doc, `src/types/mod.rs:276`, *"width = session EmbeddingContract::dim"* — from harmless into fatal, on the one adapter with no schema to enforce it. Every in-tree writer is guarded (`Memory::build`'s override path refuses a width change at `memory.rs:659` and a cross-kind relabel while vectors remain at `graph/graph.rs:837-852`), which is why this is P2 and not P1, but the guard lives in `Memory`, not at the store boundary the comment claims is safe.
- **Required remediation:** Either enforce the width at the SQLite write gate (`concept_binds` / `upsert_concepts` already run inside the flush transaction that touches `sessions`, so the contract is available) with a typed error, mirroring what Cockroach's DDL does for free; or, if the read-side detection is deliberately the only line of defence, correct the comment (the public `flush` surface, not just direct SQL, can produce these) and state the blast radius (one corrupt row fails the session's entire vector leg and therefore its recall and hybrid derive). Consider excluding-and-warning per row instead of failing the query, which is what `VectorSearchStore` effectively does — the divergence from the reference implementation is currently undocumented.

### F-R1-2 (P2) — `check_vector_compatibility` is structurally vacuous for SQLite, and four doc sites assert it is a real store-side authority

- **Evidence:** `resolve_backends` builds the store with `build_store_with_vector_dim(store_cfg, Some(embedder_cfg.dim)…)` (`src/resolve.rs:106`), then refuses any embedder whose real output differs from config — `if embed_dim != embedder_cfg.dim { return Err(...) }` (`resolve.rs:114-118`) — and only then calls `check_vector_compatibility(store.vector_dimensions(), embed_dim)` (`resolve.rs:119`). For SQLite, `store.vector_dimensions()` *is* `embedder_cfg.dim` (`sqlite.rs:645-647` returning `self.vector_dim`, set from that same value at `mod.rs:627-629`), and `embed_dim` is already proven equal to `embedder_cfg.dim`. The comparison is `x == x`. It cannot fail on any path that reaches it. Four places say otherwise:
  - `resolve.rs:100-104` (added by this commit): *"reports the configured embedder width, so `check_vector_compatibility` below still has a store-side authority to check"* — there is no store-side authority; the store is echoing the embedder.
  - `store/mod.rs:116-117` (edited by this commit): *"Dim is **not** a global product constant: the store is the authority."*
  - `sqlite.rs:20-31` module doc, "Width authority", which frames `vector_dimensions()` as one of "two authorities that do exist".
  - `lambo.example.toml:20-22` (`include_str!`'d as a tested contract): *"stores that persist vectors expose `GraphStore::vector_dimensions()`; process resolve requires a match."*

  The new test appears to prove the check works — `assert!(check_vector_compatibility(wide.vector_dimensions(), 768).is_err())` at `sqlite.rs:2406` — but it constructs a `(Some(1536), 768)` pair by hand, and `resolve_backends` cannot produce a disagreeing pair for SQLite. Separately, the fallback path makes the store adapter read the embedder layer's config default (`sqlite.rs:306`: `crate::embed::EmbedderConfig::default().dim`), inverting the layering the trait doc asserts.
- **Impact:** F2's stated width authority does no work. The only authority that actually attests the stored vectors' space is the per-session durable contract on the read path — which the module doc says correctly, in the same paragraph where it also credits `vector_dimensions()` with a job it cannot do. A reader (or the next adapter author following B2) will believe process resolution catches a width disagreement on SQLite; it cannot. This is an evidence gap of exactly the kind the culture counts: a test that looks like proof, and four assertions of a property no code path can exercise.
- **Required remediation:** Pick one. (a) Drop the claim: say plainly that SQLite's `vector_dimensions()` exists only to satisfy `check_vector_search_contract`'s capability/width pairing (CON-5) and carries no independent authority, and correct all four sites including `lambo.example.toml`. (b) Give it real authority: have `vector_dimensions()` report the width the database actually holds where one exists — but it is sync and session-less, so this likely means a separate async check at attach (`load_reader_graph_with_contract` already refuses a stored/live contract mismatch, `cli/mod.rs:70-73`, which is the check that genuinely fires). Either way, add a test that a *disagreement reachable through `resolve_backends`* is caught, or delete the test that implies one is.

### F-R1-3 (P2) — F2 makes the full scan a per-concept hot path on `derive`, under one shared 30s deadline and one pooled connection; the seam's revisit trigger measures only recall

- **Evidence:** `hybrid::derive` computes a single `io_deadline = now + HYBRID_IO_TIMEOUT` (30s, `graph/hybrid.rs:154`, `:339`) and then calls `store.vector_candidates_checked` **inside the per-unmatched-concept loop** (`hybrid.rs:459-598`, one call per item). Each call is a full `SELECT id, embedding FROM concepts WHERE session_id = ? AND embedding IS NOT NULL` plus a UTF-8 decode and a text→`f32` parse of every element (`sqlite.rs:1296-1331`) — `limit` is ignored by design. The pool is `max_connections(1)` (`sqlite.rs:405`), so each scan holds the only connection and the write-behind flush waits behind it. The module doc's revisit trigger says *"When the scan starts showing up in **recall** latency"* (`sqlite.rs:47-50`), and the F spec's trigger is *"measure recall latency and peak RSS"*. Neither names derive, which does N scans per call where recall does one. A deadline overrun returns `StoreError::Backend("hybrid vector candidate lookup timed out after 30s")` (`hybrid.rs:521-528`), which propagates and fails the whole derive before its commit phase — a path that could not run on SQLite before F2.
- **Impact:** The scaling wall the spec worried about is on a hotter path than the spec or the module doc says, with a hard 30s cliff attached, on the default local store. For Mooshik's single unified session (the spec's stated reason the seam exists at all) a derive of k concepts over n stored vectors is O(k·n) BLOB decodes with no caching and no reuse between loop iterations, serialized against the flush task on one connection. Nothing in the tree measures it — no benchmark, no bound, no warning.
- **Required remediation:** Correct the revisit trigger in `sqlite.rs`'s "The scan is a seam" and in the F spec to name the derive path as the hotter one, with the k×n shape and the shared 30s deadline stated. Cheapest real mitigation, if wanted now: hoist one scan per `derive` call (the pool is the same, the session is the same, the contract check is the same) instead of one per unmatched concept.

### F-R1-4 (P2) — Done-when box 5 (recall parity between SQLite and Cockroach on the same seeded graph) is unmet, and the tree already has the shape for it

- **Evidence:** The only parity artifact is `vector_scores_match_the_cockroach_distance_conversion` (`sqlite.rs:2530-2600`), which **transcribes** Cockroach's `distance_to_score` into the test body (`fn distance_to_score(dist: f64) -> f64 { (1.0 - 0.5*dist*dist).clamp(-1.0,1.0) }`) and compares SQLite's cosine against it on four hand-normalized 4-d vectors. That proves the formula transcription is right — which the test says, honestly — but it is not parity on a seeded graph, and it cannot detect a change to the real `cockroach.rs::distance_to_score` because it does not call it. No test compares which candidates or which ranks the two adapters return. Two in-tree shapes were available and unused: the T3.6 three-way agreement matrix (`sqlite.rs:3649-3688`, `structural_queries_agree_with_memory_on_both_fixtures`) already asserts SQLite's structural answers exactly equal a reference oracle's over both committed fixture graphs, node × min-age; and `memory.rs`'s `VectorSearchStore` (`memory.rs:3204+`) is an exact-cosine oracle with the identical ordering contract (`total_cmp` desc, then smaller UUID — `memory.rs:3319-3325` vs `sqlite.rs:1345-1349`). Combining them would give a cluster-free vector agreement matrix.
- **Impact:** The acceptance criterion that the two tiers agree, and that any divergence is ANN approximation rather than adapter skew, has no artifact. `cockroach-live` is gated off on this branch (`ci.yml:169`), so no live leg covers it either. Related, and the reason this matters beyond box-ticking: `cosine` is norm-invariant (`embed/math.rs:21` divides by both norms) while Cockroach's `1 − d²/2` is not, so the two adapters agree *only* for unit-norm vectors. Nothing enforces that — the `Embedder` trait (`embed/mod.rs`) documents no normalization requirement; `bge_m3` normalizes (`embed/bge_m3.rs:222`), `FixtureEmbedder` emits unit vectors (`embed/fixture.rs:103-106`), and `A-gemini-embedder.md:73` tells the next embedder to. For a hypothetical non-normalizing embedder the divergence is large, not marginal: stored `[2,0,0,0]` against probe `[1,0,0,0]` scores 1.0 on SQLite and 0.5 on Cockroach. The parity test cannot see this because it normalizes its own inputs.
- **Required remediation:** Add a vector agreement matrix in the shape of `assert_structural_agreement_matrix`: seed both committed fixture graphs plus a stamped contract and synthetic vectors into `SqliteStore` and into an exact-cosine oracle, and assert the returned `Vec<Scored<NodeId>>` is exactly equal for a set of probes × limits. That is the cluster-free half. For the Cockroach half, either mark the box as awaiting the live tier explicitly (and say so in the commit trail rather than implying the transcription test covers it), or state the unit-norm precondition as a documented `Embedder` contract so the `1 − d²/2` identity has something to rest on.

### F-R1-5 (P2) — The docs now promise semantic recall on SQLite that the walkthrough's own configuration cannot deliver, and no artifact shows the vector leg producing a semantic hit under any shipped embedder

- **Evidence:** `docs/reference/end-to-end.mdx:124` and `site/src/content/docs/end-to-end.mdx:128` now read: *"The walkthrough above uses SQLite, so it exercises all three. … The in-memory store has no vector leg: recall there matches on the words you use rather than on meaning."* The contrast implies the walkthrough's SQLite recall matches on meaning. The walkthrough's config is `[embedder] kind = "fixture"` (`end-to-end.mdx:31-33`). `FixtureEmbedder` is a hash-seeded pseudo-random unit vector keyed on the exact normalized phrase, with exactly one hardcoded semantic family (`embed/fixture.rs:70-78`: `"register user" | "register_user" | "create account" | "create_user" => "family:user-registration"`); every other pair of distinct phrases is near-orthogonal by construction. Worse, hybrid stores the vector of the *context-framed* text — `context_text` produces `"{content} — {origin}"` (`hybrid.rs:226-231`) — while recall embeds the bare query, which is precisely why the acceptance test needs a test-only `ContextTolerantEmbedder` that strips the framing before delegating (`sqlite.rs:5440-5460`; the test's own doc admits `FixtureEmbedder` "cannot" bridge it). Running the documented walkthrough confirms the mechanism fires without the meaning: three concepts land with durable 1024-wide vectors (`sqlite3 lambo.db "SELECT content, length(embedding) FROM concepts"` → `user schema|12688`, `auth middleware|12638`, `must stay backward compatible|12645`; `sessions` → `fixture||1024`), and `lambo recall --query "update user schema"` returns `user schema (1.09)`, `auth middleware (0.25)`, `must stay backward compatible (0.25)` — the two non-keyword hits at the flat recent-leg score, no semantic lift. Also updated in the same spirit: `docs/reference/cli.mdx:84` and `site/.../cli.mdx:86` now tell users that "on SQLite or CockroachDB recall finds memory the swarm wrote itself" by meaning.
- **Impact:** The mechanical claim (SQLite has a vector leg, it runs, it returns exact nearest neighbours) is true and well evidenced. The semantic claim the prose actually makes to users is unevidenced on SQLite under any shipped configuration: `fixture` has no semantics, and no committed artifact — test, evidence file, or runbook — shows the SQLite vector leg producing a hit under `bge_m3`. `cockroach-live` covers the Cockroach side but is gated off on this branch, and a local llama-server rig exists but was not exercised. A reader following End-to-end will conclude they have verified semantic recall when they have verified a vector query returning near-orthogonal scores.
- **Required remediation:** Either (a) qualify the docs — say the walkthrough exercises the vector leg *mechanically* and that the fixture embedder is deterministic rather than semantic, so a semantic hit needs a real embedder; or (b) supply the evidence: one `bge_m3`-backed SQLite run (llama-server) showing a query with no shared vocabulary recalling a derived concept, captured under `evidence/`, plus the note that hybrid embeds context-framed text so the query must be near the *framed* string. Either way, name the context-framing/bare-query asymmetry somewhere outside a test comment — it is the reason the acceptance test needs a wrapper that does not exist in production.

### F-R1-6 (P3) — The anti-vacuity guard catches a rename but not an `#[ignore]`, and pins one of the nine tests the row runs

- **Evidence:** The row's first command runs 9 tests (`store::sqlite::tests::vector*` plus both `vector_e2e::*`); the guard pins one name. Simulated the three cases against the real binary:
  - vacuous filter exits 0 — `cargo test --features store-sqlite,fixtures --lib store::sqlite::tests::vectorRENAMED` → `running 0 tests` / `test result: ok. 0 passed … 824 filtered out`, exit 0. This is the hole the guard exists to close, confirmed real.
  - guard fires on a rename — same `--list | grep -q` with the pinned name suffixed `RENAMED` → **exit 1**. The named threat is genuinely caught.
  - guard does **not** fire on `#[ignore]` — `--list` prints all 824 tests as bare `name: test` with no ignored marker. `embed::bge_m3::tests::live_smoke_against_llama_server` is `#[ignore]`d (it reports as `ignored` in the same run that reports `1 ignored`) yet appears in `--list` at line 286 as `embed::bge_m3::tests::live_smoke_against_llama_server: test`, indistinguishable from a live test. So adding `#[ignore]` to the acceptance test leaves the grep green *and* the run green (`0 failed`), testing nothing — exactly the vacuity the row's comment says `--list | grep` prevents.
- **Impact:** The row's comment claims the guard means "a rename would leave this row green while testing nothing; `--list | grep` fails instead." True for renames, false for `#[ignore]` and for renaming any of the other eight tests. Test-infrastructure only.
- **Required remediation:** Assert the run count rather than only the name, e.g. pipe the first command's output through a check for `9 passed` / `0 ignored`, or grep the run output for the pinned test's `... ok` line instead of grepping `--list`. At minimum, correct the comment to say the guard covers a rename of that one test.

### F-R1-8 (P3) — The `build_store` fallback reports 1024 on a reachable production path regardless of the session's durable width, and the mismatch message points at the wrong number

- **Evidence:** `resolve_store_only` (`src/resolve.rs:150-155`) calls plain `build_store`, so SQLite gets `vector_dim = EmbedderConfig::default().dim = 1024` (`embed/mod.rs:161`) and advertises `VECTOR_SEARCH` with `Some(1024)` no matter what the database holds. Reproduced: `[5] store reports width Some(1024) for a session whose durable contract dim is 4`. The module doc calls this value *"the width configured for this process"* (`sqlite.rs:25-27`) — on that path nothing configured it. Separately, the probe-width refusal message reads `"query embedding has {n} dimensions but session {s} stores vectors of {stored.dim} (see vector_dimensions())"` (`sqlite.rs:1041-1046`), but the number it reports is `stored.dim`, not `vector_dimensions()`; the repro shows those can differ (4 vs 1024), so the pointer sends the operator to a value that contradicts the message.
- **Impact:** Inert today — nothing outside `resolve::check_vector_compatibility` / `check_vector_search_contract` consumes `vector_dimensions()`, and store-only verbs never embed. It is a latent lie for the next consumer, and the misdirecting error message costs an operator a debugging cycle.
- **Required remediation:** Qualify the module doc (the fallback is a *default*, not a configured width, on the `build_store` / `resolve_store_only` path), and either drop `(see vector_dimensions())` from that message or replace it with the durable-contract wording the message actually uses.

### F-R1-9 (P3) — The checked variant's doc states a race mechanism that cannot occur in-process; the real protection is cross-process

- **Evidence:** `sqlite.rs:980-985`: *"SQLite's single connection serializes writers, but a flush landing between two separate statements could still swap the contract out from under vectors already selected."* With `max_connections(1)` (`sqlite.rs:405`), a same-process flush cannot land between two statements of a transaction that holds the only connection — the pool is a mutex. The interleave the transaction actually prevents is the **cross-process** one (`lambo serve` writing while `lambo recall` / `serve-web` reads the same file DB — the documented topology at `end-to-end.mdx:112-118`), and that is the case I verified with the WAL two-connection experiment recorded in the claims table.
- **Impact:** The conclusion is right and the transaction earns its keep; the stated reason is wrong, which makes the comment misleading for anyone reasoning about whether a future `max_connections(n)` change matters (it would, and the comment would then read as already covering it).
- **Required remediation:** Say cross-process. One sentence: within a process the single pooled connection makes the interleave impossible; the transaction closes it against a concurrent *writer process* on the same file DB, which WAL snapshot isolation guarantees.

## Positive observations

- **The seam is real, not asserted.** `select_session_vectors` and `rank_by_cosine` are genuinely separable: selection takes `(tx, session, probe, limit, dim)` and ignores probe/limit, scoring is pure and truncates. An ANN body swap changes neither `rank_by_cosine` nor `vector_candidates_checked` nor any caller. The spec's structural requirement is met exactly as written.
- **Error taxonomy is right at every boundary.** Malformed BLOB (bad UTF-8, unparseable element, wrong width) → `Backend`; contract change and probe/contract width disagreement → `Invariant`; caller limit over `MAX_VECTOR_CANDIDATE_LIMIT` → the pre-existing guard, checked before anything else. `k = 0` short-circuits before the contract read, and the test proves it by passing a contract that would otherwise be refused.
- **`session_embedding_from_parts` is a genuine dedup, not a copy.** `load_session` and the checked read now share one classifier, so a `kind` XOR `dim` corrupt row is reported identically by both — STORE-7 parity with Cockroach's function of the same name, and the (Some, None) / (None, Some) arms preserve the previous messages verbatim.
- **The probe-width guard's authority is deliberately different from Cockroach's, and both are fail-closed.** Cockroach checks the probe against `self.vector_dim` (its DDL width) before opening the transaction (`cockroach.rs:883-891`, `Invariant`); SQLite checks it against the session's durable `stored.dim` after the contract read. SQLite's is the stronger of the two for its schema, since a `BLOB` has no DDL width to check against.
- **Determinism matches both references bit for bit.** `total_cmp` descending, then smaller `NodeId`, then `truncate(limit)` — identical to `VectorSearchStore` (`memory.rs:3319-3325`). The tie test constructs the pair so the smaller id is written *second*, which is the version of the assertion that can actually fail.
- **NULL is not zero.** A concept with no vector is excluded by the `embedding IS NOT NULL` predicate rather than scored 0.0, and the test proves it by adding a vector-less concept and asserting the pool stays at 3.
- **The capability flip does not break any other feature row.** `sqlite-minimal` (`--no-default-features --features store-sqlite`) compiles and runs 7 of the 9 vector tests (the `embed-fixture`-gated `vector_e2e` module correctly drops out); `minimal`, `cockroach`, `demo` and the full `ship` profile (sqlite + cockroach together) all pass. `Capabilities::HISTORY` remains absent and has no production consumer, so nothing else changed shape. `memory.rs:5540-5547`'s comment was correctly updated rather than left to rot, and the E2E-1 override-relabel test's rationale still holds.

It does not: `cli::recall::run_detailed` passes `Some(&backends.embedding)` to `load_reader_graph_with_contract` **unconditionally**, not gated on capability (`cli/recall.rs:111-116`, unchanged by this commit), so that refusal already fired on SQLite pre-F with the actionable `--allow-embedding-mismatch` message. Verified by reading the pre-commit revision of both files.

## Verdict

**REQUEST_CHANGES** — blocking **F-R1-1**, **F-R1-2**, **F-R1-4**, **F-R1-5**.

F1's query path is the strongest part of this change and I could not break it: the transaction is real (verified, not read off the comment), the seam is genuinely separable, the taxonomy and determinism match both references exactly, the codec round-trips and pre-F databases upgrade cleanly, and F2's capability flip is honest at the product level. All ten gate invocations pass, on nine feature configurations.

What blocks is claim quality, in four places where the prose outruns the code. F-R1-1: the read path is carefully built to detect a corruption its own comment says only direct SQL can create, while the public `flush` surface creates it in one call and one such row then fails the entire session's recall *and* hybrid derive, permanently — a state Cockroach's DDL makes unreachable. F-R1-2: the width authority F2 introduces is a self-comparison that cannot fail, asserted as a real store-side check in four places including a test that appears to prove it and a config file shipped as a tested contract. F-R1-4: the recall-parity acceptance box has no artifact, only a formula transcription, when the tree already contains both halves of the harness it needs. F-R1-5: the user-facing docs now promise recall by meaning on SQLite, and the walkthrough they promise it about is configured with an embedder that has no meaning in it — with no committed evidence of a semantic hit under any shipped embedder.

F-R1-3 (derive is the hot path, not recall; 30s cliff; one connection) is a P2 I would fix in the same pass because it is a two-line doc correction plus an optional one-scan-per-derive hoist. F-R1-6 through F-R1-10 are P3s: a guard that catches the threat it names but not `#[ignore]`, an unlinted feature row, a latent 1024 with a misdirecting error message, an imprecise race rationale, and an unmet soft README box plus a broken comment wrap.

Re-review must verify: a width guard at the SQLite write gate (or a corrected comment plus the stated blast radius); that every remaining claim about `vector_dimensions()` as an authority is either made true or withdrawn, in all four sites including `lambo.example.toml`; a vector agreement matrix over the committed fixtures against an exact-cosine oracle; and either qualified docs or a real-embedder SQLite artifact under `evidence/`.
