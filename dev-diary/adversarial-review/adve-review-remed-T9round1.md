## Summary of the fix

`dispatch.rs` classifies a query into `RecallKind::{General, Structural}` by keyword-substring matching; `Daemon::recall` (daemon/mod.rs:363-402) routes a `Structural` query past the word/vector phase-1 gather and, under the graph read guard, calls `dispatch::try_structural`. `try_structural` resolves an anchor concept and returns the anchor's direct structural dependents (Hierarchical/Causal out-neighbors and Dependency in-neighbors) ranked by strongest incident structural-edge weight; on no-anchor/no-dependents it returns `None` and the caller falls through to the blended pipeline (refusal). Instrumentation (`tracing::trace!` target `lambo::recall`) was added to `candidates.rs` (per-candidate phase-1 leg) and `assemble.rs` (per-hit `d*w_daemon + r*w_query` decomposition).

**Verified correct:**
- Both exemplar failures are fixed. `dependency_question_returns_structural_dependent_by_traversal` asserts `RDS-Lambo-Demo-DB` is surfaced and ranked first (weight 9.5 > the SG's rules' 4.5); `delete_safety_question_returns_real_ranking_not_flat_floor` asserts a descending, non-constant ranking (no 0.18 floor). Non-vacuous: they fail on the old blend and the refusal-path test asserts a general query and an anchorless structural query both return `None`.
- Traversal is **structurally sound on edge types**: only `Dependency`/`Hierarchical`/`Causal` are traversed (`dispatch.rs:45-46`), exactly `format::STRUCTURAL_EDGE_TYPES` (format.rs:73-77) and the spec §4.1 errata — **no CoOccurrence/Semantic/Derives/Temporal false dependents**, no self-arcs, concepts-only filter (dispatch.rs:175-179). Anchor + `SG-Base-VPC` resolution correctly prefers the bare Entity by `(type-prio, shortest length, id)` (dispatch.rs:101-118); the prose "the shared security group" branch is gated on explicit "security group" language and refuses otherwise (dispatch.rs:120-139). Empty → `None`, no panic, 200.
- Deterministic ordering by `(score desc, id asc)`; `top_k` respected via `.take(top_k)`; token budget respected by whole-block truncation with longest-prefix-first keeping (dispatch.rs:235, 260-272).
- Integration is centralized: CLI, MCP, and serve-web all reach the modified `Daemon::recall`, so no surface still drives a structural query through the old blend. Regression: all existing recall/daemon/MCP tests pass (no caller of `Daemon::recall`, `RecallHit`, or the `pub mod dispatch` addition broke).
- Instrumentation is behavior-preserving (trace-only, no control-flow change) and measurable (the `capture_logs(TRACE)` test asserts the classification line, per-hit arm line, and the dependent all appear).

## Findings

### P1

### P2

**T9-R1-1 — The classifier can route a genuinely lexical/vector question to the traversal, short-circuiting the blend it was added to protect.**
`src/recall/dispatch.rs:52-79` (markers + `classify`), `src/daemon/mod.rs:363-402` (routing).
`classify` is a plain case-insensitive substring test over `STRUCTURAL_MARKERS` with no grammar/anchor-shape gate, and `Daemon::recall` treats a `Structural` verdict as license to skip the phase-1 gather and, if an anchor resolves with dependents, return a traversal answer with the word/vector pipeline **never run** (mod.rs:393-402 returns early). Because the marker set is broad — bare `"depend"` matches inside `"independent"`, `"dependencies"`, `"depends"`; `"references"` and `"is it safe"` are ordinary prose — a non-structural question can be misrouted. Reproduced: `classify("is the system independent of a single region")` → `Structural` (the `depend` substring inside `independent`); such a query is then only saved by anchor resolution accidentally resolving an identifier *and* it having dependents, at which point the user gets a dependent-list instead of the word/vector recall they actually asked for. That is the exact category error (routing a lexical question to the wrong arm) the fix's own module doc sets out to avoid (dispatch.rs:8-9), just mirrored. The safety valve only mitigates: the existing General tests (`"update user schema"`, `"pagination"`) contain no marker words, so the **false-positive path is entirely untested**.
*Fix:* gate the dispatch on cheap *negative* confirmation — e.g. require the anchor to actually resolve as part of classification rather than letting `try_structural` decide, or restrict markers to explicit dependency phrasings (`"what depends on"`, `"depends-on"`, `"blast radius of"`, `"safe to delete"`) and drop bare `"depend"`/`"references"`/`"is it safe"`; and add a false-positive test asserting a marker-bearing but non-dependency query stays `General` (e.g. `"is the system independent of a single region"`, `"the report references the changelog"`).

**T9-R1-2 — The traversal answer's membership does not match the §4.1 blast-radius predicate, and it annotates itself with that same predicate (self-contradiction).**
`src/recall/dispatch.rs:151-195` (`dependents`) vs `src/recall/format.rs:89-133` (`inbound_sources`/`blast_radii`), `dispatch.rs:239-250` (stamping `blast_radius`).
Two different "depends on" predicates collide in one result. `dependents()` returns **every** direct structural neighbor regardless of whether the dependent has other structural sources. `blast_radius`/spec §4.1 counts a node as depending on `X` only when `X` is its **sole** structural source (`srcs.len() == 1`, format.rs:123-124) — a multi-source dependent is deliberately not a blast-radius dependent because it survives `X`'s deletion. `dispatch.rs:246-250` then fills each canonical hit's `blast_radius` field from `blast_radii`, so a multi-source dependent is simultaneously *returned as a dependent* yet stamped `blast_radius: Some(0)` — internally contradictory, and for the delete-safety exemplar it **over-reports risk** ("is it safe to delete X" would list a node that also depends on Y as breaking). The T9 doc and module doc lean on blast-radius semantics (T9 § "route by query kind"; dispatch.rs:14), and the review brief explicitly asks whether the traversal respects blast-radius semantics / T7's split — it does not, at the membership level. In the current exhibit every dependent is single-source, so both predicates coincide and the tests pass; this is a generalization gap, not an in-exhibit failure.
*Fix:* make `dependents()` (or a caller-facing filter) respect the exclusive single-source depends-on predicate — reuse the shared `inbound_sources` logic (format.rs:89-105) instead of a fresh neighbor scan — so the returned set and the `blast_radius` field agree and the delete-safety answer reflects genuine blast radius. At minimum, reconcile the field with the membership (don't stamp `Some(0)` on a node being reported as a dependent).

### P3

**T9-R1-3 — The "refusal" fall-through runs a degraded blend that has already dropped the vector/recent legs.**
`src/daemon/mod.rs:372-382, 393-402`.
The gather is skipped based on the classifier verdict (`structural → Phase1Input::default()`), *before* dispatch is known to fire. When a Structural query has no resolvable anchor or no dependents, `try_structural` returns `None` and control falls through to the "blend" — but with an empty gather, so the fall-back is keyword(+fixed recent) only, missing the independently gathered vector leg a General classification would have received. So the documented honest refusal (dispatch.rs:18-19, mod.rs:389-392) is not the honest full blend; it is a keyword-only answer that is strictly weaker than pre-T9 behavior for this query class (e.g. "which things depend on zone redundancy" — no identifier resolves — now loses vector recall). `[INFERENCE: severity]` — narrow class, non-wrong answer, but a real regression for it.
*Fix:* only skip the gather when the dispatch *fires* (e.g. classify + resolve anchor *before* gathering, or re-gather on the refusal path), or explicitly document/accept the degraded fall-back.

**T9-R1-4 — Instrumentation allocates eagerly, not gated on `tracing::enabled!`.**
`src/recall/candidates.rs:136-149` (`legs` `HashMap` + per-candidate pushes + `sort/dedup`), `src/recall/assemble.rs:158-170` (`graph.node` lookup + `arm` string + content formatting for *every* assembled member).
The review brief asks whether the added `trace!` allocates in a hot loop. `tracing::trace!` itself is lazy (its args are only evaluated when the filter is enabled), but the hand-written infrastructure around it runs **unconditionally**: `candidates` allocates a `HashMap<NodeId, Vec<&str>>`, pushes into it per candidate, then sorts/dedups per output row, and `assemble` does a `graph.node()` hashmap lookup and builds the `arm`/`content` strings for every member even when no trace subscriber is attached. It is once-per-recall on a small graph, so the impact is negligible today, but it does contradict the "default-invisible, no hot-loop alloc" framing.
*Fix:* wrap the whole instrumentation block in `if tracing::enabled!(target: "lambo::recall", Level::TRACE) { … }` so the eager allocation happens only when a trace subscriber is actually present.

**T9-R1-5 — Structural hits are rendered without the §13 load-bearing-pillar warning.**
`src/recall/dispatch.rs:252` (`render_block(&hit, &[])`) vs `src/recall/assemble.rs:258-274` (which pushes `format::blast_radius_warning` for canonical hits).
A canonical structural dependent gets its `blast_radius` field populated in the hit, but the rendered block omits the "Load-bearing pillar — N nodes depend on this" ⚑ warning that the blended pipeline renders for the same field. A user viewing the structural answer's context sees the score/blast-radius metadata but not the safety callout.
*Fix:* build the warning lines for canonical hits before `render_block` (reuse `format::blast_radius_warning`) so the structural surface and the blend surface render identically.

**T9-R1-6 — The structural answer ignores `query.traversal_depth` and canonical-first promotion (§10).**
`src/recall/dispatch.rs:151-195, 217-288` (hard-coded one hop, no `traversal_depth` use); ordering by strength only.
`RecallQuery.traversal_depth` (default 2, types/mod.rs:603-604) is honored by `expand` in the blend but silently unused by the traversal — defensible since blast-radius semantics is one-hop, but undocumented. And the structural answer does not apply spec §10's "canonical members always promoted first" partition that `assemble` enforces, so a canonical dependent can rank below a non-canonical one by strength.
*Fix:* either honor `traversal_depth` / apply canonical promotion, or document each as an intentional divergence from the blend in the module doc.

**T9-R1-7 — Structural queries bypass the recall cache and the hotlist entirely.**
`src/daemon/mod.rs:393-402` (dispatch returns before the cache key/read/write at mod.rs:405-444 and before the `hot` write at mod.rs:406).
A Structural query neither reads nor populates the recall cache (each is a fresh traversal), and the traversal does not refresh recency for the concepts it returns. Not a correctness bug, but it means repeated dependency questions re-traverse rather than cache, and answered dependents never register recency.
*Fix (optional):* cache the structural `RecallResult` under the same `CacheKey` (it is deterministic per graph snapshot), and/or refresh the hotlist for returned concepts.

### Nits

**T9-R1-N1 — Redundant marker set.** `dispatch.rs:52-62`: `"dependents"` (54), `"dependencies"` (55) and `"depends-on"` (61) are all substrings that `"depend"` (53) already matches; they never add a firing case. Harmless/self-documenting, but the redundancy obscures which are intentional.

**T9-R1-N2 — Doc comment overstates the routing.** `src/daemon/mod.rs:363-365` says "skip the word/vector phase-1 gather I/O and the blended pipeline entirely," but on dispatch failure the blend *does* run (degraded — see P3-3). Comment should say "skip for a dispatched structural query."

**T9-R1-N3 — Fragile test assertion.** `dispatch.rs:531` (`let _ = try_structural(...)`) discards the result and asserts the dependent via log text instead of via `result.hits`; combined with P3-4's eager instrumentation this still passes only because tracing is force-enabled in the test harness. Prefer asserting on `result.hits` directly.

**T9-R1-N4 — Warning count can overstate the context.** `dispatch.rs:280-286`: the "(N dependents)" warning uses `hits.len()` (pre-token-truncation), so under a small `max_tokens` the headline can name more dependents than the context actually renders. Use the kept-block count.

## Explicit judgments

**Classifier correctness — NOT sound (P2).** Substring matching over broad markers (`"depend"`, `"references"`, `"is it safe"`) with the power to fully suppress the blended pipeline is too permissive: proven false positive `"is the system independent of a single region" → Structural`, and the design relies on an accidental anchor-resolve to avoid misrouting. It is correct for both exemplars and for anchor-bearing dependency phrasings, but as a general "route by query kind" classifier it misclassifies a genuine lexical/prose question — the mirror image of the defect it fixes — and the false-positive path is untested.

**Traversal answer soundness — structurally sound on edge types, semantically divergent on membership (P2).** Edge-type handling is correct and complete (Dependency/Hierarchical/Causal only; no CoOccurrence/Semantic/Derives/Temporal; concepts-only; no self-arcs; deterministic; `top_k`/token-budget respected; 200/no-panic on refusal). But the membership predicate (any direct structural neighbor) disagrees with the §4.1 blast-radius predicate it also annotates hits with (exclusive single-source dependent), which is both self-contradictory and, for delete-safety questions, risk-over-reporting in general graphs. Both coincide in the exhibit, so both exemplars are genuinely fixed.

Verdict **REQUEST_CHANGES**: the P2s are narrow (generalization-only; neither breaks the exhibit or any test), but they strike at the two places the brief asked me to be most adversarial (classifier accuracy and structural/§4.1 correctness), so they warrant a round-2 pass before ACCEPT.
