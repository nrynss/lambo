## 1. Help-text findings — MCP (owner: T8.2)

### T88-H1 — internal developer notes are published on the wire (highest impact)

`WireConceptType`'s rustdoc (`src/mcp/server.rs:50-72`) becomes the enum's JSON-Schema
`description` in every `tools/list` response. Captured verbatim from a live stdio session,
the published text includes:

> Byte-echo note (R4 nit): an invalid value here yields serde's `unknown variant …` error …
> This is **not** interceptable at our layer: every tool takes its params through rmcp's
> `Parameters<T>` extractor … revisit if rmcp grows an extraction-error hook.

Every MCP client and every model sees this. It names internal review findings, an internal
helper (`validate_size`), and a dependency's internals. Recommend a short user-facing
`description` on the wire, with the rationale moved to a non-doc comment.

### T88-H2 — `spec §` reference in a published argument description

`RecallParams.agent_id` (`src/mcp/server.rs:98`) publishes
`"Calling agent (spec §2.2 — see the attribution note in the tool docs)"`. Both references
are meaningless to a client: there is no spec on the wire, and there are no "tool docs" the
client can reach.

### T88-H3 — the attribution rule is not in any tool description

A foreign `agent_id` on the six non-reserve tools is accepted, the work is recorded under
the process's agent, and a warning is attached. Only `lambo_reserve`'s description mentions
its (stricter) identity rule. A model reading descriptions alone would reasonably assume
`agent_id` attributes the write. The reference page now states it, but the wire text should
carry at least a sentence.

### T88-H4 — published schemas carry no maxima, and one contradicts the runtime

`tools/list` publishes `top_k`, `max_tokens`, `traversal_depth`, `depth`, `ttl_seconds` as
`{"format":"uint","minimum":0,"type":["integer","null"]}` with **no `maximum`**, and string
fields with no `maxLength`. Runtime enforces `top_k` 1..=100, `max_tokens` 1..=100_000,
depths 0..=5, ttl 1..=3600, strings <= 16384 bytes.

Two consequences: a client cannot pre-validate, so every out-of-range call costs a round
trip; and `top_k`'s published `minimum: 0` **contradicts** the runtime minimum of 1
(`top_k: 0` is refused with `top_k must be in 1..=100`).

### T88-H5 — verified consistent, no action

`lambo_stats`, `lambo_saints`, `lambo_derive`, `lambo_record_action`, `lambo_inspect` and
`lambo_reserve` descriptions match observed behavior. `get_info` instructions match the
binary verbatim (captured from `initialize`). The "never send a timestamp" instruction is
enforced: a client `created_at` is refused by `deny_unknown_fields`.

## 2. Help-text findings — CLI (owner: T8.3, except T88-H9)

### T88-H6 — user-facing lease error carries a spec reference and raw SQL

Verified live (exit 1):

```
lambo derive: conflict: session demo is already held by another writer
(agent-a@host#10492) — it acquired the single-writer lease 66s ago and is still refreshing
it. Spec §2.2 is one writer per session; refusing to open a second. If that holder is
wedged, an operator can force a takeover: DELETE FROM session_leases WHERE session_id =
'<session>';
```

The holder identity and the refusal are excellent. Two problems: `Spec §2.2` means nothing
to a user, and a raw `DELETE` is operator surgery offered in a message that any routine
agent invocation triggers. Recommend dropping the spec citation and moving the SQL behind a
pointer. The reference page quotes this verbatim today because it is what users will see.

### T88-H7 — doubled prefix in the ambiguity error

```
lambo inspect: inspect: 'a' matches 5 concepts — name one exactly, or pass its node_id:
```

The command prefix is applied twice (`src/cli/inspect.rs` message already begins `inspect:`,
and the dispatcher adds `lambo inspect: `). Verified live.

### T88-H8 — `MAX_INSPECT_NODES` doc-comment contradicts the code

`src/cli/caps.rs:30` says "Cap on neighbours rendered **per `inspect` frontier level**".
`render_neighbourhood` (`src/cli/inspect.rs:146`) initialises one `budget = MAX_INSPECT_NODES`
**before** the hop loop and decrements it across all hops, so 200 is a **total**, not
per-level. The doc-comment is wrong; the code is fine. Reference pages state the total.

### T88-H9 — `lambo demo` help describes behavior that does not exist (owner: T8.4 / T8.5)

`--help` says "Scripted two-agent demo scenario". The implementation
(`src/main.rs:388-392`) is a stub: it prints `lambo demo (stub): scenario=rest-api` and
exits 0 without touching memory. `--scenario` has no help text of its own and no list of
valid values. The reference page now says the command is not built yet.

### T88-H10 — `lambo release` after a CLI `reserve` reports a generic not-found

`reserve --help` and the runtime note both explain that a CLI reservation ends when the
process exits. The follow-up `release` then fails with
`lambo release: not found: no reservation on node <uuid>` (exit 1), which does not connect
back to that explanation. A message naming the cause would close the loop. Low severity:
the help text is accurate, only the error is terse.

### T88-H11 — verified consistent, no action

Every subcommand and every flag has help text. `--config` is correctly documented as global
on all subcommands. Concept-kind values, defaults (`--depth 2`, `--ttl-seconds 30`,
`--port 7700`, `--bind 127.0.0.1`, `--agent lambo-serve`, `--transport stdio`), the
`CHILD:PARENT` orientation, and the reader-vs-writer note on `stats` all match the binary.
Exit codes match the documented scheme (usage 2, runtime 1).
