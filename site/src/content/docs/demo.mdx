Run `lambo demo` to see two scripted agents share memory while building a REST API. The demo shows concept promotion and the warnings an agent receives before editing shared work.

## Run the demo

Run the command in a directory without a Lambo configuration to use the in-memory store.

```bash
lambo demo
```

By default, each run creates a fresh session ID.

| Flag | Default | What it does |
|---|---|---|
| `--scenario` | `rest-api` | Picks the scenario (`rest-api` is the built-in scenario). |
| `--session` | fresh id per run | Writes into a session id you choose. |

<Warning>
If you pass `--session`, choose a fresh session ID. Existing memory changes the scenario’s starting state and can cause its assertions to fail.
</Warning>

## What the scenario does

Agent A records `user schema`, `auth middleware`, and `session store`, then records the actions that depend on them.

Agent B adds rate limiting and records its dependencies on `auth middleware` and `user schema`.

Agent A adds `oauth_id` to `user schema`.

Agent B calls `recall("update user schema")`. The result marks the concept as load-bearing, shows its 15 dependents, and reports Agent A’s recent edit.

## What the demo checks

Each act demonstrates one claim you can check in the output.

- Twelve interactions produce 27 concepts. Repeated ideas can match concepts that the agents have already written.
- The canonization engine promotes `user schema` through Candidate, Venerable, and Canonical based on its recorded evidence.
- Recall reports a blast radius of 15 for `user schema`, reflecting nine child concepts and six dependent actions.
- The conflict notice names the other agent and reports the age of its write.

## How the demo runs

The demo uses the public `Memory` API. Lambo builds the graph, applies canonization, and renders the recall block.

The run checks the interaction count, concept count, and blast radius before it reports success.

## Timing overrides

The demo changes background intervals and the conflict window to finish quickly. Its promotion thresholds match the defaults.

| Knob | Default | Demo |
|---|---|---|
| `canonization_edge_min_age` | 60s | 10ms |
| `canonization_eval_interval` | 60s | 25ms, frozen during the build phase |
| `daemon_tick_interval` | 1s | 5ms |
| `backend_flush_interval` | 1s | 5ms |
| `gc_interval` | 10000 mutations | 1 mutation |
| `conflict_recency_window` | 30s | 810s |

The conflict window is the one knob the demo widens. The demo stamps its writes from a script clock that spans 13 minutes, so the window is the default 30 seconds plus that span. Every scripted write stays inside it, as every write did when the run was stamped from the wall clock and took about a second.

Every admission threshold stays at its default. Those are `gc_survived` at least 3 and dependents from at least 2 other interactions for Candidate, at least 3 distinct sources and coverage at least 0.3 for Venerable, and blast radius above 5 for Canonical. This demo runs the default `Swarm` policy, where since 0.6.0 no stage selects by score (`Solo` still admits Candidates by score band), so the run ends with 15 canonization events: ten Candidates, four of them Venerable, and `user schema` alone Canonical.

## Why two runs match

The demo controls when canonization runs so the outcome stays stable across repeated runs.

After the last write it declares session synonyms one at a time until every concept clears the `gc_survived` floor, which opens Stage 1's survival gate uniformly. Then it polls until the audit trail stops growing across three consecutive canonization cycles. With the graph frozen and every scoring dimension measured against the session rather than the wall clock, the outcome becomes a pure function of the graph.

The run prints a normalized summary with the volatile parts masked. Session ids, node ids, scores, and recorded ages become placeholders, so you can diff two runs by eye.

<Note>
Waits are bounded polls on observable conditions, never fixed sleeps. The demo either observes the condition it needs or fails naming the condition it was waiting for.
</Note>

## Read the output

The canonization section shows the engine promoting one concept across three cycles, then confirming it reached a fixed point.

```
── CANONIZATION — the engine, not the script, promotes user schema ─────
  gc_survived floor 3 ≥ 3 — Stage 1's survival gate is open for every concept
  cycle   1   user schema              → Candidate   (canonization_events row written)
  cycle   2   user schema              → Venerable   (canonization_events row written)
  cycle   3   user schema              → Canonical   (canonization_events row written)
  no transitions for 3 consecutive cycles — the state machine is at its fixed point
```

The normalized outcome includes the warning about `user schema`. The summary replaces variable values with placeholders.

```text
    user schema [Entity, canonical] (score <s>, id <node>, blast radius 15, names ["user document","user entity","user model"])
    ⚑ Load-bearing pillar — 15 nodes depend on this. Modify with caution.
    Agent A wrote to it <n> seconds ago
```

In the live recall block, ages reflect the demo’s scripted timestamps.

## Run it against a durable store

Point the demo at SQLite, PostgreSQL (`pgvector`), or CockroachDB to exercise the full write-behind path and leave a graph behind you can inspect.

```bash
lambo --config lambo.toml provision
lambo --config lambo.toml demo --session evaluation
```

Then read the result back with ordinary read verbs, which do not take the writer lease.

```bash
lambo --config lambo.toml saints --session evaluation
lambo --config lambo.toml inspect --session evaluation --focus "user schema"
lambo --config lambo.toml serve-web --session evaluation
```

On CockroachDB you can also query `canonization_events` directly, through `psql` or through the CockroachDB managed MCP server, and watch the same transitions the demo narrated. Scope the query by `session_id`, because one cluster accumulates events from every session that has run against it:

```sql
SELECT node_id, from_status, to_status, blast_radius, occurred_at
FROM canonization_events
WHERE session_id = '<your session id>'
ORDER BY occurred_at;
```

Run through the managed MCP server, that returns the status walk as the demo told it: the parent concept moving Candidate, then Venerable, then Canonical, with the blast radius recorded on the promotion and left null on the earlier hops.
