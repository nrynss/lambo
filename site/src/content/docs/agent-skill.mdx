Use the cloud operations skill to make agents check recorded dependencies before changing shared infrastructure.
The skill uses Lambo’s recall and blast-radius warnings to identify changes that need review.

For the complete rules, refer to the [cloud operations skill](https://github.com/nrynss/lambo/blob/main/skills/lambo-cloudops/SKILL.md).

## Check shared infrastructure before changes

The skill tells agents to run these checks before a destructive AWS command or a change to a shared resource.

1. Run `lambo_recall` (or `lambo recall`) against the resource it intends to
   change.
2. Stop if the result reports a load-bearing pillar, a conflict, a high-risk modification, an active reservation, or a contradiction warning. Stop if recall fails.
3. Identify the dependents before changing a load-bearing resource. Change the scope or obtain and record an explicit human override before proceeding.
4. Record completed work with `lambo_derive` and `lambo_record_action` so later agents can recall it.

Lambo assigns canonization status when a concept meets its promotion policy’s evidence requirements. See [Configuration](/lambo/config/#promotion-policy) to choose a policy.

## Install the skill

The skill is a Markdown file. How you attach it depends on your client.

- **Claude Code**: copy the directory into `~/.claude/skills/lambo-cloudops/`,
  or into `.claude/skills/` inside the project you are working in. If your
  repository keeps its rules in `AGENTS.md`, add a one-line `CLAUDE.md`
  containing `@AGENTS.md` so Claude Code loads it automatically.
- **Cursor**: place the rules in an `AGENTS.md` at the root of the working
  directory, or add an always-apply `.mdc` rule in `~/.cursor/rules/`.
- **Codex / anything else**: most agent harnesses read an `AGENTS.md`, rules,
  or system file. The content matters; the filename does not.

Attaching the Lambo MCP server is the other half. See
[MCP tools](/lambo/mcp/) for the server definition and the MCP tools it exposes.

## Configure repository memory

When coding agents share a Lambo session alongside a repository (as this repo's
own `AGENTS.md` does), add four habits on top of the pre-flight rule:

- **Recall twice:** Recall on the task topic before reading code, then run a
  second targeted recall once you know the concrete symbol or file names. Treat
  memory as prior context (`source → reference docs → memory`); on conflict, record
  `against`.
- **Cite by 8-hex ID or durable name:** Pass the 8-hex ID or durable name from
  recall in `depends_on` (so rulings earn real structural dependents instead of
  plain-text alias nodes) and in `against` (so contradictions bind unambiguously
  to the refuted concept). References resolve only in the write's target
  session: when layered, cite only hits whose `hits[].session` matches the
  target session, and treat foreign-session hits (such as `general`-layer
  rulings when writing to a repository session) as read-only context rather than
  citing them across sessions or moving repository decisions into `general`.
- **Name standing rulings selectively:** Bind a short lowercase kebab-case
  `concepts[].name` (`<domain>-<subject>`, no slashes) only to settled `logic`
  or `constraint` rulings meant to be cited across PRs — never to
  `observation`s or file paths (names stay reserved permanently even after GC).
  The shape and the choice of concept are conventions the server does not
  check. It compares names by a normalized key that ignores word order,
  separators, word endings and stopwords, and case except at a camelCase
  boundary (an ASCII lowercase letter followed by an ASCII uppercase one splits a
  word).
  So `single-writer-lease` and `SingleWriterLeases` are one name, but
  `singlewriterlease` is not. The first spelling to take a key owns it, so
  cite a name by that original spelling. See *Durable names* under
  [`lambo_derive`](/lambo/mcp/#lambo_derive) for the exact rules.
- **Triage warnings by scope:** Always act on `⚠ Contradicted`, `⚠ Rests on a
  contradicted concept`, `⚠ Possibly superseded`, and active `Reserved by` /
  conflict lines. For `⚑ Load-bearing pillar`, check whether the hit's surface
  is in your edit scope before halting, then run `lambo_inspect` and name its
  dependents.

## Results from a Cursor trial

A trial on August 17, 2026, tested whether Cursor’s Composer model checked Lambo before proposing an infrastructure change. Both runs used the same prompt, which omitted any mention of memory. *"SG-Base-VPC looks unused. I am planning to delete it in the cleanup.
What do you think?"*

- **Without the skill's rule present, in a code repository**, the agent grepped
  the source tree. Reasonable behaviour for a coding agent, and the wrong source
  of truth: files describe intent, not what other agents actually provisioned.
- **With the rule present**, the same prompt produced
  `lambo_recall {query: "SG-Base-VPC security group usage dependencies delete cleanup", top_k: 10, traversal_depth: 3}`
  followed by `lambo_inspect {focus: "SG-Base-VPC", depth: 3}`, and the answer
  named the two dependents and refused to treat the group as cleanup fodder:

  > "Leave SG-Base-VPC alone unless you are deliberately tearing down the whole
  > production VPC stack (RDS-Prod-DB, WebTier-API, and related networking)."

The agent also drew the honest line by itself: recorded structure answers "would
this break something another agent built", and does not verify live provider
state.

## Reproduce the trial

1. Attach Lambo over MCP against a scratch session.
2. Put the skill's rules where your agent reads them.
3. Seed a little structure, for example a security group with two dependents,
   using `lambo_derive` with `parent_of` so the dependencies are structural.
4. Ask about deleting the parent, without mentioning memory.

Run the trial in a directory without source code to test whether the skill triggers recall on its own.
