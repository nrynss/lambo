Lambo is agentic graph memory. It runs as an MCP server that exposes seven tools your agent can call to store what it learns, recall relevant prior memory, and coordinate edits. A running `lambo serve --session <id>` process is the single writer for that session, and your agents connect to it as MCP clients.

## Transports

Lambo serves over stdio by default, and over HTTP when you ask for it.

| stdio | `lambo serve --session demo` | The default. Works with any MCP client through the standard `mcpServers` configuration. |
| HTTP | `lambo serve --session demo --transport http` | Streamable HTTP on port `7700`, bound to `127.0.0.1`. Change them with `--port` and `--bind`. |

On loopback the HTTP transport is unauthenticated by default. Binding anywhere else fails closed and requires a bearer token (`--auth-token` or `LAMBO_AUTH_TOKEN`). It also applies a global rate limit, a ceiling on concurrently live sessions, and a request-body limit. See [Configuration](/lambo/config/#http-transport) for the knobs.

<Warning>
The process behind the HTTP endpoint is a session writer, and it is not open to the world. Unless you bind only to loopback, configure a bearer token or `lambo serve` refuses to start, and once you do, every request must carry `Authorization: Bearer <token>`. Protect it as a writer, not as a read-only service.
</Warning>

### More than one client on one machine

Starting a second `lambo serve` for the same session no longer fails. The first process to
start holds the session and becomes the hub; later ones connect to it over a local socket and
forward every tool call, so each client gets full read, full write, and read-your-writes on
request against one graph rather than one client getting memory and the rest getting none.
"On request" because writes are applied in the background and acknowledged with a receipt
(see [`lambo_derive`](#lambo_derive)); waiting on that receipt works through the hop exactly
as it does in the hub. There is nothing to configure — point each client at
`lambo serve --session <id>` the ordinary way.

Two things are worth knowing. Writes still happen in the holder, so `lambo_stats` reports the
holder's process; and if the holder dies, forwarded calls return a clear error saying nothing
was read or written and that memory returns once a `lambo serve` holds the session again —
your agent should carry on rather than block on it. Forwarding is local-only and applies to
the stdio transport; a second `--transport http` serve on a held session still refuses to
start, and says which process holds it.

The socket lives in a private per-user directory: `$XDG_RUNTIME_DIR/lambo` if that variable is
set, otherwise `/tmp/lambo-<uid>`. Those are the only two, and `TMPDIR` is deliberately not
among them — some clients pass it through to the servers they spawn and some scrub it, so
keying a shared address on it made two clients on one machine disagree about where the socket
was. The directory must be mode 700 and owned by you; `lambo serve` creates it that way and
refuses both to bind into and to forward into one that is not, since a socket in a directory
other accounts can reach would let any local account issue writes against your session. If you
see that refusal, remove the directory or point `XDG_RUNTIME_DIR` at one you own. A very long
`XDG_RUNTIME_DIR` can also leave no room for a socket address (the limit is 104 bytes for the
whole path); a serve on such a machine still serves its own client normally and logs the
reason, and only the forwarding stops working.

Clients that disagree about the directory anyway still work. The socket's file name is derived
from the session and the store, so a serve that finds a holder listening somewhere else
forwards to wherever the holder actually published, and refuses only when the *name* differs —
which means a different session or a different store, not a different environment.

The socket file itself is disposable. Deleting it while a holder is running makes that holder
unreachable to other clients until it restarts — the holder keeps working for its own client
and no data is at risk. Deleting one left behind by a crashed process is always safe; so is
leaving it, because the next holder clears it under the session lease.

### HTTP for a machine with several independent clients

Stdio is the default transport, and it is the right one for a single orchestrator and
its subagents — that is one connection to one server and works through the client's
`mcpServers` entry with nothing else to do. The moment a machine runs more than one
*independent* client — OMP and Claude Code and Pi, say, each a distinct product — reach
for HTTP instead. Run one `lambo serve --session <id> --transport http` and point every
client's `mcpServers` at that one URL, so a single process owns the session as its
writer rather than each client spawning its own stdio `serve` that then has to proxy to
the holder. The reason for the switch is single-writer, not subagents: the plurality
that makes stdio the wrong default is independent clients on one machine, not the
number of agents under a single orchestrator.

Moving a client from `command` to `url` is a migration across *every* config layer that
names the server, and a stale entry anywhere rejects it. A client reads the project
`.mcp.json`, the user or global scope, and the per-client files — Pi's
`~/.pi/agent/mcp.json`, Cursor's `~/.cursor/mcp.json`, an OMP workspace `.mcp.json`,
Codex's `~/.codex/config.toml` — and a layer that still holds `command` beside the new
`url` is rejected even when the endpoint itself responds. Migrate by copying the
registration into each layer that names the server; never by editing one file and
assuming the others pick it up.

## What every tool expects

Every tool takes an `agent_id`, and every tool rejects any argument it does not define, so a typo fails rather than being ignored.

<Note>
Do not send timestamps. Lambo stamps all times itself, and no tool accepts a timestamp argument. Sending one is refused by name.
</Note>

You manage ordering. A read sees a write only after that write's tool call has returned. If you want a recall to see something you just derived, call `lambo_derive` first, wait for it to return, and then call `lambo_recall`.

### What Lambo accepts in text

Any string you send is limited to 16 KB. Lambo also refuses two classes of character. In both cases it names the offending codepoint and never echoes the raw byte back to you.

- **Control characters.** Tab and newline are the only ones you may send. Every other control character is refused, so a stray `U+0000` or an ANSI escape sequence cannot reach stored content and corrupt whatever renders it later.
- **Invisible formatting characters.** Lambo refuses bidi overrides such as `U+202E`, the zero-width family such as `U+200B`, blank-rendering fillers such as `U+3164`, the byte order mark, and tag characters. These paint nothing on screen, so a concept carrying one reads as innocuous to you while reading differently to a model.

Invisible characters that real writing needs stay allowed. The zero-width joiner and non-joiner, the variation selectors, and the combining grapheme joiner all pass, so Persian, Indic, and emoji text goes through unchanged.

<Note>
Lambo keeps the allowed invisible characters in the content it stores, and ignores them when it decides whether two concepts are the same. Texts that look identical on screen therefore land on the same concept. Nobody can mint a hidden duplicate of an existing concept by slipping an invisible character into it.
</Note>

```json
{"content": [{"type": "text", "text": "concept.content contains a disallowed invisible formatting character (U+202E); bidi overrides, zero-width characters, blank fillers, the BOM and tag characters are refused because they are invisible in review but not to the model (zero-width joiner and non-joiner are allowed, and are stripped from canonical keys)"}],
 "isError": true}
```

### How agent_id is used

Send the id of the agent making the call. Lambo honours it: your work is recorded in the graph under exactly that id, and your soft locks are held under it. One `lambo serve` process serves any number of agents, so several clients can share one server without any of them losing its identity. The process's own `--agent` is what it holds the session lease and writes its heartbeats under; it is not applied to your calls.

The id is **caller-asserted and unverified**. Nothing authenticates it: over stdio the client owns the process, and over HTTP one bearer token authenticates the server rather than each agent. So identity here is a cooperative declaration, which is the same trust level Lambo's soft locks already have — they are advisory and live in RAM. In practice:

- Use one stable id per agent, such as `claude-orchestrator` or `codex-agent`.
- Send the id on one line, at most 256 characters. `agent_id` refuses newlines, tabs, any other control character, the Unicode line and paragraph separators `U+2028`/`U+2029`, and length over 256 even though other strings accept some of them, because your id is rendered into other agents' context blocks as the holder of your locks: a line break there would let you write lines into someone else's context, and a very long id could push the block it annotates out of a budgeted context entirely.
- Distinct ids get distinct locks and contend honestly: one agent reserving a node another holds gets a conflict that names the holder and the expiry, so it can wait or work elsewhere.
- Two callers sending the **same** id share one lock and can release each other's. That is by design, and worth knowing before you let two clients default to the same name.

### Errors

Errors come back as normal tool results with `isError` set to `true` and a short reason. Lambo never puts internal detail such as endpoints, connection strings, or driver messages into an error, and logs the full detail server-side instead.

| What went wrong | What you see |
|---|---|
| A missing, unknown, or malformed argument | The parameter error naming the field, before the tool runs. |
| A value outside its range | The bound, such as `top_k must be in 1..=100`. |
| A string over the size cap | The field, the cap, and the size given. |
| A string carrying a control or invisible character | The field, the offending codepoint, and which class of character was refused. |
| A focus that matches several concepts | The candidate list with node ids, so you can name one exactly. |
| An `agent_id` that is not a single line | That the id must be one line with no tabs, control or line-separator characters, and the codepoint found. |
| An `agent_id` over 256 characters | The cap and the length given. |
| A lock another agent holds | Who holds the node and until when, and that nothing was reserved or released. |
| The server losing its single-writer lease | The class `conflict` and a note that the detail was logged. The holder and expiry are shown only for a lock another agent holds; the lease's own state is not model-facing. |
| A store or embedding failure | The class of failure, such as `store error`, and a note that the detail was logged. |
| A handler fault | An internal error, with a note that the call had no effect beyond anything already written. |

## Tools

These are the seven tools your agents call.

### lambo_recall

Recall relevant memory for a query. This returns the Lambo context block, which is the set of memories that matter for the query, with markers for canonical facts, blast-radius warnings, and conflicts. The block is the first text content of the result, and the individual hits come back as structured content alongside it.

Recall combines keyword matching with vector similarity, then expands through the graph. Which of those legs run depends on your store. Every concept your agents write through `lambo_derive` and `lambo_record_action` keeps its embedding. A store with vector search then finds memory your own agents wrote, not just memory you loaded in bulk.

| Store | What recall uses |
|---|---|
| CockroachDB | Keyword matching and vector similarity, plus graph expansion. |
| SQLite | Keyword matching and vector similarity, plus graph expansion. |
| In-memory | Keyword matching plus graph expansion. |

Recall still works without a vector leg. You get matches on the words you use rather than on meaning, so a query that shares no vocabulary with a stored concept may miss it.

| Argument | Type | Required | Range or default |
|---|---|---|---|
| `agent_id` | string | Yes | |
| `query` | string | Yes | Up to 16 KB. |
| `top_k` | integer | No | `1` to `100`. Defaults to the configured value, which is `5`. |
| `max_tokens` | integer | No | `1` to `100,000`. Defaults to the configured value, which is `500`. |
| `traversal_depth` | integer | No | `0` to `5`. Defaults to the configured value, which is `2`. |

```json
{"name": "lambo_recall", "arguments": {"agent_id": "agent-a", "query": "stdio wire check"}}
```

```json
{"content": [{"type": "text", "text": "stdio wire check [Entity] (score 0.86)"}],
 "structuredContent": {"context": "stdio wire check [Entity] (score 0.86)",
   "hits": [{"node_id": "ddbc8bc8-52ed-465b-9a2a-b0066bda51ad", "content": "stdio wire check",
             "concept_type": "Entity", "score": 0.8565231086776713,
             "is_canonical": false, "blast_radius": null}],
   "warnings": []},
 "isError": false}
```

### lambo_derive

Store new concepts learned from the current interaction.

**This call returns before the write is applied.** Lambo validates your input, fixes this write's place in the session's order, and answers — the embedding and the graph insert happen in the background. A warm derive against a local BGE-M3 embedder went from a 14 ms call to a 0.05 ms call this way, because the embedder is no longer inside it. Two consequences worth planning around:

* The ack carries a **receipt id** instead of the node ids, because it does not yet know them. Its outcome — what was created, what matched an existing concept, or why it failed — is delivered two ways: piggybacked onto your next tool response as a `write receipts:` text block, and fetchable at any time by passing the receipt to [`lambo_stats`](#lambo_stats).
* If you need a write visible to your very next read, pass the receipt to `lambo_stats` with a `wait_ms` first. That is the only thing you have to do differently, and only when you actually need it.

Writes you send one after another are applied in that order, whatever other agents are doing through the same server. Two calls you fire concurrently are a different matter: each one's place in the session's order is fixed when it is accepted, so two overlapping calls can be accepted in either order, and Lambo does not invent one for you. Duplicate detection is unaffected: the embedding still happens before the insert.

**A derive needs the embedder, and on the default configuration it needs it for every write.** With `match_strategy = "hybrid"` — the default — a concept is stored with its embedding or it is not stored at all: an embedder that is unreachable, restarting or too slow fails the write rather than applying a concept that semantic recall could never find. The failure is honest and per call (the receipt says `failed` and that nothing was written). What survives an outage is the *unattempted* write: one not yet attempted when the session closes waits for an embedder as a durable intent, replayed by the next serve; a write the worker reaches during the outage fails, and its receipt says so — the honest asymmetry, because only the in-session caller has a receipt to read. But it does mean a server whose embedder is down accepts reads and refuses writes. If you would rather keep writing without an embedder, that is a lawful mode and you get it by **declaring** it: set `match_strategy = "canonical"` for keyword-only concepts, session-wide and deliberately, instead of having it happen to you one call at a time.

| Argument | Type | Required | Notes |
|---|---|---|---|
| `agent_id` | string | Yes | |
| `concepts` | array of `{content, concept_type}` | Yes | Up to 64 per call. |
| `concepts[].content` | string | Yes | Up to 16 KB. |
| `concepts[].concept_type` | enum | Yes | One of `entity`, `logic`, `constraint`, `resource`, `observation`. |
| `parent_of` | array of `{parent, child}` | No | Hierarchy links. Both ends resolve as concepts, and either may be created. |

<Warning>
`concept_type` is lower case on the wire. Sending `Entity` is refused with "unknown variant `Entity`, expected one of `entity`, `logic`, `constraint`, `resource`, `observation`".
</Warning>

```json
{"name": "lambo_derive", "arguments": {"agent_id": "agent-a",
  "concepts": [{"content": "user schema", "concept_type": "entity"}],
  "parent_of": [{"parent": "user schema", "child": "auth middleware"}]}}
```

```json
{"content": [{"type": "text", "text": "accepted 1 concept(s) for background write; validated and ordered, not yet applied\nreceipt lwr1.708217ebbf356946.1a01fa59db7.15: pending — admitted, not yet applied; ask again\nThe outcome arrives on your next tool response. To wait for it, call lambo_stats with receipt=lwr1.708217ebbf356946.1a01fa59db7.15 (add wait_ms to block)."}],
 "structuredContent": {"summary": "accepted 1 concept(s) for background write; validated and ordered, not yet applied",
   "receipt": "lwr1.708217ebbf356946.1a01fa59db7.15", "receipt_state": "pending", "warnings": []},
 "isError": false}
```

`created` and `matched` are **absent** rather than empty. An empty list would be a claim about a write that has not run; the ids live on the receipt.

A write refused for backpressure answers the same shape with `receipt_state` of `dropped` and a summary that says plainly that nothing was written. It is not an error: the call succeeded, the write did not.

### lambo_record_action

Record something the agent did, along with what it produces, modifies, and depends on. The action becomes a `Resource` concept, `produces` and `modifies` become causal edges, and `depends_on` becomes dependency edges.

**Like `lambo_derive`, this returns before the write is applied**, and its ack carries a receipt resolved the same way. It has no embedding step of its own, so what asynchrony buys here is ordering: both write tools feed one queue per agent, so an action you record and then derive from is applied in that order.

| Argument | Type | Required | Notes |
|---|---|---|---|
| `agent_id` | string | Yes | |
| `action` | string | Yes | Up to 16 KB. |
| `produces`, `modifies`, `depends_on` | array of string | No | Up to 64 entries combined across the three. |

```json
{"name": "lambo_record_action", "arguments": {"agent_id": "agent-a",
  "action": "created migrations/003.sql", "produces": ["migrations/003.sql"],
  "depends_on": ["user schema"]}}
```

```json
{"content": [{"type": "text", "text": "accepted action 'created migrations/003.sql' for background write; validated and ordered, not yet applied\nreceipt lwr1.708217ebbf356946.1a01fa59db7.16: pending — admitted, not yet applied; ask again\nThe outcome arrives on your next tool response. To wait for it, call lambo_stats with receipt=lwr1.708217ebbf356946.1a01fa59db7.16 (add wait_ms to block)."}],
 "structuredContent": {"summary": "accepted action 'created migrations/003.sql' for background write; validated and ordered, not yet applied",
   "receipt": "lwr1.708217ebbf356946.1a01fa59db7.16", "receipt_state": "pending", "warnings": []},
 "isError": false}
```

`action_node`, `created` and `edges` are on the receipt, for the reason `lambo_derive`'s ids are.

### lambo_reserve

Take a soft lock on a memory node before you edit it, so two agents do not edit the same concept at once. Set `release` to `true` to release the lock instead.

| Argument | Type | Required | Notes |
|---|---|---|---|
| `agent_id` | string | Yes | The identity the lock is held under. Caller-asserted and unverified: a distinct id gets a distinct lock, and callers sharing an id share the lock. |
| `node_id` | string (UUID) | Yes | From `lambo_recall` or `lambo_inspect`. |
| `ttl_seconds` | integer | No | `1` to `3600`. Defaults to `30`. |
| `release` | boolean | No | Release instead of reserve. |

```json
{"name": "lambo_reserve", "arguments": {"agent_id": "agent-a",
  "node_id": "478416c2-0000-0000-0000-000000000000", "ttl_seconds": 60}}
```

<Note>
Reservations are advisory and live in memory only, so they do not survive a server restart. After a restart, the absence of a reservation does not guarantee that nobody else is working on the node.
</Note>

### lambo_inspect

Look at the neighbourhood around a concept, including its type, whether it is canonical, its blast radius, and the edges leading out from it.

| Argument | Type | Required | Notes |
|---|---|---|---|
| `agent_id` | string | Yes | |
| `focus` | string | Yes | Concept text or a node UUID. Up to 16 KB. |
| `depth` | integer | No | `0` to `5`. Defaults to `2`. |

Lambo resolves `focus` exactly first, then as a single substring match, and says in the result text when it resolved a substring. If the focus matches several concepts it refuses rather than guessing, and lists up to ten candidates with their node ids. The rendered neighbourhood stops after 200 neighbours and says so.

```json
{"name": "lambo_inspect", "arguments": {"agent_id": "agent-a", "focus": "user schema", "depth": 2}}
```

### lambo_saints

List the session's canonical memories, which are the concepts Lambo has promoted to canonical facts. Each row carries the node id, the content, the type, the blast radius, the access count, and when it was created. This tool takes only `agent_id`.

### lambo_stats

Report session health: flush lag, write-behind log depth, background write queue depth, node, edge, and concept counts, canonization progress, and whether the session is degraded. It is also where you ask what happened to a write.

| Argument | Type | Required | Notes |
|---|---|---|---|
| `agent_id` | string | Yes | |
| `receipt` | string | No | A receipt id from a `lambo_derive` or `lambo_record_action` ack. Answers what happened to that one write. |
| `wait_ms` | integer | No | `0` to `4000`. With `receipt`, wait this long for the write to be applied before answering. A larger value is clamped, not refused. |

Unlike `lambo stats` on the command line, this reaches the writer, so the flush figures are real rather than `n/a`.

**Asking about one write.** Pass `receipt` and the payload gains a `receipt` object: an `id`, a `state`, and a `detail` sentence written for a model to read. On `applied` it also carries `created`, `matched`, `created_count`, `matched_count`, and the `semantic_merged` / `reinforced` / `edges` counts — everything the ack could not know. Add `wait_ms` and the call blocks until the write lands, which is how you get read-your-writes when you need it; the session figures in the same payload are read after that wait, so they never disagree with the receipt beside them.

The `state` is one of nine, and none of them is "unknown":

| State | What it means |
|---|---|
| `applied` | The write is in the graph. Its ids are in the same object. |
| `pending` | Admitted and ordered, not yet applied. Ask again, or ask with `wait_ms`. |
| `pending_replay` | Admitted by an **earlier** server on this session, recorded as a durable intent, and still owed a replay. Not the same wait as `pending`: it sits behind a backlog replayed one write at a time, and it may settle in this server or in a later one. Ask again, and recall rather than re-deriving. |
| `failed` | Attempted and rejected. Nothing was written; `detail` says why. |
| `intent_durable` | The session closed before this write was applied — and the write is **not lost**: it is recorded as a durable intent, and the next server on this session **re-attempts** it, in the order you sent it. Ask about the same receipt id there to learn the outcome: `applied_after_restart` if it landed, `pending_replay` while it is still owed, `failed` if the embedder refuses that content. |
| `applied_after_restart` | The write was applied across a restart — either replayed from its durable intent by this server, or applied by the previous one with the fact carried over. The `detail` carries the applied summary; recall finds the concepts. |
| `dropped` | Never attempted — the queue was full when you were acked. Nothing was written. |
| `expired` | This server issued the receipt and no longer holds its outcome. Receipts are kept for 300 seconds. Recall to see whether the write is there. |
| `restart_lost` | A **different** server process issued it and no durable record of it survived. The outcome is unknowable from here: the write may or may not have been applied before that process ended. Recall before re-deriving. |
| `never_issued` | This server has never handed out that id. |

A receipt is scoped to the agent that created it, so asking about someone else's answers `forbidden` and discloses nothing about the write.

**Write queue keys**, always present because every write goes through the queue: `write_queue_bound`, `write_queue_lane_bound`, `write_queue_measured`, `write_queue_bound_source`, `write_queue_items_per_sec`, `write_queue_serial_items_per_sec`, `write_queue_probe_serial_items_per_sec`, `write_queue_outstanding`, `write_queue_accepted`, `write_queue_applied`, `write_queue_failed`, `write_queue_abandoned`, `write_queue_deferred`, `write_queue_replayed`, `write_queue_replay_owed`, `write_queue_dropped`, `write_queue_dropped_closed`, and `receipts_retained`.

The bounds guard fairness and memory, never durability: an acked write is recorded as a durable intent at admission, so a queue that cannot drain defers work to the next server on the session instead of losing it. `write_queue_lane_bound` (64) is how many of *your* writes can be outstanding at once — one agent's fair share, a sixteenth of the queue — and `write_queue_bound` (1024) is the ceiling across every agent on the server, sized from how many receipts Lambo will hold. Both are fixed shares rather than measurements, deliberately: a bound derived from a measured rate was wrong in a new way every time the workload changed shape, and with durability carried by durable intents, being refused is something you can retry while being lost is not. A single busy agent meets the lane bound first, and its receipt says which bound refused it.

The rate keys are telemetry about your embedder, not the source of any bound. `write_queue_measured` says whether anything measured a rate at all; `write_queue_bound_source` says what did — `probe` for the startup measurement, `observed` once your own writes have been timed (the better number, and the one that keeps tracking an embedder that slows down later), or `unmeasured`. `write_queue_items_per_sec` and `write_queue_serial_items_per_sec` are the raw rates at two widths, and `write_queue_probe_serial_items_per_sec` is the startup probe's own figure, kept beside the rate in force rather than overwritten by it: while the source is `probe` the two are the same number, and once `observed` takes over the gap between them says how far the startup estimate was from the work your agents actually send — several times faster usually means your concepts are much longer than the text the probe embeds.

Read `write_queue_dropped` first: a non-zero value means acked writes did not happen, and each one says so on its own receipt. `write_queue_dropped_closed` is the part of that total refused because the session was shutting down rather than because the queue was full — a different problem with a different answer, which is why it is counted separately as well as inside the total. `write_queue_deferred` counts acked writes a clean shutdown handed to the NEXT server as durable intents — neither applied nor failed nor lost; their receipts say `intent_durable`. `write_queue_replayed` counts a previous server's durable intents this one applied at startup; they are not summed into `write_queue_applied`, which counts only this server's own accepted writes. `write_queue_replay_owed` is the other half of that pair and it is a debt, not a total: durable intents this server found owed and has not yet applied. A non-zero value that is not going down means the replay has not been able to run — most often because the embedder was not answering when this server started, in which case nothing was discarded and the next start tries again.

When the server was started with `serve --ledger`, the payload also carries `ledger_path`, `ledger_written_lines`, `ledger_dropped_lines`, `ledger_dropped_channel_full`, `ledger_dropped_write_failed`, and `ledger_queued_lines`. The dropped total is the one to read first: the call ledger drops lines rather than delay a tool call, so a non-zero value means any count taken from the ledger file is a lower bound. The two keys beside it say which kind of drop it was — `channel_full` is backpressure (the writer fell behind, so the filesystem is slow), `write_failed` is everything else (a batch whose write or open failed, a batch abandoned at shutdown, or an append after shutdown, so the path is wrong) — and they sum to the total. `ledger_queued_lines` is the writer's queue depth: lines accepted but not yet on disk. Read it when the drop counters are all zero but the file is not growing — on a path whose `open` blocks (a reader-less FIFO, a hung mount) the writer parks before its first write, so `written` and both drop counters stay at zero until the queue fills, and only this key distinguishes a parked writer from an idle server. Without `--ledger` all six keys are absent. The write queue keys above have no such switch, because there is no mode in which writes bypass the queue.

## How the server introduces itself

When your client connects, the server names the session and tells the model how to use it. For a session called `demo`, the instructions read:

```text
Lambo agentic graph memory for session 'demo'. Call lambo_recall before acting on a
task to load relevant prior memory, lambo_derive and lambo_record_action to write what
you learned and did, lambo_reserve before editing a shared concept, and lambo_inspect /
lambo_saints / lambo_stats to look around. Every tool takes your agent_id: it is
caller-asserted and unverified, so send one stable id of your own — work is recorded under
it, soft locks are held under it, distinct ids get distinct locks, and callers sharing an
id share locks. Never send a timestamp: the server stamps them. Ordering is yours to
manage, and writes are applied in the BACKGROUND: lambo_derive and lambo_record_action
return once your input is validated and ordered, and their ack carries a receipt id.
Their outcome arrives on your next tool response. If you need a write visible to the very
next read, call lambo_stats with that receipt and a wait_ms first; otherwise carry on —
writes you send one after another are applied in that order (two you fire at once have no
order to keep).
```

"Model-driven" means the model chose the arguments and issued the tool calls itself, rather than the calls being scripted at the JSON-RPC layer. Cursor needs `cursor-agent mcp enable <name>` before it will list tools, and in non-interactive `-p` mode `--approve-mcps` approves loading the server but not the individual tool calls, which are then auto-rejected with `User rejected MCP: lambo-lambo_derive`. Claude Code registers the server with `claude mcp add` and reports health through `claude mcp list`.
</Note>

## Claude Code against the managed CockroachDB server

The row above is about driving *Lambo's* server. Separately, Claude Code drove the **CockroachDB Cloud managed MCP server** model-first, reading back the graph Lambo had written. That is the read-only half of the deployment model: the writer is `lambo serve`, and a managed MCP server inspects the durable store without ever writing to it.

Scoped to a single session, the canonization history comes back as the durable record of what the demo narrates:

| node_id | from_status | to_status | blast_radius | occurred_at |
|---|---|---|---|---|
| 724c92b9… | None | Candidate | null | 14:50:08.306429Z |
| 3e3a6984… | None | Candidate | null | 14:50:08.306429Z |
| 724c92b9… | Candidate | Venerable | null | 14:50:08.992263Z |
| 724c92b9… | Venerable | **Canonical** | **9** | 14:50:09.600577Z |
| 1848c6e5… | None | Candidate | null | 14:50:10.103585Z |

Node `724c92b9` is `user schema`. It walks Candidate, then Venerable, then Canonical across 1.29 seconds, and `blast_radius` is null on the earlier hops and 9 on the promotion, because only the promotion gate measures it. That 9 is the same blast radius the [demo](/lambo/demo/) prints in its final recall block — the number the demo narrates and the number written to CockroachDB are the same number, checked from opposite ends.

Three independent MCP clients have now produced this table from the managed server: OMP, Claude Code, and the Cursor Agent CLI. Their captures agree on every field — different clients, different models, one durable record.

Full transcripts for every run live in [`evidence/`](https://github.com/nrynss/lambo/tree/main/evidence) in the repository: `mcp-client-stdio/` for the Claude Code handshake and the seven-tool stdio capture, `mcp-client-interop/` for the Cursor runs and the managed-server capture above, and `managed-mcp-canonization-events.md` for the OMP capture.

## Limits

Lambo enforces these when the call runs. The published tool schemas do not carry the maxima, so your client will not reject an out-of-range value before sending it. Expect to learn about an out-of-range value from the error rather than from your client.

| Limit | Value |
|---|---|
| Any single string | 16 KB |
| `top_k` | 100 |
| `traversal_depth` and inspect `depth` | 5 |
| `max_tokens` | 100,000 |
| Concepts per `lambo_derive` | 64 |
| Targets per `lambo_record_action`, combined | 64 |
| Reservation TTL | 3600 seconds |
| Neighbours rendered by `lambo_inspect` | 200 |
| Candidates listed for an ambiguous focus | 10 |
| `wait_ms` on `lambo_stats` | 4000 milliseconds |
| Write receipts kept | 300 seconds, or 4096 receipts, whichever binds first |

Every limit above is a maximum. `top_k`, `max_tokens`, and `ttl_seconds` also have a minimum of `1`, so `0` is refused. `wait_ms` is the one limit that **clamps rather than refuses**: a larger value waits the maximum instead of erroring, because a client asking to wait longer than Lambo will wait is asking for something harmless.

<Warning>
The published schema for `top_k` states a minimum of `0`, which the runtime does not accept. If you generate a client from the schema, do not let it send `top_k: 0`. It comes back as `top_k must be in 1..=100`.
</Warning>

`lambo_inspect` renders at most 200 neighbours in total across every hop, not 200 per hop.

See [Command line](/lambo/cli/) for the same operations from the terminal, and [Library API](/lambo/api/) for the underlying Rust library.
