Write and recall memory in a local SQLite session, then connect agents to the same session over MCP.

## The model

At most one writer holds the session lease at a time. A running `lambo serve` holds it for its attached session. A one-shot CLI write takes the lease for the duration of the command. Separate readers query the store without acquiring it.

The writer applies changes to its in-memory graph and flushes the write-behind log to the store in batches. A separate reader sees changes after they reach the store. Call `lambo_stats` on the writer to check flush lag.

Canonization runs in the background. Lambo promotes concepts when they meet the promotion policy’s evidence requirements.

A store with vector search and a semantic embedder supports recall by meaning. See [What recall searches](#what-recall-searches).

Lambo validates text before writing. It refuses control characters other than tab and newline and rejects certain invisible formatting characters, including bidirectional overrides and zero-width spaces. See [What Lambo accepts in text](/lambo/cli/#what-lambo-accepts-in-text).

See [Formal verification with Lean](/lambo/formal-verification/) to check which behaviors the models cover.

## A walkthrough you can run

Use SQLite and the fixture embedder to run the walkthrough locally without an external service. If you build from source with default features, add `--features store-sqlite`.

<Steps>
  <Step title="Configure the store and embedder">
    ```toml lambo.toml
    [store]
    kind = "sqlite"
    path = "./lambo.db"

    [embedder]
    kind = "fixture"
    dim = 1024
    ```
  </Step>
  <Step title="Provision the schema">
    ```bash
    lambo --config lambo.toml provision
    ```
    ```
    sqlite schema provisioned (init_schema, idempotent)
    ```
  </Step>
  <Step title="Write a concept and record an action">
    ```bash
    lambo --config lambo.toml derive --session demo --agent agent-a \
      --content "user schema" --kind entity \
      --concept "auth middleware:entity" \
      --concept "must stay backward compatible:constraint" \
      --parent-of "auth middleware:user schema"

    lambo --config lambo.toml record-action --session demo --agent agent-a \
      --action "created migrations/003.sql" \
      --produces "migrations/003.sql" \
      --depends-on "user schema"
    ```
  </Step>
  <Step title="Read the session">
    ```bash
    lambo --config lambo.toml recall --session demo --query "update user schema"
    lambo --config lambo.toml inspect --session demo --focus "user schema"
    lambo --config lambo.toml stats --session demo
    ```
  </Step>
</Steps>

## Drive the same session over MCP

For stdio, configure your MCP client to launch `lambo serve` for the `demo` session. See [Connect an MCP client](/lambo/installation/#connect-an-mcp-client) to register the command.

For HTTP, start the writer in a terminal.

```bash
lambo --config lambo.toml serve --session demo --agent agent-a --transport http
```

Point your MCP client at `http://127.0.0.1:7700/mcp`.

To watch the wire yourself, pipe JSON-RPC frames into the server, one per line. This handshake, tool listing, and single call is what a client does for you.

```bash
{
  echo '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-11-25","capabilities":{},"clientInfo":{"name":"probe","version":"0.1.0"}}}'
  echo '{"jsonrpc":"2.0","method":"notifications/initialized"}'
  sleep 1
  echo '{"jsonrpc":"2.0","id":2,"method":"tools/list","params":{}}'
  sleep 1
  echo '{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"lambo_derive","arguments":{"agent_id":"agent-a","concepts":[{"content":"stdio wire check","concept_type":"entity"}]}}}'
  sleep 1
} | lambo --config lambo.toml serve --session wire-demo --agent agent-a
```

The `initialize` reply includes the server instructions. The `tools/list` reply includes the available tools and their schemas. A successful `lambo_derive` acknowledgment includes a receipt in `result.structuredContent`. The example value below represents that part of the reply.

```json
{
  "summary": "accepted 1 concept(s) for background write; validated and ordered, not yet applied",
  "receipt": "<receipt-id>",
  "receipt_state": "pending",
  "agent_id": "agent-a",
  "warnings": []
}
```

Pass the returned receipt and `wait_ms` to `lambo_stats`. Wait for an `applied` or `applied_after_restart` state before you depend on the new concept. See [MCP write receipts](/lambo/mcp/#lambo_stats) to interpret the receipt state.

Stop a terminal server with `Ctrl-C`, or let your stdio client close the connection. On clean shutdown, Lambo attempts a final flush and releases the lease. A later writer can replay write intents that reached the persistent store.

<Warning>
A failed final flush or a forced stop can lose changes that exist only in the writer process. If you receive `close_unflushed`, check the receipt or recall after restart before resubmitting the write.
</Warning>

To watch the session in a browser while the writer runs, add a read-only `lambo serve-web` window on the same store:

```bash
lambo --config lambo.toml serve-web --session demo
```

It serves on port `7710` (loopback, unauthenticated by default) and only reads. It shows live recall, the canonization feed, and durable counts. It never contends for the writer lease. See [Command line](/lambo/cli/) for its flags.

## What recall searches

Recall gathers candidates from keywords, recent interactions, and vector similarity. Vector similarity requires a store with vector search and an available query vector. Lambo then expands through graph edges from those candidates.

| Store | Keyword | Vector | Graph expansion |
|---|---|---|---|
| SQLite | Yes | Yes | Yes |
| PostgreSQL (`pgvector`) | Yes | Yes | Yes |
| CockroachDB | Yes | Yes | Yes |
| In-memory | Yes | No | Yes |

With default hybrid matching and a vector-capable store, Lambo embeds new text concepts written through `derive` and `record-action`. A semantic embedder can help recall concepts whose text shares few or no words with the query.

SQLite uses an exact vector scan. A writer scans its in-memory vectors, which include changes it has applied and has yet to flush. A separate `lambo recall` or `lambo serve-web` process scans the database and sees the vectors that have reached the store.

The fixture embedder lets you exercise vector writes and lookups offline. For semantic recall, configure `kind = "candle"` in the Metal build for Apple silicon or `kind = "bge_m3"` with a local llama.cpp server. The walkthrough has stamped `demo` with the fixture embedding contract, so a writer using the new embedder cannot attach to it directly. To keep its concepts, stop the writer, back up the store, and migrate the session at the same vector width. See [Re-embed stored concepts](/cli#re-embed-stored-concepts) for the procedure. To start without those concepts, use a new session name with the new embedder.

For an example with SQLite and BGE-M3, refer to the [recorded semantic recall run](https://github.com/nrynss/lambo/tree/main/evidence/mooshik-f-sqlite-bge).

`derive` embeds the concept together with the originating call text. `recall` embeds the query as you enter it. The fixture embedder can give those inputs different vectors even when the query matches the concept text.

See [Troubleshoot missing memory](/lambo/troubleshoot-missing-memory/) to check the session, write receipt, and search results when a concept is missing.

## Readers and the writer

While a `serve` process owns a session, the command line read verbs still work against it, because they go to the store rather than to the writer.

What they cannot see is the writer's own state. A reader reports the counts and says which figures are writer-only.

```
session 'demo' (reader snapshot)
nodes=7 edges=12 concepts=5 canonical=0
epoch=0
flush_lag=n/a log_depth=n/a daemon_cycles=n/a canonization_cycles=n/a
note: flush_lag / log_depth / daemon_cycles / canonization_cycles are writer-only; this is a reader process
```

For flush lag and write-log depth, ask the writer through the `lambo_stats` tool.

## One writer, enforced across processes

A second **command line write** on the same session is refused while a `serve` holds the lease. The refusal names the holder, so you know which process to stop.

A second `serve` is different, and usually starts: over stdio it connects to the holder and forwards your calls, so the session still has exactly one writer while every client gets full access. Over HTTP, a second `serve` that pins only the held session is refused like a command line write; one that pins several sessions, or attaches sessions on demand, starts and answers `503` for the held session. See [MCP tools](/lambo/mcp/#more-than-one-client-on-one-machine) for both, and for when a second stdio `serve` is still refused.

```bash
$ lambo --config lambo.toml derive --session demo --agent agent-b --content "x" --kind entity
lambo derive: conflict: session demo is already held by another writer (agent-a@host#10492) — it acquired the single-writer lease 66s ago; the lease was last refreshed 6s ago and expires in 39s unless the holder refreshes it again. ...
$ echo $?
1
```

If a holder crashes, its lease expires and the next writer takes the session. The old holder is then fenced: its further writes are refused and its un-flushed tail is dropped rather than allowed to overwrite the new holder.

## Run a swarm

Connect each agent to the same session over MCP and give it a distinct `agent_id`. Agents write through `lambo_derive` or `lambo_record_action` and check their receipts through `lambo_stats`.

Use `lambo_reserve` on that writer to coordinate edits to shared concepts. See [MCP tools](/lambo/mcp/) to find the write, receipt, and reservation arguments.
