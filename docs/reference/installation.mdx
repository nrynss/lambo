Install the `lambo` binary to run commands in a terminal or serve sessions over MCP. Use `lambo.toml` to select a store and embedder.

Release binaries include the `ship` feature set. You can select the in-memory store, SQLite, CockroachDB, or PostgreSQL in the configuration file. To use the in-process Candle embedder, install the Metal build for Apple silicon.

See [Migration and memory repair](/migration) to upgrade a store with existing sessions or repair legacy names.

## Install the binary

Each release carries one `lambo` binary per platform plus a SHA-256 checksum file. Releases are published for Linux x86_64, Linux arm64 and macOS arm64, with the full `ship` adapter set compiled in. Apple silicon also gets a Metal build, `lambo-<version>-macos-arm64-metal`, which adds the in-process candle embedder running on the GPU (`[embedder] kind = "candle"`, `device = "metal"`). The stock binaries do not carry candle.

<Steps>
  <Step title="Run the install script">
    ```bash
    curl -fsSL https://github.com/nrynss/lambo/releases/latest/download/install.sh | sh
    ```
    The script detects your OS and architecture, downloads the matching binary, verifies its SHA-256 against the published checksum, and installs it to `~/.local/bin`.
  </Step>
  <Step title="Confirm the install">
    ```bash
    lambo --version
    ```
  </Step>
</Steps>

Set `LAMBO_VERSION` to pin the release. To choose another install directory, set `LAMBO_INSTALL_DIR` to a directory you can write to.

```bash
curl -fsSLo install.sh https://github.com/nrynss/lambo/releases/download/v0.15.0/install.sh
LAMBO_VERSION=0.15.0 LAMBO_INSTALL_DIR="$HOME/bin" sh install.sh
```

To install the Metal build on Apple silicon, set `LAMBO_FLAVOR=metal` on `sh`, the command that reads it. The script verifies its checksum the same way, and refuses `metal` on any other platform.

```bash
curl -fsSL https://github.com/nrynss/lambo/releases/latest/download/install.sh | LAMBO_FLAVOR=metal sh
```

To pin the Metal build to a specific version, download that release's script and run it pinned:

```bash
curl -fsSLo install.sh https://github.com/nrynss/lambo/releases/download/v0.15.0/install.sh
LAMBO_VERSION=0.15.0 LAMBO_FLAVOR=metal sh install.sh
```

Set `LAMBO_DRY_RUN=1` the same way to print the asset and URLs the script would fetch without downloading anything.

Prebuilt binaries are published for Linux and macOS; Windows support is blocked by the Unix-socket session endpoint ([#39](https://github.com/nrynss/lambo/issues/39)). An older `lambo-0.2.2-windows-x86_64.exe` asset remains on the [releases page](https://github.com/nrynss/lambo/releases).

## Write a lambo.toml

Configure a local SQLite file and the fixture embedder to run Lambo without an external service.

```toml lambo.toml
[store]
kind = "sqlite"
path = "./lambo.db"

[embedder]
kind = "fixture"
dim = 1024
```

Create the SQLite schema with `lambo --config lambo.toml provision`. SQLite stores the session on disk so you can read it from another process or after a restart.

The in-memory store belongs to a single process. Clients that connect to the same server can share it until that process exits. Use SQLite, CockroachDB, or PostgreSQL to share the store across separate Lambo processes.

See [Environment variables](/config#environment-variables) to find the configuration keys you can override.

If you select an adapter with a backing service, make that service available before you start Lambo. For example, `bge_m3` needs `llama-server`, and PostgreSQL needs the `pgvector` extension.

## Run it the first time

Write and recall a concept before you connect a client to the session.

<Steps>
  <Step title="Write a concept">
    ```bash
    lambo --config lambo.toml derive --session demo --agent agent-a \
      --content "user schema" --kind entity
    ```
  </Step>
  <Step title="Recall the concept">
    ```bash
    lambo --config lambo.toml recall --session demo --query "user schema"
    ```

    The output includes `user schema` and its concept type, `Entity`.
  </Step>
</Steps>

See [End to end](/end-to-end) to connect agents to an existing session and check write receipts.

## Connect an MCP client

See [Choose an MCP transport](/mcp-transports) to compare stdio and HTTP or move an existing session to a shared writer.

Most MCP clients, such as Claude Code and Cursor, read an `mcpServers` configuration. Add Lambo as a server and let the client start it over stdio. Point `command` at your `lambo` binary and pass the `serve` arguments.

```json
{
  "mcpServers": {
    "lambo": {
      "command": "/path/to/lambo",
      "args": [
        "--config", "/path/to/lambo.toml",
        "serve",
        "--session", "demo",
        "--agent", "agent-a",
        "--transport", "stdio"
      ]
    }
  }
}
```

With this configuration, your client starts `lambo serve` and connects over stdio. Set `store.path` to the absolute path of the database you provisioned so the client opens it from any working directory.

Real clients drive this, not only unit tests. Claude Code and the Cursor Agent CLI each completed the handshake and tool discovery over stdio (listing all seven tools on the initial capture, before `lambo_stale` and `lambo_derive_image` were added). OMP, the Oh My Pi harness, is an MCP client out of the box. Two models drove the tools autonomously in those captures: DeepSeek Flash under OMP called derive, recall, and stats against a live CockroachDB session, and Cursor's model ran derive, record_action, recall, and stats in sequence. Pi needs its MCP adapter installed first, after which it drives the full MCP surface.

For HTTP, start the server in a terminal.

```bash
lambo --config lambo.toml serve --session demo --agent agent-a --transport http
```

Configure your MCP client to connect to `http://127.0.0.1:7700/mcp`.

On an Apple silicon Mac, [macOS multi-session setup](/macos) runs that HTTP server under launchd with one session per repository and wires Claude Code, Cursor and Codex to it.

<Warning>
HTTP clients can write to the sessions they can access. Loopback accepts connections without authentication by default. For a non-loopback bind, configure `--auth-token`, `LAMBO_AUTH_TOKEN`, or `[[serve.credential]]` and send the token in the `Authorization` header. See [HTTP transport](/config#http-transport) to configure the listener.
</Warning>

## Set up real embeddings

On Apple silicon with the Metal build (`LAMBO_FLAVOR=metal`), run BGE-M3 in-process on the GPU with no external server:

```toml
[embedder]
kind = "candle"
device = "metal"
dim = 1024
```

Alternatively (or on Linux), run a local `llama-server` with an embedding model and point Lambo at it.

```bash
llama-server -m path/to/bge-m3.gguf --embedding --port 8080 \
  -c 8192 --batch-size 8192 --ubatch-size 8192
```

The batch flags matter: llama-server embeds an input in one batch, and at its default 512-token physical batch (`--ubatch-size`) it answers HTTP 500 for a longer input while `/health` still passes. From a checkout, `scripts/run-llama-embed.sh` starts the same server on the file `scripts/fetch-bge-m3.sh` downloads, with these flags.

Then set the embedder in `lambo.toml`.

```toml
[embedder]
kind = "bge_m3"
dim = 1024
url = "http://127.0.0.1:8080"
```

<Warning>
See [Re-embed stored concepts](/cli#re-embed-stored-concepts) to change the embedder for an existing session. If the embedder outputs changed under the same contract, see [Repairing a canary drift](/cli#repairing-a-canary-drift).
</Warning>

## Set up durable storage

For a local file, set `kind = "sqlite"` and `path = "./lambo.db"`, then run `lambo --config lambo.toml provision`. For PostgreSQL with `pgvector`, set `kind = "postgres"` and export `LAMBO_POSTGRES_DSN`, then run `lambo --config lambo.toml provision`. For CockroachDB, apply the schema with `scripts/provision.sh` (or `lambo --config lambo.toml provision` from a checkout), select `kind = "cockroach"`, and keep the connection string in the environment so the secret stays out of the file:

```toml
[store]
kind = "cockroach"
```

```bash
export LAMBO_COCKROACH_DSN="postgresql://USER@HOST:26257/lambo?sslmode=verify-full"
```

See [Configuration](/config) for all store keys, PostgreSQL/pgvector setup, and provisioning details.

## Build from source

You do not need this to run Lambo. Build from source when you want an unreleased change, a smaller binary, or to work on Lambo itself. You need a stable Rust toolchain from [rustup.rs](https://rustup.rs).

```bash
git clone https://github.com/nrynss/lambo.git
cd lambo
cargo build --release --features ship
# Apple silicon, with the Metal candle embedder:
cargo build --release --features ship,embed-candle-metal
```

Cargo writes the binary to `target/release/lambo`. The stock release binaries are built with `--features ship`, so the first command matches them. The Metal release asset is built with `--features ship,embed-candle-metal`, so the second matches that one. You can also install straight from git, which compiles the default branch and may be newer than the latest tag. Without `--features`, that builds the crate's default features (the `memory` store and the `fixture` and `bge_m3` embedders), so add `--features ship` for the full set:

```bash
cargo install --git https://github.com/nrynss/lambo.git --features ship
```

Cargo features select which adapters are compiled in. List fewer to get a smaller binary.

| Feature | What it adds |
|---|---|
| `store-memory` | In-memory store. This is the default and needs no external service. |
| `store-sqlite` | SQLite store, backed by a local file. |
| `store-cockroach` | CockroachDB store, for a hosted cluster. |
| `store-postgres` | PostgreSQL store with pgvector (`kind = "postgres"`). |
| `embed-fixture` | Deterministic fixture embedder for tests and quick starts. |
| `embed-bge` | BGE-M3 embeddings served by `llama-server`. |
| `embed-gemini` | Vertex AI Gemini embeddings (`gemini-embedding-001`), authenticated with a service account. |
| `embed-eg2` | EmbeddingGemma 2 text and image embeddings served by `llama-server` b11452 or later (`kind = "embeddinggemma2"`). Builds on `embed-bge`. |
| `embed-elastic` | Embeddings through the Elasticsearch Inference API (`kind = "elastic"`): `POST /_inference/text_embedding/<id>` on a cluster you name, with an optional API key. Builds on `embed-bge`. Needs a reachable Elasticsearch cluster at runtime. |
| `embed-candle` | In-process BGE-M3 through candle (`kind = "candle"`), CPU backend only. Builds anywhere. |
| `embed-candle-metal` | `embed-candle` plus the Metal GPU backend. Apple silicon only. This is what the Metal release asset adds to `ship`. |
| `embed-candle-accelerate` | `embed-candle` plus Apple's Accelerate framework for the CPU backend. macOS only. |
| `embed-candle-cuda` | `embed-candle` plus the CUDA GPU backend. Needs a CUDA toolkit at build time and an NVIDIA GPU at runtime. The backend's `cudarc` (0.19.10) knows CUDA toolkits up to 13.4. On a newer 13.x toolkit the build stops with `Unsupported cuda toolkit version`; set `CUDARC_CUDA_VERSION=13040` for the build to use the 13.4 bindings, as the project's CUDA rig does to build and run on CUDA 13.5. If nvcc rejects the system GCC as too new (`Failed to preprocess host compiler properties`), set `NVCC_CCBIN=clang`. |
| `embed-bedrock` | Reserved for Amazon Titan embeddings through Bedrock. Not implemented, so it fails at startup if selected. |
| `recall-elastic` | Optional Elasticsearch recall tier, selected by a top-level `[recall]` section (`kind = "elastic"`). The index serves recall's vector leg; the store stays the source of truth. Needs a reachable Elasticsearch cluster at runtime. |

The `ship` feature turns on every store and embedder above except `embed-bedrock` and the `embed-candle` family, plus `recall-elastic`. Choosing features only changes what the binary *can* do. Which store and embedder it *does* use is still a `lambo.toml` decision.
