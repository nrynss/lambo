Lambo reads a `lambo.toml` file. It looks for the file in this order: the `--config` path, then the `LAMBO_CONFIG` environment variable, then `./lambo.toml`. An environment variable always wins over the file for any key it sets.

## What lambo.toml contains

The file has `[store]`, `[embedder]` and `[daemon]` sections, an optional `[serve]` section for [multi-session serving](#multi-session-serving), an optional `[web]` section for [the read-only window's views](#read-only-window-views), an optional `[fusion]` section for [recall fusion](#recall-fusion), an optional `[selection]` section for [redundancy-aware selection](#redundancy-aware-selection), plus a small number of top-level process settings. It chooses which compiled backends this process runs, the cadence the background work runs at, and the canonization policy the serving verbs run them under.

```toml
# Top-level keys must come BEFORE the first [table] header, or TOML scopes them
# into that table and the unknown-key check refuses the file.
promotion_policy = "Solo"   # optional; the default remains Swarm

[store]
kind = "sqlite"
path = "./lambo.db"

[embedder]
kind = "bge_m3"
dim = 1024
url = "http://127.0.0.1:8080"
```

<Warning>
Unknown keys are refused, so a typo fails at startup instead of silently falling back to a default. A misspelled `knd`, a misspelled `[embeder]` section, and a key that belongs to the library rather than the file all stop the process before it attaches a session.
</Warning>

Recall defaults, flush timing, canonization cadence and limits, and scoring weights are not `lambo.toml` keys. They are library settings you pass when you build a `Memory` in Rust, so putting one in the file stops the process rather than tuning anything. The canonization gate thresholds are not settings at all: they are compiled into Lambo. Six settings are exceptions, and none of them is a threshold: `promotion_policy` and `canonization_supersede` below, and the four cadence keys in [Daemon cadence](#daemon-cadence). `promotion_policy` is a selector — it sets no number. But do not read that as "the numbers stay the same": `Solo` replaces Stage 1's floors with a score and adds a score band to the later hops, and the store-evidence gates still decide Venerable and Canonical. See [Library API](/api) for what each policy actually measures. `[fusion]` is one more: it chooses how recall combines its legs, and its numbers are the fusion's own, not canonization's. See [Recall fusion](#recall-fusion). `[selection]` is another, a switch with no number of its own: see [Redundancy-aware selection](#redundancy-aware-selection).

```
$ lambo --config lambo.toml provision
lambo provision: failed to resolve store: config: lambo.toml: unknown field `default_top_k`, expected one of `store`, `embedder`, `daemon`, `promotion_policy`, `serve` (line 1, column 1)
```

The refusal names the line and column but never quotes the line itself, so a misspelled key next to a secret (a DSN with a password in it, say) does not print the secret into your logs. A value under the wrong key is not quoted back either: an unknown `[store] kind` or `[embedder] kind` lists the accepted kinds with `(value not shown)`, a wrong-typed value reads `invalid type: string (value not shown), expected ...` (numbers are hidden the same way), and an unknown key is named only while it looks like a key (letters, digits, `_` and `-`, up to 40 characters), so a DSN pasted as a quoted key is not printed. An unknown `promotion_policy` is quoted only when it is a short word, so a typo stays visible.

## Promotion policy

`promotion_policy` is an optional selector for how canonization promotes. Omit it to preserve the existing `Swarm` behavior. Set it to `Solo` for a single writer whose recurring evidence should be eligible for promotion.

<Warning>
It is a **top-level** key, so it has to appear before the first `[store]` or `[embedder]` header. Put it after one and TOML scopes it into *that* table, so the refusal names that table's keys and never mentions the placement. With the layout above, moving it below `[store]` gives:

```
unknown field `promotion_policy`, expected one of `kind`, `dsn`, `path`, `vector_dim`
```

A store error, about a key that was spelled correctly. Below `[embedder]` you get the same shape with the embedder's much longer key list instead. This is the mistake worth knowing about, because nothing in either message points at the line's position.
</Warning>

Accepted values are `Swarm` and `Solo`, matched after trimming and without regard to case, so `solo` and `Solo` are the same thing — the same leniency `store.kind` and `embedder.kind` already have. Anything else fails at startup and names both what you wrote and the valid set. There is no silent fallback to the default.

There is no `lambo serve --promotion-policy` flag. Set it in the file or in `LAMBO_PROMOTION_POLICY`; no `serve` flag in Lambo duplicates a `lambo.toml` key, and every backend and policy selector is chosen the same way.

`Solo` does not lower the Canonical bar, and since 0.6.0 it cannot skip it either. A concept becomes a Solo Candidate by a recurrence score over its own supporting evidence (the days it was derived or depended on; edits to it do not count) rather than by `Swarm`'s survival and dependence floors, so under `Solo` you do not need to lower [`[daemon] gc_interval`](#daemon-cadence) to get Candidates. Every later hop needs the score's band **and** the store evidence `Swarm` needs: dependents from at least three other interactions with enough spread for Venerable, then more than five dependents and a clear re-promotion cooldown for Canonical. On `lambo serve-web`'s inspect panel the four-gate breakdown is still replaced by a line naming the policy, with the re-promotion cooldown shown under both policies; the panel's `admission` explanation lists every gate the live policy reads, with one reason per gate that fails. See [Library API](/api) for the score itself.

<Warning>
`lambo serve-web` resolves its **own** `lambo.toml` and its own environment, and nothing carries the writing process's policy to it. So what the panel describes is the *reader's* resolution: start `serve-web` where it reads the same config as the `lambo serve` writing that session, or the page will explain a policy that is not the one promoting. A `lambo serve` under a systemd unit with `Environment=LAMBO_PROMOTION_POLICY=Solo`, opened with a `serve-web` run by hand in a shell that does not export it, is the shape of the mistake. `/api/inspect` names the resolution it used in `promotion_policy` — on the response and again on the gate block — so the mismatch is visible rather than silent.
</Warning>

`lambo demo` is out of scope, but it is not unaffected. It runs a scripted *swarm* demonstration on its own compiled-in config, so it ignores the **value**: `promotion_policy = "Solo"` changes nothing about what the demo does. It still validates it, because the file is parsed before any command decides what to keep from it — which is also why an unparseable policy stops even the four commands that never resolve an embedder (`provision`, `saints`, `inspect`, `stats`), unlike a degenerate `[daemon]` cadence.

```
$ LAMBO_PROMOTION_POLICY=Bogus lambo --config lambo.toml demo
lambo demo: failed to build backends: config: LAMBO_PROMOTION_POLICY: unknown promotion policy "Bogus" (expected Swarm | Solo)
```

[`[daemon]`](#daemon-cadence) is the same bargain with a narrower scope: the demo discards the cadence you set and still refuses a degenerate one, but only the commands that resolve an embedder refuse it at all.

## Supersession

`canonization_supersede` turns on evidence-driven supersession (0.6.0). It is a top-level boolean, like `promotion_policy` a selector rather than a threshold, and it defaults to `false`, so a file without it behaves exactly as before:

```toml
canonization_supersede = true   # optional; top-level, before the first [table]
```

With it on, each canonization cycle first demotes a Canonical concept to ordinary memory when a concept that contradicts it (written with `against`) has since earned its own structural support: dependents from at least three other interactions, newer than the Canonical concept's latest eligible evidence, with Stage 2's spread. A contradiction with no newer support never demotes anything, and the contradicting concept is not promoted by it: it climbs on its own evidence. The bar is deliberately uneven: the contradicting side must clear Stage 2 again with newer support, while one new piece of support for the Canonical concept, from anyone but the agent that declared the contradiction, puts it ahead again.

The demoted concept enters the usual re-promotion cooldown, and a concept inside its cooldown cannot supersede another. With the setting on, Stage 3 also **holds** at Venerable any concept a contradicting concept would supersede at once: a superseded one climbing back, and also one that was never Canonical, since promoting it would only demote it on the next cycle. It waits there until it earns support newer than the contradicting side's. When two concepts contradict each other and each qualifies against the other, only the one with the newest counted support may supersede or hold the other, so they cannot hold each other forever. `lambo inspect` shows it (`held: contradicted by <id> with newer evidence`) and names a concept's latest demotion and why; recall marks a superseded concept with a `⤓ Superseded at ... by ...` line. No new numbers: it reuses Stage 2's bars, the age floor and the cooldown. A value that is not `true` or `false` stops the process at startup, as does the key under a table.

<Warning>
**Give agents distinct ids before turning this on.** Support written by the agent that declared a contradiction never counts for the concept it contradicted: a writer cannot defend a belief against its own contradiction. So with a single writer, or several agents sharing one `agent_id`, nothing that writer adds for the contradicted concept can ever release it from a contradiction it declared; only another agent's support can. Who wrote a piece of support is decided by the agent acting when it was written; when two agents acted at the same instant and it cannot be told whose it is, that pair is not probed at all, so an ambiguity never demotes anything.
</Warning>

## Recall fusion

`[fusion]` (#173) chooses how recall combines its three query legs (keyword, vector, and the concepts of the three most recent interactions) into a hit's query relevance, the `w_query` half of its score. It is optional, and a file without it ranks exactly as before.

```toml
[fusion]
kind = "rrf"   # optional; the default is "max"
k = 3.0        # optional; RRF only
```

| Key | Type | Default | Notes |
|---|---|---|---|
| `kind` | string | `"max"` | `"max"` takes the highest raw leg score. `"rrf"` is reciprocal rank fusion. |
| `k` | number | `3.0` | RRF's constant. Larger values flatten the gap between ranks. |
| `keyword_weight` | number | `1.0` | The keyword leg's RRF weight. |
| `vector_weight` | number | `1.0` | The vector leg's RRF weight. |
| `recent_weight` | number | `0.3` | The recent leg's RRF weight. |

**`max`.** The legs score on different scales: keyword matching is BM25, which is unbounded and routinely above 1; vector similarity is a cosine, at most 1; a recent concept scores a flat 0.35 (0.63 under the calibrated EmbeddingGemma 2 contract, see `[embedder] calibration`). The highest of the three wins, so in practice a keyword match outranks any vector match.

**`rrf`.** Each leg ranks its own members (score descending, the usual tie-break by canonical key), the recent leg by recency (the newest interaction's concepts share rank 1). A hit's relevance is `Σ weight / (k + rank)` over the legs it is in, divided by the most the legs that ran could give (rank 1 in each; the keyword leg counts whenever the query has text, even when nothing matched), so it lies between 0 and 1, and on a text query a recent concept alone does not score as a perfect match. The recent leg's score is still recorded, but no longer ranks anything.

**Why `max` stays the default.** Measured on the evaluation set (`fixtures/eval/`) through the whole recall pipeline, `k` chosen on the `dev` split and `held_out` used only to confirm (`evidence/issue-173-fusion/`):

| | nDCG@10 dev | hit@1 dev | nDCG@10 held-out | hit@1 held-out |
|---|---|---|---|---|
| BGE-M3, `max` | 0.848 | 0.728 | 0.865 | 0.785 |
| BGE-M3, `rrf`, k = 3 | 0.893 | 0.784 | 0.887 | 0.785 |
| EmbeddingGemma 2, `max` | 0.848 | 0.728 | 0.865 | 0.785 |
| EmbeddingGemma 2, `rrf`, k = 3 | 0.889 | 0.768 | 0.881 | 0.760 |

RRF ranks better overall, but not everywhere, and the gain is below the +0.05 nDCG@10 that #173 set as the bar for a new default. On the held-out split exact-identifier queries drop (nDCG@10 0.948 to 0.899 under BGE-M3, 0.881 under EmbeddingGemma 2) and contrast queries drop (0.897 to 0.859 and 0.872). Telling a query with no answer from one with an answer by its top score does not get consistently better or worse: the chance that an answerable query's top score beats a no-answer query's falls on `dev` (0.775 to 0.682 under BGE-M3) and rises on `held_out` (0.673 to 0.717). Neither kind separates them well enough to gate on. The literature's `k = 60` is much worse here (nDCG@10 0.698 on `dev`): it puts a leg's first and tenth hit within about 0.06 of each other, so the daemon's share of the score decides the order.

`k` and the weights must be finite and at least 0, and `"rrf"` needs at least one weight above 0; anything else, or an unknown key, stops the process at startup. With `serve --ledger`, every recall hit found by a query leg records its rank in each leg and both fused values (`fusion` on the hit), whichever kind ranked, so one can be compared against the other on live traffic.

## Redundancy-aware selection

`[selection]` (#181) decides whether recall skips a hit that repeats one it already took. A reader sees the first two or three hits, so two copies of one fact can take two of those slots: a semantic match writes its own node beside the one it matched, and a store written before embedding coverage can hold the same text twice (an `Entity` and an `Observation`). It is optional and off by default, and a file without it, or with it off, recalls exactly as before.

```toml
[selection]
skip_redundant = true    # optional; the default is false
similar_signals = false  # optional; the default is false
```

| Key | Type | Default | Notes |
|---|---|---|---|
| `skip_redundant` | boolean | `false` | Skip a member redundant with a hit already taken; the next distinct member fills its slot. On its own, only identical text counts as redundant. |
| `similar_signals` | boolean | `false` | Also count a `Semantic` edge, or vectors at or above the merge threshold, as redundant. Needs `skip_redundant = true`. |

**What counts as redundant**, checked cheapest first:

- the same text, once spacing, Unicode composition and invisible characters are set aside, whatever the two concept types (nothing else is erased, so a different case, identifier, number, path, punctuation or word order is different text: `src/Foo.rs` is not `src/foo.rs`). This is the only signal by default.

With `similar_signals = true`, two more:

- a `Semantic` edge between the two;
- vectors at or above the session's merge threshold (`semantic_match_threshold`, or the calibrated or labelled-pairs threshold that replaces it, see `[embedder] calibration`), when both carry a vector. A concept without a vector is never judged by this one. `lambo recall`, `serve-web` and `lambo session verify` use the same threshold as a serve: with `[embedder] related_pairs`, the threshold a writer derived from that file and cached in the store (matched by the file's SHA-256); while no writer has measured the current file (or the canary is off, or the file cannot be read), the contract's calibrated threshold, or the configured one, as a writer falls back.

**Never redundant:** a pair one of which contradicts the other (`against`, in either direction), or one of which is suspected of replacing the other (#198, see `suspected_supersession_line`); two texts that differ in an identifier (a snake_case, CamelCase or all-caps word, a path, version or file name, or seven or more hex digits; case counts) or in a digit of any script, that negate a different number of times (`not`, `never`, `don't`, `avoid`, `unless`, `non-`, ...), where one has a word and the other its opposite (`enable` and `disable`, `safe` and `unsafe`), or whose shared words come in another order (`warn replaces verify` and `verify replaces warn`). **Never skipped:** a hit forced into the result (hot-list conditions, a contradicted Canonical or Venerable concept and its contradicting concept, a kept reservation holder), and a hit that carries a warning line of its own (a hot-list or contradiction line, a stale citation, a supersession or possibly-superseded line, a reservation), because the copy kept may not carry it. Canonical concepts still come first.

Only the first `min(20, 4 × top_k)` hits are checked, each against at most 20 hits already taken; past that, hits fill the remaining slots as before. A dependency question answered by graph traversal lists the anchor's dependents as before; the setting does not filter it. When nothing in that window is redundant, the result is byte-identical to the rule being off. `top_k` and `max_tokens` then apply as usual.

**What the reader sees.** The kept hit names what was skipped in its label, after its id: `(score 0.42, id 1a2b3c4d, also 5e6f7a8b)`, at most three ids and then `+N more`. Each id is an inspect focus. These items count against `max_tokens`, so under a tight budget a later hit can fall out of the rendered context. The skipped members, each with the signal that found it (`same_content`, `semantic_edge`, `cosine`), are `skipped_redundant` on the hit in `lambo_recall`'s `structuredContent`, the web portal's `/api/recall` and the `--ledger` recall line; that key is absent on every other hit. In a layered recall, what a merged layer copy skipped is `also_skipped_redundant` on the hit (each item names its `session`).

**Layered recall** applies each session's own setting inside that session's recall, where the concepts' edges are; across layers, the existing deduplication still keeps the nearest tier's copy, and the hits a merged copy's session skipped for it follow it (`also <id> in <session>`). `lambo session verify` replays the setting and counts a skipped member as deduplicated, not lost.

**Why it is off by default.** On the evaluation set under BGE-M3 (`evidence/issue-181/`), with copies and rewordings injected, identical-text skipping raised the distinct memories in a 500-token context at `top_k = 3` from 1.44 to 2.05 (dev) and 1.45 to 2.03 (held-out), and changed nothing without redundancy, with declared contradictions, or with related but different facts. Turn it on where duplicates are common.

**Why `similar_signals` is off by default.** Against identical-text skipping alone, the `Semantic`-edge and cosine signals added 3 answer facets over the 8 cells (split, `top_k`, budget) with injected copies, and lost 42 over the 8 cells with labelled related-but-different facts. Every wrong skip came from five such pairs that the write path had merged with a `Semantic` edge (two names swapped, a default moved, an exception inverted, a value given in words), which the text guard of the time did not see. The stricter guard now rejects all five on that set, and the signals then add nothing there, but they stay off until measured on real stores, where sibling concepts of one write sit closer than these did. Declaring a contradiction with `against` protects a pair mainly because the write path then refuses to merge it (no `Semantic` edge), not through recall's `Contradicts` veto, which then only stops the cosine signal. Turn it on only where near-copies are common and related facts are declared contradictory.

`skip_redundant` and `similar_signals` must be `true` or `false`, and `similar_signals = true` needs `skip_redundant = true`; anything else, or an unknown key, stops the process at startup. It is a table of its own, not a key under `[recall]`, which configures the recall tier.

## Store

`[store]` selects where the graph is persisted.

| Key | Type | Default | Notes |
|---|---|---|---|
| `kind` | string | `memory` | `memory`, `sqlite`, `cockroach`, or `postgres`. |
| `path` | string | none | The SQLite file, used when `kind` is `sqlite`. |
| `dsn` | string | none | The CockroachDB or PostgreSQL connection string, used when `kind` is `cockroach` or `postgres`. Prefer the environment variable so the secret stays out of the file. |
| `vector_dim` | integer | none | The vector width you assert for the store. SQLite reports it instead of echoing `[embedder] dim`, and `lambo provision` creates PostgreSQL's `vector(n)` column at it (else 1024). A command that resolves both the store and the embedder (every writer, `lambo serve` included) refuses to start when it differs from `[embedder] dim`, whatever the store kind; `lambo embed` and `lambo session verify` do not check it. See [Vector width](#vector-width). |

`kind` also accepts a few spellings: `mem` and `ram` for `memory`, `crdb` for `cockroach`, `pg` for `postgres`, and `sqlite3` for `sqlite`. `"postgres"` and `"pg"` are PostgreSQL, not CockroachDB.

The in-memory store is scoped to one process. Many agents can share it through a single `lambo serve`, because they all talk to that one process. Nothing outside that process can read it, and it does not survive a restart. Use `sqlite`, `cockroach`, or `postgres` when a separate command line process has to see the same session.

The kind you choose must be compiled into your binary. If it is not, Lambo fails at startup and names the feature to rebuild with. See [Installation](/installation).

**Where deduplication looks.** With hybrid matching, the writer that holds a session decides whether a new concept repeats an existing one. On `sqlite` it compares the new concept against its own in-memory graph. On `cockroach` and `postgres` it asks the database for the concepts already flushed and compares against its own in-memory copy of the ones it has not flushed yet, so a fact derived twice in quick succession merges even before the first copy is flushed, and the cost of a derive does not grow with the session. Comparing against every concept in memory instead took about 98 ms per new concept at 100,000 concepts of 1,024 dimensions; the unflushed part costs about 0.8 ms per new concept with 1,000 concepts unflushed, plus the database's indexed search. Recall on `cockroach` and `postgres` still ranks vectors in the database. The writer scores candidates by exact cosine similarity and the database by its own distance, so the two can disagree on a pair whose similarity sits right at `semantic_match_threshold`. On CockroachDB the approximate index can miss a flushed concept, which is then not merged.

**Merging and its guards.** A new concept merges into an existing one when the cosine similarity of their vectors is at least `semantic_match_threshold` (0.85), or the threshold that replaces it (see `[embedder] related_pairs` and `calibrated_merge_threshold`). On every store, two guards refuse a merge whatever the similarity (#193). First, the two texts must name the same identifiers: the same runs of digits and the same identifier-shaped tokens, in the same order (any token with a digit, `/` or `.`, such as `v0.5.0`, `src/mcp/server.rs` or `round3`), so `release v0.5.0 is current` and `release v0.6.0 is current` stay two facts. Second, a new concept never merges into a concept it names in `against`. A refused hit leaves the new concept fresh, with its vector, unless another hit at or above the threshold passes both guards. `lambo canon alias-preview --similar` applies these guards, among others, to its suggestions. The receipt counts each refused merge. {/* code: src/graph/canonical.rs same_identifiers is_identifier_token digit_runs, src/graph/hybrid.rs merge_guard */}

## Recall tier

`[recall]` adds an Elasticsearch index beside the store that serves the vector part of recall. It is optional, and it is not a store kind: the `[store]` you chose stays the source of truth, and leases, fencing, canonization and graph queries never touch Elasticsearch. Each flush the store commits is copied to the index, and recall asks the index for the nearest concepts instead of scanning vectors in the store.

```toml
[recall]
kind = "elastic"
url = "https://my-cluster.es.example.com"
api_key = { env = "LAMBO_ES_API_KEY" }
index_prefix = "lambo"
```

| Key | Type | Default | Notes |
|---|---|---|---|
| `kind` | string | none | `elastic`. Required. |
| `url` | string | none | The cluster's base URL, `http://` or `https://`. A URL that carries a user name, a password, a query string or a fragment is refused. With `api_key` set, the URL must be `https://`, or `http://` to a loopback host (`localhost`, `127.0.0.0/8`, `::1`), so the key never crosses the network in clear text; plain `http://` to any other host is refused at startup, naming the host and scheme. Redirects are not followed: a `3xx` answer is an error that does not show the redirect target. |
| `api_key` | table | none | `{ env = "NAME" }`: the environment variable that holds the API key, sent as `Authorization: ApiKey <key>` only over `https` or over plain `http` to a loopback host. A loopback `http` client with a key ignores the proxy environment. An error quotes Elasticsearch's `error.type` and `error.reason` with any run of 8 or more characters of the key replaced, as for a hosted embedder. The key itself is never accepted in the file. Omit it for a cluster with security off. |
| `index_prefix` | string | `lambo` | Lowercase letters, digits, `-`, `_` and `.`. Vectors go to `<prefix>-v-<hash>`, one index per embedding model, and a small `<prefix>-meta` index keeps one sync marker per session. Must not contain `-v-` or end in `-v`, so that `<prefix>-v-*` can never match another deployment's indices on a shared cluster. |
| `refresh` | string | `"false"` | When a write becomes searchable: `"false"` leaves it to the index refresh interval (1 second by default), `"wait_for"` waits on every write and is for tests. |
| `timeout_ms` | integer | `5000` | Per-request timeout for writes and searches. Must be greater than zero. Refreshes, deletes by query and counts, whose work grows with the session, get 300 seconds. |

`[recall]` is a top-level table, not part of `[store]`. It needs the `recall-elastic` feature; a binary built without it refuses the section and names the feature rather than ignoring it. Lambo creates each index with its mapping the first time it writes to it.

**Staleness.** A concept becomes searchable in the index up to one refresh interval after its flush, so the vector part of recall can miss a concept written in the last second or so. The keyword and recent parts of recall still find it. This is an accepted difference from a store that ranks vectors itself. Deduplication when a writer derives new concepts does not use the index: it compares against the writer's own in-memory graph, so a fact derived twice in quick succession still merges.

**Ranking.** Lambo creates each vector index with plain float HNSW (no quantization), asks it for 16 more neighbours than recall needs, and re-scores them with exact cosine from the stored vectors. Scores and order therefore match the store's exact scan for the concepts the index returns. The index only chooses which concepts are considered, and an approximate HNSW search can occasionally miss a near neighbour that an exact scan would find. This is the second accepted difference. Because every neighbour comes back with its stored vector, a query's response grows with the number of concepts asked for: at 1024 dimensions about 0.7 MB for 50, and at most about 20 MB at the largest limit (2048), where Lambo asks for no extra neighbours. Lambo downloads at most 32 MiB of any response from the cluster, error bodies included, or for a vector search what that many neighbours can take if it is more (32 bytes a dimension and 32 KiB a neighbour). A longer response is an error that quotes none of it, handled like any other failure of the index (see below).

**When the index is unavailable.** A failed copy never fails the flush, because the store already has the data. The session is marked stale, and until the index is repaired recall ranks vectors in the store instead (SQLite, PostgreSQL and CockroachDB do this themselves; the in-memory store has no vector search, so recall uses only its keyword and recent parts). A failed query does the same for that one recall, and after three failed or slow (over 5 seconds) queries in a row recall stops asking the index for 30 seconds before trying again. A flush waits at most 15 seconds for its copy. The writer holding the session repairs its index in the background when it next opens the session, after a later flush, and after a flush that changes the session's embedding contract, one repair at a time per session, and `lambo recall-index backfill` repairs it when no writer is running. Writes made without a session lease (seeding) are not copied: the next writer to open the session, or a backfill, copies them. See [Command line](/cli#rebuild-the-recall-index).

Erasing a session also removes it from the index, and reports success only once a search of the index finds nothing of the session. See [Command line](/cli#rebuild-the-recall-index).

### Running the live Elasticsearch tests

The adapter has manual integration checks against a disposable local cluster,
using synthetic data and the fixture embedder. They stay ignored in ordinary
test runs and are not added to CI. Start the approved single-node cluster:

```sh
docker run -d --name lambo-es-live -p 127.0.0.1:59200:9200 \
  -e discovery.type=single-node -e xpack.security.enabled=false \
  -e 'ES_JAVA_OPTS=-Xms512m -Xmx512m' \
  docker.elastic.co/elasticsearch/elasticsearch:8.15.3
```

`kind` also accepts `bge`, `bge-m3` and `openai` for `bge_m3`, `vertex` for `gemini`, `titan` for `bedrock`, `fake` for `fixture`, `embeddinggemma-2` and `eg2` for `embeddinggemma2`, and `elasticsearch` for `elastic`, in any letter case. An alias changes nothing but the spelling: the kind is reported and stamped under its canonical name, so `openai` is still `bge_m3` and `eg2` is still `embeddinggemma2`.

A store that persists vectors declares its own width, and Lambo refuses to start if `dim` disagrees with it.

While `lambo serve` sits idle, the operating system can compress or swap out model weights that nothing is touching, and the next call pays to bring them back. On Apple silicon the candle embedder's weights live in unified memory, so this is where it shows. Keep-warm embeds one short fixed probe on an interval and discards the vector. It writes nothing to the store, the graph or the call ledger, and it is not part of the embedding contract, so you can change it without re-embedding. The first touch comes one interval after startup, never during it.

### Google credentials

The `gemini` embedder and a Cloud SQL IAM login (`LAMBO_POSTGRES_IAM=1` on the `postgres` store) authenticate as one Google identity. The embedder's `gemini_credentials` key (or `LAMBO_GEMINI_CREDENTIALS`) names its file directly; otherwise both use the first of these that answers:

1. `GCP_LAMBO_CREDENTIALS`, the path of a service-account key or an authorized-user credentials file.
2. `GOOGLE_APPLICATION_CREDENTIALS`, the same.
3. The file `gcloud auth application-default login` writes: `$CLOUDSDK_CONFIG/application_default_credentials.json` when `CLOUDSDK_CONFIG` is set, otherwise `~/.config/gcloud/application_default_credentials.json` (`%APPDATA%\gcloud\application_default_credentials.json` on Windows).

An empty variable counts as unset. A variable naming a missing file is an error that names the path; it never falls through to the gcloud file. The gcloud file is used only if it exists and is a file, so after `gcloud auth application-default login` no variable is needed.

### Hosted endpoints

The `bge_m3` kind speaks the OpenAI embeddings API (`POST <url>/v1/embeddings`), so it also reaches a hosted OpenAI-compatible endpoint when you give it a token. Cloudflare Workers AI serves BGE-M3 at 1024 dimensions:

```toml
[embedder]
kind = "openai"   # the same adapter as bge_m3
dim = 1024
url = "https://api.cloudflare.com/client/v4/accounts/<account-id>/ai"
model = "@cf/baai/bge-m3"
api_key_env = "CLOUDFLARE_API_TOKEN"
```

`api_key_env` names a variable; the token itself never goes in `lambo.toml`. Lambo reads the variable when it resolves the embedder and sends `Authorization: Bearer <token>` with every embed request. Without `api_key_env` no `Authorization` header is sent.

- If the variable is unset or empty, startup fails and names the variable. Lambo never falls back to sending no token.
- The token is sent only over `https`, or over plain `http` to a loopback host (`localhost`, `127.0.0.0/8`, `::1`) such as a local server. Plain `http` to any other host is refused at startup, naming the host, so a token never crosses a network in clear text. Without `api_key_env`, `http` URLs work as before.
- The value must look like a variable name: upper case letters, digits and `_`, not starting with a digit, at most 64 bytes. A value that does not, or that looks like a token, is refused without being shown. So is an inline `api_key = "..."`.
- It may not name `LAMBO_AUTH_TOKEN` or any `[[serve.credential]]` `token_env`, from the file or from `LAMBO_EMBED_API_KEY_ENV`. Those variables hold `lambo serve`'s own credentials, and one variable may not hold both a serve credential and the embedder's token.
- It may not name a variable lambo reads its own credentials from either: `LAMBO_COCKROACH_DSN`, `LAMBO_POSTGRES_DSN`, `DATABASE_URL`, `GCP_LAMBO_CREDENTIALS`, `GOOGLE_APPLICATION_CREDENTIALS` or `LAMBO_GEMINI_CREDENTIALS`. The same rule applies to `[[serve.credential]] token_env`.
- Redirects are never followed. A `3xx` from the endpoint fails the write as a configuration error naming the status (not the redirect target): point `url` at the endpoint itself. A `url` with a query or fragment is refused, because the embeddings path is appended to it.
- Plain `http` to a loopback host ignores `HTTP_PROXY`, `HTTPS_PROXY` and `ALL_PROXY`, so a token meant for a local server is never handed to a proxy. `https` URLs still use them: a proxy only tunnels the TLS connection.
- When an error body from the endpoint is quoted into an error, any run of 8 or more consecutive characters of the token is replaced, whether raw, JSON-escaped or percent-encoded. Shorter fragments, case-changed copies and other encodings are not detected. Quoted bodies are cut at 8 KiB. Logs and errors show the URL as scheme, host, port and path only.
- A success response is read up to 64 bytes a dimension, at least 4 MiB. A longer one fails the write without being read further or quoted. One cut off mid-body (a reset, or a stall past the request timeout) is an outage, so the write keeps its durable intent.
- A `401` or `403` from the endpoint fails the write as a configuration error, the same as a wrong URL.

The same model behind a different server is a different embedding contract, because the two can differ numerically. Set `model` to the hosted id (as above) so a hosted session's contract differs from a local one, and start a fresh session or run `lambo re-embed` rather than mixing the two.

### EmbeddingGemma 2

`kind = "embeddinggemma2"` embeds text and images into one space with Google's EmbeddingGemma 2, served by llama.cpp's `llama-server`. It needs llama.cpp build b11452 or later; older builds refuse the model with `unknown model architecture: 'gemma-embedding2'`. Download the Q8_0 GGUF and its vision projector from `ggml-org/embeddinggemma-2-GGUF` and start the server like this:

```bash
llama-server --host 127.0.0.1 --port 8191 \
  -m embeddinggemma-2-Q8_0.gguf \
  --mmproj mmproj-embeddinggemma-2-Q8_0.gguf \
  --embeddings --pooling mean \
  --image-min-tokens 280 --image-max-tokens 280 \
  --ctx-size 8192 --batch-size 8192 --ubatch-size 8192
```

```toml
[embedder]
kind = "embeddinggemma2"
url = "http://127.0.0.1:8191"
dim = 768
```

- Lambo adds the model card's task prefixes itself: a stored concept is embedded as `title: none | text: ...`, a recall query as `task: search result | query: ...`, and an image with no prefix. A server, or a client computing vectors, that uses other prefixes is in a different space.
- `dim` can be `768`, `512`, `256` or `128`. Lambo takes the first `dim` of the 768 values and re-normalizes them.
- The session's contract records the weights and the prompt profile, for example `ggml-org/embeddinggemma-2-GGUF@bfcd2987/Q8_0;prompts=lambo-eg2-v2`, because `llama-server` ignores the model name in a request. Set `model` to the artifact your server actually runs. A different artifact or profile is a different contract: start a fresh session or run `lambo re-embed`.
- The profile also fixes the form an image is sent in. At a fixed budget llama.cpp still puts an image larger than about 768 px a side on a coarser patch grid than a smaller one, and resamples every image from whatever resolution it was given, so the same picture sent at 512 and at 1024 px embedded up to about 0.01 apart (cosine). Lambo therefore decodes every PNG, JPEG and WebP and sends it as a lossless PNG whose longer side is exactly 768 px: larger images are scaled down (Lanczos3), smaller ones scaled up (Catmull-Rom), aspect ratio kept. Measured on b11517 for pictures submitted at 128 to 3000 px: a flat image embeds bit-identically at every size; a patterned one does not, because a picture scaled to 768 px is not the same pixels as one drawn at 768 px. Renders at 768 px and above agree to a cosine of at least 0.9991 (checkerboard) and 0.9995 (smooth gradient); a 128 px checkerboard is 0.982 from the 768 px one, since enlarging cannot restore detail that was never sent. What Lambo stores about the image (its id, hash and type) describes the bytes you sent; only the request to the server carries the converted form. Images are decoded only up to 4096 px a side, two at a time.
- A client that computes image vectors itself is in the same space only if it sends the server the same canonical form: decode without applying EXIF orientation or colour profiles (a palette PNG becomes RGB or RGBA, a CMYK JPEG becomes RGB, alpha is kept straight, 16-bit samples are kept); resize in one step so the longer side `L` becomes 768 and the shorter side `s` becomes `max(1, floor((s * 768 + floor(L / 2)) / L))` (integer arithmetic, halves rounded up), with Lanczos3 when shrinking and Catmull-Rom when enlarging, on the stored channel values; skip the resize when `L` is already 768; encode as PNG with no ancillary chunks. The deflate settings do not matter, only the pixels. Lambo uses the Rust `image` crate 0.25 for this; another resampler gives close but not bit-identical pixels. If an update of that crate ever changes the canonical pixels for the same input, Lambo's tests fail and the change ships as a new profile name, never under `lambo-eg2-v2`.
- The profile fixes the image budget at 280 tokens. The two image flags set it, and the batch flags let a whole image fit: at the server's default ubatch of 512 the budget is silently cut to 256 tokens, a different space. The budget bounds an image's area, so an image's token count still depends on its size and shape (on b11517, 293 for a square up to 768 px, 260 for a larger one, anywhere from 236 to 540 for other shapes). Because no single image's count shows the budget, Lambo checks it with a reference image of its own: before the first image it embeds for a server that passed the `/props` check, and again every 60 seconds, it embeds a 1x1 picture and refuses image embeds, naming the flags, unless the server reports the 293 tokens b11517 reports at the 280 budget (within 8). A response to it without a token count refuses image embeds too, since `llama-server` always sends one. A server that does not answer `/props` gets no reference check, so its image budget, like the `--pooling mean` setting of any server (which `/props` does not report), rests on your word; the log says so once.
- Before its first embed, Lambo asks the server's `/props` which file it loaded, its quantization and whether it has a vision projector. It refuses to embed with a file whose name does not mention EmbeddingGemma 2 or a quantization other than the one `model` names (llama.cpp's own names are matched to the file names' tokens, so `Q4_K - Medium` is `Q4_K_M` and `all F32` is `F32`), and refuses images when the server has no vision projector. A server that does not answer `/props` (a hosted endpoint, Ollama) is used without the check, and the log says so once. If `/props` cannot be reached or answers with a server error, the log says so once and Lambo asks again after a wait that doubles from 1 second up to 30 seconds, not on every embed. Until a server has passed the check once, text and images embedded in that window (at most about 30 seconds per failed check, typically at startup) go to it unchecked, with no reference image check, the same as a server without `/props`; they are stamped with the configured contract, so if the server could be the wrong one, keep Lambo's writes stopped until the log shows the check passed. The answer is asked again every 60 seconds and right after an embed request gets no answer at all (connection refused or reset) or a 503 "Loading model", so a server restarted with another model or quantization is refused before Lambo writes more vectors under the old contract. Any other 503 (a busy server) is retried without asking again. If the server refuses Lambo's reference image itself, the error names the reference image check as a server or configuration problem, not a fault in your image. Once a server has passed the check, embeds wait (and are retried) while `/props` cannot be reached, and a server that stops answering `/props` is refused: restart Lambo if you replaced it on purpose.
- Some of these checks rest on facts measured on llama.cpp b11517 and may change with the build: the 293-token count of the reference image, and the text of the HTTP 500 for an input larger than the physical batch ("increase the physical batch size"), which Lambo settles as a failed input naming `--ubatch-size`. After upgrading llama.cpp, re-measure them (`evidence/issue-22-eg2/` records how): a build that frames images differently refuses every image with a message naming b11517 and the flags (set `images = false` meanwhile), and a build that rewords the 500 makes an oversized input a retried server error again.
- An image sent to a server started without `--mmproj` fails as a configuration error naming `--mmproj`, not as a retryable server error. Without `--mmproj`, set `images = false`.

#### Size invariance

Every image is resized to a 768 px longer side before it is embedded. That makes its vector largely, but not fully, independent of the size you send:

- A flat image (one colour) gives a bit-identical vector at any size.
- Real images sent at 768 px or larger agree to a cosine of at least 0.999.
- Small images with sharp detail can drift by up to about 2% (a cosine of 0.98 for a checkerboard sent at 128 px), because enlarging cannot restore detail that was never sent.

If bit-identical vectors matter, for example when you compare vectors directly or deduplicate on them, always send the same rendition of an image, such as the original file.

### Elastic Inference API

`kind = "elastic"` creates embeddings through the Elasticsearch Inference API, so a deployment that already runs on Elastic needs no second embedding service. It needs the `embed-elastic` feature, which released binaries include.

```toml
[embedder]
kind = "elastic"
url = "https://my-cluster.es.example.com"
model = ".jina-embeddings-v3"     # the inference endpoint id
dim = 1024
api_key_env = "LAMBO_ES_API_KEY"
canary = "verify"
```

- Lambo sends `POST <url>/_inference/text_embedding/<model>` with one text per request and reads the `text_embedding` answer. `url` and `model` are both required; neither has a default. `model` is the inference endpoint id, and which ids exist depends on the deployment: `GET /_inference/_all` lists them with their `task_type`. Only a `text_embedding` endpoint with float elements works. ELSER (`.elser-2-elastic`) is `sparse_embedding` and the multimodal endpoints (such as `.jina-clip-v2`) are task type `embedding`, so Elasticsearch refuses them for this kind, and the error says so. An endpoint that returns byte or bit embeddings is refused too.
- `url` follows the same rules as `[recall]`: `http://` or `https://`, and no user name, password, query string or fragment. A path prefix (a proxy in front of the cluster) is kept.
- `api_key_env` names the variable that holds an Elasticsearch API key (the encoded form). Lambo sends it as `Authorization: ApiKey <key>`, as the recall tier does, only over `https` or over plain `http` to a loopback host. The other rules under [Hosted endpoints](#hosted-endpoints) apply the same way: an unset variable stops startup, redirects are not followed, and an error body is quoted only with the key removed. Omit `api_key_env` for a cluster with security off.
- `dim` must equal the endpoint's width (`.jina-embeddings-v3` is 1024). A response of any other width fails the write, naming both numbers.
- A stored concept is sent with `input_type: INGEST` and a recall query with `input_type: SEARCH`, so an asymmetric model embeds each in its own role. Not every Elastic service accepts `input_type`. An endpoint that refuses it fails as a configuration error that names `send_input_type`. Set `send_input_type = false` to omit the field for both roles. Lambo never drops it on its own, because without the roles an asymmetric model embeds into a different space.
- The session's contract is kind `elastic` with the endpoint id as its model, for example `.jina-embeddings-v3`, or `.jina-embeddings-v3;input_type=off` when `send_input_type = false`. Another endpoint id, or turning `send_input_type` off, is a different contract: start a fresh session or run `lambo re-embed`.
- Elastic can change the model behind an endpoint id without changing the id, and the contract would not notice. The canary does: set `canary = "verify"` so every writer attach embeds the canary phrases again and is refused when they drift from the vectors this store pinned (`--allow-embedding-mismatch` attaches anyway). The default `"warn"` only logs it.
- Exactly one Elastic contract has a calibration row (#237): `.jina-embeddings-v3` at 1024 dims with `send_input_type` on, measured at recent-leg 0.13, layer floor 0.39 and merge threshold 0.86 (`evidence/issue-237/`). Any other endpoint id, width, or `send_input_type = false` has no row — even one whose id names BGE-M3, because an endpoint id is a name the operator chose — and Lambo logs once at startup that the contract is uncalibrated.
- `url` and `model` are the same keys `llama-server` uses, so `LAMBO_LLAMA_EMBED_URL` and `LAMBO_LLAMA_MODEL` override them here too.
- `connect_timeout_ms` (default 5000) bounds establishing the connection and `timeout_ms` (default 60000) the whole request, as for the other HTTP embedders. A transport failure says which it was — a timeout, a refused connection, or another transport error — with the underlying cause appended, and the URL stripped as before. The 5 s connect default fails fast on broken DNS; leave it unless the endpoint is slow to accept: a cold Elastic Cloud Serverless deployment can need 20 s for its first connection, in which case raise `connect_timeout_ms` (or `LAMBO_EMBED_CONNECT_TIMEOUT_MS`) rather than reading the timeout as an outage to wait out.

**When Elastic is unavailable.** The embedder has no fallback. A second embedder would put vectors from two models in one session, which the embedding contract forbids. With `match_strategy = "hybrid"` (the default), a derive whose embed fails is not applied. What happens to the write depends on why the embed failed:

- **An outage keeps the write.** A connection failure, a timeout, a response cut off before its body arrived in full (a reset, or a stall past the request timeout), a status that says the server is busy (`408`, `425`, `429`, `5xx`) or a status Lambo does not classify leaves the write's durable intent in place, and its receipt answers `pending_replay`. The server holds that agent's later writes behind it and retries them in the background, oldest first (a second after the outage, backing off to every 30 seconds), so they apply in order once Elastic is back, with or without a further write; what is still held when the session closes, the next serve re-attempts. That serve replays only after one liveness embed at startup succeeds; if Elastic is still down, the intents stay pending and nothing retries them until the next restart. Asked about the same receipt id there, `lambo_stats` answers `pending_replay` while the replay is still owed, `applied_after_restart` once it lands, or `failed` if Elastic then refuses that content. After an outage, recall (or read the receipt after the restart) before deriving the same concept again, or it may be written twice.
- **A failure about the text or the configuration is final.** A `400`, `413`, `415` or `422` (Elastic refused the text, the `input_type` field or the endpoint's task type), a `401`, `403` or `404` (a configuration error an operator must fix), a redirect, a response of the wrong width, one Lambo cannot parse or one over the size cap (64 bytes a dimension, at least 4 MiB, refused without being read further or quoted), and a vector that is not finite or has zero norm all settle the write `failed` for good. The next serve does not retry it.

A write not yet attempted when the session closes is kept as a durable intent too, and replayed by the next serve. Intents outlive the process only in a persistent store; with `store.kind = "memory"` nothing survives a restart. A recall whose query cannot be embedded skips the vector leg with a warning and answers from the keyword and recent legs. To keep writing without an embedder, declare `MatchStrategy::Canonical` through the library's `MemoryBuilder::match_strategy`; `lambo.toml` has no `match_strategy` key and refuses one.

<Warning>
The `elastic` embedder and the `[recall]` tier are independent: you can configure either without the other. Using Elastic for both puts both of recall's vector dependencies on one service. With the recall tier alone, an Elastic outage is survivable: recall ranks vectors in the store and the writer repairs the index afterwards. With Elastic also creating the embeddings, the same outage means writes answer `failed` (under `hybrid`; each keeps its durable intent, and the next serve re-attempts it) and recall answers from its keyword and recent legs only, until Elastic is back.
</Warning>

#### Running the live Elastic embedder test

One ignored test embeds a document and a query against a real inference endpoint and checks the width and the unit norm of both. It is not part of CI. An explicitly requested run without the URL or the id fails rather than skipping. With the API key exported in `LAMBO_ES_API_KEY` (leave it unset for a local cluster with security off), run:

```sh
LAMBO_ELASTIC_EMBED_URL=https://my-cluster.es.example.com \
  LAMBO_ELASTIC_INFERENCE_ID=.jina-embeddings-v3 LAMBO_ELASTIC_EMBED_DIM=1024 \
  cargo test --features embed-elastic --lib embed::elastic::tests::live -- --ignored --nocapture
```

<Warning>
Do not switch embedder models in the middle of a session without re-embedding, because vectors from different models are not comparable. The kind, the model, and the width together form the session's embedding contract.
</Warning>

## Daemon cadence

`[daemon]` is optional and sets cadence only — how often the background work runs, never what a concept must clear to be promoted. Omit the whole section for the defaults.

| Key | Default | What it sets |
|---|---|---|
| `gc_interval` | `10000` | Mutations between GC sweeps. |
| `gc_max_interval_secs` | `86400` | Seconds after the last GC sweep at which a session with at least `gc_idle_floor` mutations since then sweeps anyway. |
| `gc_idle_floor` | `100` | Session mutations since the last sweep below which the time bound does not fire. |
| `canonization_eval_interval_secs` | `60` | Seconds between canonization evaluation passes. |

A degenerate value is refused rather than quietly clamped — `gc_interval = 0` is a mutation counter and not a period, so it stops the process:

```
$ lambo --config lambo.toml demo
lambo demo: failed to build backends: config: gc_interval must be >= 1 (a mutation counter), got 0
```

The check runs wherever the process resolves an embedder, because that is the resolution path the cadence is applied on. Four commands do not resolve one — `lambo provision`, `lambo saints`, `lambo inspect` and `lambo stats` open the store alone — so those four accept a degenerate cadence without complaint. Every other command refuses it.

That boundary is not "commands that build a session". `lambo recall` builds none — it is a lease-free reader — and is refused anyway, because the refusal is about the file, not about a lease:

```
$ lambo --config lambo.toml recall --session s --query x
lambo recall: failed to build backends: config: gc_interval must be >= 1 (a mutation counter), got 0
$ lambo --config lambo.toml saints --session s
0 canonical memories in session 's'
```

A bad `promotion_policy` has the wider scope of the two, and the difference is worth knowing: an unparseable policy is refused while the file is being read, so it stops every command, those four included. A degenerate cadence is refused later, when the backends are built. See [Promotion policy](#promotion-policy).

Under the default `Swarm` policy `gc_interval` is the one worth understanding. Stage 1 requires `gc_survived >= 3`, so at the default a concept needs roughly 30000 mutations before it can be promoted at all, which an ordinary session of a few dozen concepts never reaches — this is why `lambo demo` sets it to 1 internally. Under `Solo` it does not gate Candidates; see [Promotion policy](#promotion-policy). `lambo.example.toml` carries the same notes inline.

GC also sweeps on time. When `gc_max_interval_secs` has passed since a session's last sweep and the session took at least `gc_idle_floor` mutations since then, it sweeps even though it is far below `gc_interval`; whichever trigger comes first wins. An idle session never sweeps on time alone (bar the one catch-up below), so `gc_survived` keeps measuring survival under eviction pressure rather than age. The time and watermark of the last sweep are stored with the session, so a writer restart does not reset the clock and does not by itself cause a sweep: a restarted writer sweeps only if one was already due. A session that took at least `gc_idle_floor` mutations since its last sweep and whose writer was down for a week sweeps once on its first cycle back, not seven times. A session that has never swept starts its clock when a writer first attaches to it, rather than sweeping. That is a delay, not an exemption: a never-swept session counts every lifetime mutation toward `gc_idle_floor`, so one that already has at least that many sweeps once about `gc_max_interval_secs` after the clock started, even if no write has arrived since. This is a deliberate catch-up for stores that grew before sweeps ran on time. Both keys must be positive; zero is refused the same way `gc_interval = 0` is. A `gc_idle_floor` at or above `gc_interval` is accepted but makes the time bound unreachable (the mutation trigger always gets there first), so the file is accepted with a warning at startup. Neither changes what a sweep collects.

## Multi-session serving

`[serve]` configures one `lambo serve` process that holds several sessions. It is optional: omit it and `lambo serve` behaves exactly as it always has.

This section is the key reference. For how pinned and on-demand sessions, credentials, bounds and the admin routes fit together, read [Several sessions in one serve](/cli#several-sessions-in-one-serve) first.

An HTTP `lambo serve` reads `sessions`, `default_session` and `max_attached`: it pins every session in `sessions` beside its `--session` values, serves `default_session` at `/mcp`, and refuses to start when the pinned sessions together exceed `max_attached` or `default_session` is not one of them (the default session must be pinned). See [Several sessions in one serve](/cli#several-sessions-in-one-serve). A stdio serve owns one session and ignores `sessions` and `max_attached`: its `--session`, or, without one, the session `[[serve.projects]]` or `default_session` chooses ([below](#choosing-a-stdio-serves-session)).

An HTTP `lambo serve` also enforces `[[serve.credential]]`; see [Credentials](#credentials). A stdio serve authenticates nobody (its client owns the process), so it ignores the credentials and never reads their variables.

An HTTP `lambo serve` enforces `attach_concurrency`, `idle_detach_secs` and `per_session_rps` too. `per_session_rps` gives every session its own request bucket; the other two bound the sessions a serve attaches on demand, which it does once a credential reaches past the pinned sessions (a `session_prefix`, or an unpinned name). A stdio serve owns one session, so none of the three applies to it. An HTTP serve never reads `[[serve.projects]]`, which is a stdio serve's only: when an HTTP serve's table sets it, `lambo serve` logs one warning at startup (`[serve] sets keys this serve ignores`) that names the key and no value from it. A malformed table is still refused when the file is read, so it stops every command, like an unknown key.

```toml
[serve]
sessions = ["lambo", "rustydocs", "general"]   # pinned: attached at startup
default_session = "general"
max_attached = 16
attach_concurrency = 2
idle_detach_secs = 900
per_session_rps = 50

[[serve.projects]]
path = "~/Documents/work/lambo"
session = "lambo"

[[serve.credential]]
name = "agents"
token_env = "LAMBO_AGENTS_TOKEN"
sessions = ["lambo", "rustydocs", "general"]

[[serve.credential]]
name = "dresscode"
token_env = "LAMBO_DRESSCODE_TOKEN"
session_prefix = "dc-u-"
create = true
erase = true
```

| Key | Default | What it sets |
|---|---|---|
| `sessions` | none | Pinned sessions, attached at startup and never idle-detached. Served by an HTTP `lambo serve`, beside its `--session` values. |
| `default_session` | none | The session `/mcp` serves, and the one a stdio serve without `--session` uses when no `[[serve.projects]]` entry covers its working directory. |
| `max_attached` | `16` | Cap on attached sessions, pinned plus on-demand. At least 1, and at least the number of pinned sessions. At the cap, an on-demand attach detaches the least recently used idle on-demand session that the asking credential's share allows, or is refused with `503` and `Retry-After` when there is none. A credential reaching past the pinned sessions with no place left beside them is warned of at startup. |
| `attach_concurrency` | `2` | Sessions that may attach at once, on demand or retried in the background. At least 1. Always 1 on SQLite, whose one connection serializes attaches with every flush. |
| `idle_detach_secs` | `900` | Seconds an on-demand session may go without a tool call before it is detached (its tail flushed, its lease released). At least 1. Pinned sessions are never idle-detached. |
| `per_session_rps` | `--rate-limit-rps` | Request rate for each attached session (burst twice that), drawn after the credential's; a request over it gets `429`. `0` turns the per-session limit off. A serve of one session that attaches nothing on demand applies it only when it is set. |
| `[[serve.projects]]` | none | `path` and `session`: a stdio serve started without `--session` under `path` uses `session`. `path` must be absolute or start with `~/`; `*` is supported in its final component. An HTTP serve does not read it. |
| `[[serve.credential]]` | none | A bearer credential and the sessions it may reach (below). |
| `layers` | none | The shared sessions every pinned session that is not itself a layer also reads on `lambo_recall`, as an ordered list, nearest tier first. At most one in this release. See [Layers](#layers). |
| `[serve.session_layers]` | none | Per-session overrides of `layers`, each the same list form; `[]` opts a session out. |
| `[[serve.layer]]` | none | Per-layer ranking: `session`, `weight` (default `0.5`) and `min_similarity` (default `0.50`, or the embedding contract's calibrated floor: 0.72 under EmbeddingGemma 2 at 768 dims; see `[embedder] calibrated_layer_floor`). |

Every session named in `[serve]` must be addressable by URL: 1 to 128 bytes of `A-Z`, `a-z`, `0-9`, `.`, `_`, `:` and `-`, not starting with `.`. A name outside that rule is refused here, but you can still serve it on its own with `lambo serve --session <name>`, which keeps its looser rule.

A credential never holds its token. `token_env` names the environment variable that does, and an HTTP `lambo serve` reads it at startup: an unset, empty or non-UTF-8 variable refuses the start (exit `2`, before any model is loaded), naming the credential and the variable and never a value. An inline `token = "..."` is refused, and the refusal does not quote it. A credential reaches the sessions in `sessions` (exact names, or `"*"` for every pinned session plus every session under any credential's prefix) and those under `session_prefix` (ids that start with the prefix and are longer than it). It may carry `create` (attach a session that does not exist yet), `erase` (erase a session in its reach with `POST /admin/s/<session>/erase`) and `admin` (list the sessions in its reach with `GET /admin/sessions`). A request to either route without the flag, or for a session outside the credential's reach, gets the empty `404`. The names `default` and `local` are reserved, and `token_env` may not be `LAMBO_AUTH_TOKEN`. `token_env` must be a conventional variable name (`[A-Z_][A-Z0-9_]*`, at most 64 bytes) and must not look like a token (an AWS key id, or a 20-plus character run of letters and digits with no `_`), because it is the key a token is most likely to be pasted into by mistake. A value that fails is refused without being quoted.

Each `[[serve.credential]]` entry takes these keys:

| Key | Required | What it sets |
|---|---|---|
| `name` | Yes | A name for logs, refusals and the ledger's `credential` field: 1 to 128 bytes of `[A-Za-z0-9._:-]`, not starting with `.`. `default` and `local` are reserved. |
| `token_env` | Yes | The environment variable holding the token, read at startup by an HTTP serve. Not `LAMBO_AUTH_TOKEN`. |
| `sessions` | `sessions`, `session_prefix` or both | Exact session names, or `"*"` for every pinned session plus every session under any credential's prefix. A name that is not pinned is attached on demand. |
| `session_prefix` | | Every session whose id starts with this and is longer. Attached on demand. |
| `create` | No (`false`) | May attach a session that does not exist yet. |
| `erase` | No (`false`) | May erase a session in its reach with `POST /admin/s/<session>/erase`. |
| `admin` | No (`false`) | May list the sessions in its reach with `GET /admin/sessions`. |

### Credentials

Every HTTP request to `lambo serve` is made as one credential, and that credential decides which sessions the request may reach. A request presents its token as `Authorization: Bearer <token>`; only a loopback serve with no credential configured needs none. The credentials a serve has:

| Configured | Credentials |
|---|---|
| nothing, on loopback | One implicit credential, `local`: every request is accepted without a token and reaches every pinned session. This is how a loopback serve has always behaved. |
| nothing, beyond loopback | None: `lambo serve` refuses to start. |
| `--auth-token` or `LAMBO_AUTH_TOKEN` | `default`: every pinned session. |
| `[[serve.credential]]` entries | Each entry, with its own `sessions`, `session_prefix` and flags, beside `default` when a legacy token is set too. |

Once any credential is configured, the implicit `local` credential is gone, so a loopback serve with a `[[serve.credential]]` requires a token on every request. Neither `default` nor `local` carries `create`, `erase` or `admin`. A configured token equal to the legacy one, or two credentials with the same token, refuse the start without quoting either token.

The presented token is compared with every configured token in constant time, so response timing does not say which credential a guess nearly matched. A request without a valid token gets `401`, whatever it asked for. A request with a valid token for a session outside that credential's reach gets the same empty `404` as an unknown session or an unrouted path, whether that session exists, is held by another writer, is being detached or failed, and the serve consults no store to answer it. Only inside its reach can a caller see a `503`, or the erased answer (MCP error `-32003` to a `POST` of one JSON-RPC request with an `id`, `initialize` included, and `410` to anything else). `/mcp` serves the default session to a credential that reaches it.

A session inside a credential's `session_prefix`, or named in its `sessions` but not pinned, is attached on demand by the first request for it: always with `create = true`, and without it only once the session exists (a writer has used it); otherwise the request gets the `404`. See [Several sessions in one serve](/cli#several-sessions-in-one-serve). `lambo serve` logs a warning at startup for a credential without `create` that reaches sessions it does not pin, and for `LAMBO_AUTH_TOKEN` (or `--auth-token`) set beside `[[serve.credential]]`: that token stays the `default` credential, reaching every pinned session, until you unset it.

A token must be printable ASCII with no leading or trailing whitespace, and at most 4096 bytes. A token that breaks this (a trailing newline from an env file, say) refuses the start with exit 2, naming the credential and never quoting the token. A presented token over 4096 bytes, or a request carrying two `Authorization` headers, gets the ordinary `401`.

Further rules once credentials are in play:

- **Host.** A loopback serve with no credential refuses a request whose `Host` is not `localhost`, `127.0.0.1` or `::1`, as protection against DNS rebinding. A serve that requires a token accepts any `Host`, because a rebound page cannot present a token it does not know, and a serve bound beyond loopback is reached under its own address or name.
- **Fair shares.** `--rate-limit-rps` applies per credential: each has its own bucket, so one credential's flood never rate-limits another. `--max-sessions` caps the MCP sessions of the whole process, and each credential may hold at most an even share of it, `--max-sessions` divided by the number of credentials, rounded down and at least 1. While `--max-sessions` is at least the number of credentials, the shares fit inside the cap, so no credential can lock the others (the operator's included) out. With more credentials than that, each share is 1, and a credential can be refused at the process-wide cap while it holds no session. With one credential the share is the whole cap.
- **MCP sessions belong to their opener.** An MCP session id answers only the credential whose `initialize` opened it. Another credential naming it, even one that reaches the same session, gets exactly what an unknown or expired id gets.
- **Attribution.** With `--ledger`, each `call` line made through a configured credential carries `credential`, that credential's name. Calls as `default` or `local` carry no such field.
- **What a token does not guard.** The credential count is not secret: response timing scales with it. A stdio `lambo serve --session <name>` run by the same OS user forwards to the HTTP serve's per-session Unix socket (a directory only that user can enter) and reaches that session whatever the credentials say. Credentials guard the network; the OS user is the boundary on the machine.

### Layers

A layer is a shared session, such as `general`, whose memories a project session's recall reads too. With `layers = ["general"]`, a `lambo_recall` to `lambo` reads `lambo` and `general` in one call and merges the two answers under one token budget. `lambo_recall` and `lambo_inspect` take `scope` to read one of the two alone. Writes, `lambo_reserve` and `lambo_saints` act on the addressed session unless they too pass `scope`: an agent writes a ruling that applies in every project with `scope = "general"`, which the layer's own write queue applies (writes to different sessions have no ordering between them, a write into a layer refuses relative file paths, as does any write to the layer's own address, and no reference or edge crosses sessions; see the MCP reference's *Writing to a layer*). A scoped call draws on the layer's own `per_session_rps`. No new credential capability is involved: a credential that reaches a layered session reaches its layers, which the start check enforces. Layers are an HTTP serve's. A stdio serve that holds its session itself serves it unlayered and logs one warning when the session would be layered; a stdio serve that forwards to an HTTP `lambo serve` holding the session (the usual case on a machine running one) reaches that session through the holder, layers included, and warns of nothing.

```toml
[serve]
sessions = ["lambo", "rustydocs", "lambo-paper", "general"]
layers = ["general"]               # ordered, nearest tier first

[serve.session_layers]
lambo-paper = []                   # opt one session out

[[serve.layer]]
session = "general"
weight = 0.5                       # measured on BGE-M3 (#157)
# min_similarity = 0.50            # absolute vector relevance; unset: 0.50, or
                                   # the contract's calibrated floor (EG2: 0.72)
```

`layers` applies to every pinned session that is not itself a layer; `[serve.session_layers]` overrides it per session. Every shape is a list, but this release supports one layer per session, and a longer list is refused (`lists 2 layers; at most 1 is supported`). On-demand sessions are never layered.

A merged recall interleaves the two answers by rank: the layer's hit at position `r` ranks as `weight / r`, against `1 / r` for the session's own. At the default `0.5` the layer's first hit sits beside the session's second. An ordinary layer hit is admitted only with vector cosine at or above its `min_similarity` (default `0.50`, or the contract's calibrated floor, below); keyword matches and warnings do not bypass this absolute cutoff. A dependent in an anchored layer traversal answer also passes. These defaults were measured on BGE-M3 in [issue #157](https://github.com/nrynss/lambo/issues/157). An unset floor is calibrated per embedding contract ([#87](https://github.com/nrynss/lambo/issues/87), `evidence/issue-87-calibration/`). Under EmbeddingGemma 2 (768 dims, Q8_0, `lambo-eg2-v2`) nearly every irrelevant concept scores above 0.50, so such a layer's floor is **0.72**: the value that admits the same share of irrelevant concepts as 0.50 does under BGE-M3. On the held-out split it keeps 92.5% of true hits. A `min_similarity` you set always applies, and `[embedder] calibrated_layer_floor = false` keeps 0.50. A layer with no vector evidence contributes no ordinary hits, including during embedding or vector-search failure; the caller's own keyword recall and anchored dependency answers still work. See [`lambo_recall`](/mcp#lambo_recall) for what a layered answer looks like.

Refused when the file is read (every command): a name outside the session charset or listed twice, more than one layer per session, a session that lists itself, a layer that has layers of its own (no transitive layering), and a `[[serve.layer]]` entry that names no configured layer or sets `weight` to anything but a finite positive number or `min_similarity` outside `[0, 1]`. Unknown keys in these tables are refused like any other.

Refused when an HTTP `lambo serve` starts (exit `2`), before any lease is taken:

- a layer, or a session with a non-empty `[serve.session_layers]` list, that the serve does not pin (by `[serve] sessions` or `--session`). Pinned sessions hold their lease for the serve's life, so a recall never attaches a layer on demand and a layer is never evicted;
- a credential that reaches a layered session but not each of its layers, naming the credential and both sessions. The implicit `local` and legacy `default` credentials reach every pinned session, so a serve using only those needs nothing more.

Once the pinned sessions are attached, a layer whose embedding contract differs from its session's refuses the start too (a model left unset in one and set to `""` in the other counts as different, and the message says so).

While the serve runs, a layer can stop serving: another writer took its lease, it is being detached, or its attach failed. Losing `general`'s lease detaches `general` alone. Until it is attached again, every layered recall answers from its own session with one warning, `recall: layer general is unavailable; results are from lambo only`, and a `scope` naming the layer is refused: retryably while it is held elsewhere or detaching, and as permanent once its attach has failed for good or it was erased (an erased layer is also warned of at start).

### Project URLs and a shared layer

An HTTP client chooses its session by URL, not by its working directory or a
project header. A useful split keeps operator-wide rulings in `general`, project
work in its own session, and work outside a mapped project in `general-usage`:

```toml
[serve]
sessions = ["lambo", "rustydocs", "general", "general-usage"]
default_session = "general-usage"
layers = ["general"]

[[serve.layer]]
session = "general"
weight = 0.5
```

Start the HTTP serve without a `--session` override if `/mcp` should use this
`default_session`. Register `.../mcp/s/lambo` in the Lambo project's client and
`.../mcp/s/rustydocs` in RustyDocs; register `.../mcp` as the client's fallback.
`general` is itself a layer, so it does not inherit `layers`. The project
sessions and `general-usage` read it. A per-session empty list can opt a
consumer out, as in the preceding example.

This configuration does not copy memories or move existing sessions. Each
project's text recall reads its own session plus `general`; its writes
go to the addressed project unless a call passes `scope = "general"` (see
[Writing to a layer](/mcp#lambo_derive)). See the
[read examples](/mcp#reading-a-layer-hit) and the operator's
[cut-over runbook](https://github.com/nrynss/lambo/blob/main/docs/operations/dogfood-rig.md#multi-session-cut-over-runbook).

### Choosing a stdio serve's session

A `stdio` serve given `--session` uses it and reads none of this. Without `--session` it picks, in order:

1. The `[[serve.projects]]` entry whose `path` contains the serve's working directory. When several do, the longest path wins. Paths are compared whole directory by whole directory, so `~/work/lambo` covers `~/work/lambo/src` but not `~/work/lambo-wt`.
2. `default_session`.
3. Nothing: the serve refuses with the usual missing `--session` error and exit code 2, before it builds any backend.

A leading `~` in `path` expands to `$HOME` (`~user` is refused). Stars in the value of `$HOME` remain literal; only the configured path supplies pattern syntax. The working directory and every entry are resolved to real paths first, following symlinks, `.` and `..`, so a project entered through a symlink uses the entry for the directory the link points to. An entry whose directory does not exist never matches. If the working directory itself cannot be resolved (for example, it was deleted), the map is skipped and `default_session` applies. Two entries that resolve to the same directory but name different sessions are refused rather than picked by file order, as a configuration error (exit code 1). When `HOME` is unset or is not an absolute path, every `~` entry is skipped and the rest of the map still applies; the serve logs one warning saying so. The serve logs which entry it used, by its configured `path`. Neither that line, the warning, nor any refusal quotes the working directory or `$HOME`.

A `*` in the final component of `path` matches zero or more filename bytes, so `~/work/lambo-wt-*` covers sibling worktrees and their descendants. The whole filename must match. Multiple stars are allowed; `?` and brackets are ordinary characters, backslashes are path separators on Windows and ordinary characters elsewhere, and there is no escape for a literal star. Stars in parent components are refused, including `*/..` or `*/.`; a trailing slash is allowed. Pattern matching is byte-exact and case-sensitive, including Unicode form, even on filesystems where literal path lookup ignores case or Unicode normalization. Non-UTF8 child names can match `*`.

The literal parent is resolved first, then its immediate children are scanned and matching directory roots are resolved, following symlinks even when their target is outside the parent. Each matching root covers its descendants by whole components. The deepest canonical root wins; at equal depth a literal entry wins over a pattern. Equal-depth patterns naming different sessions are refused, regardless of how many literal characters their patterns contain; agreeing ties are allowed. Missing, non-directory or unreadable parents skip that pattern, as does a failed directory listing. Startup scans every immediate child once per pattern, retaining only the best match, so a large parent directory adds startup work. No recursive directory scan is performed.

The map is read from the `lambo.toml` the serve loads: `--config`, then `LAMBO_CONFIG`, then `./lambo.toml` in the working directory. So a single global map used by every project needs the client to pass `--config` or set `LAMBO_CONFIG`; otherwise each serve reads its project's own `./lambo.toml`, if any, whose `default_session` or `[[serve.projects]]` then chooses the session, just as it already chooses the store. See [Serve a session](/cli#serve-a-session).

## Read-only window views

`[web]` sets which sessions `lambo serve-web` serves, which `Host` names it answers without a credential, who may read which session, and how it reads each session. It is optional: omit it and the defaults below apply.

The window reads the store through a **view**: one load of a session that every request and every open tab shares until it is older than `view_ttl_ms`. The next request after that reloads it, and requests that arrive while a load is running wait for that one load instead of starting their own. A failed load is not kept: the requests waiting on it get the error, and the next request tries again. So the store sees about one load per session per `view_ttl_ms` however many tabs are open, and the page shows durable state up to `view_ttl_ms` older than the store. The writer-published flush lag is still read on every poll.

```toml
[web]
sessions = ["lambo", "rustydocs"]
allowed_hosts = ["lambo.example.com"]
view_ttl_ms = 1500
max_loaded_sessions = 4
load_concurrency = 2
recall_concurrency = 4
embedder = true
list_sessions = false
discover_sessions = false
inherit_serve_credentials = false
```

| Key | Default | What it sets |
|---|---|---|
| `sessions` | none | Sessions to serve, after any `--session` flags. The first one overall is the default, served at `/`; each is served at `/s/<session>/`. With more than one in total, each name must be 1 to 128 bytes of `[A-Za-z0-9._:-]`, not starting with `.`. |
| `allowed_hosts` | none | `Host` values answered while no credential is configured, beside `localhost`, `127.0.0.1` and `[::1]`, after any `--allowed-host` flags. A name, or `name:port` for that port only. |
| `view_ttl_ms` | `1500` | Milliseconds a view is reused, the page's poll interval. `0` reloads on every request, still one load for requests that arrive together. At most `60000`. |
| `max_loaded_sessions` | `4` | Views kept in memory at once. The least recently used is dropped beyond it. Also caps entire dynamic prefix slots, including metadata and query caches; inactive slots expire after five idle minutes, pruned on the next dynamic request. Active requests cannot be evicted; if all slots are active, a new dynamic session gets `503` with `Retry-After: 1`. At least 1. |
| `load_concurrency` | `2` | Session loads that may run at once. 1 to 1024. Always `1` on SQLite. |
| `recall_concurrency` | `4` | Recalls that may run at once. A recall that waits 2 seconds for a slot gets `503` with `Retry-After: 1`. 1 to 1024. |
| `embedder` | `true` | Use the configured embedder for recall's vector leg. It is loaded on the first recall that needs a query vector, never at startup. `false` never loads it: recall runs on its keyword and recent parts and says the vector leg is off. `--no-embedder` does the same. See [Memory and the embedder](#memory-and-the-embedder). |
| `list_sessions` | `false` | Answer `GET /api/sessions` with the served sessions the presenting credential may list. Off, the route does not exist. With no credential configured it names every served session to anyone who reaches the port, and startup warns about it. The page's session picker offers these names, plus "Other session…" for a name typed in; without the listing it asks for a name instead. |
| `discover_sessions` | `false` | Also serve every live session in the store, including sessions created after startup, without editing `sessions` or restarting. Reaches only callers whose scope already covers every served session: no credential on loopback, `LAMBO_AUTH_TOKEN` / `--auth-token`, and a `[[web.credential]]` with `"*"`. Exact names, `session_prefix` and inherited credentials read what they read without it. Erased sessions and names outside `[A-Za-z0-9._:-]` are never served or listed. On a loopback bind it also turns on `GET /api/sessions`. `--discover-sessions` turns it on from the command line. See [Session discovery](#session-discovery). |
| `inherit_serve_credentials` | `false` | Also accept every `[[serve.credential]]` as a read credential with the same scope as on `lambo serve`, so its `"*"` is serve's, not every served session (see below). Its `create`, `erase` and `admin` are dropped: the window only reads. With no `[[serve.credential]]` nothing is imported, and startup says so; with no other credential either, the window stays unauthenticated on loopback. |

An unknown key, an out-of-range value, an empty or repeated session name and a malformed host are refused when the file is read, so they stop every command, like any other invalid key. A numeric refusal names the key and its bound, never the value. At startup `lambo serve-web` prints the sessions and bounds it runs with. It checks the store's schema at startup and loads each session on the first request that needs it. See [Watch a session in a browser](/cli#watch-a-session-in-a-browser).

### Memory and the embedder

The embedder is the window's only large cost, and only recall's vector leg uses it. How much it costs depends on where the model runs:

| `[embedder] kind` | Memory in the window process |
|---|---|
| `candle` (in-process BGE-M3) | About 1.3 to 1.4 GB of RAM (unified memory on Apple silicon) once loaded, on top of the copy the `lambo serve` beside it holds. Without it, the window holds little beyond its session views (at most `max_loaded_sessions` of them). |
| `bge_m3`, `embeddinggemma2`, `bedrock`, `gemini`, `elastic` | Nothing extra: the model runs in another process or service, and the window only sends it requests. |
| `fixture` | Nothing extra. |

So the window does not load the embedder at startup. Browsing (the page, counts, the canonization feed, inspect, the graph and `/api/session`) never loads it. The first recall that needs a query vector loads it once, and the window keeps it until it exits; recalls that arrive while it loads wait for that one load. A recall needs a query vector only when the store can search by vector, the session's stored embedding matches the configured one, and the same query has not been embedded for that session already. The model loaded is the configured one, so recall ranks exactly as it would have with the model loaded at startup; only the first such recall is slower. Startup prints which embedder recall uses and that it loads on first use.

If the load fails, that recall still answers from its keyword and recent parts, with the line `recall: query embedding failed (...); vector leg skipped`, as when an embed fails. The failure is not kept: recalls that were waiting on that load get the same answer, and the next recall tries to load again.

To never load the embedder, set `[web] embedder = false` or start the window with `--no-embedder`. Every recall then answers from its keyword and recent parts and carries the line `recall: vector leg off by configuration ([web] embedder = false or --no-embedder); keyword and recent legs only`, and `/api/session` and `/api/pulse` report `vector_search: false`. In `/api/recall`, `top_legs.vector_cosine` is then `null` and `confidence` has the basis `keyword-only-v0`, the keyword leg's term alone, as after a failed embed (see [Top leg scores and the provisional confidence](/api#top-leg-scores-and-the-provisional-confidence)): a lower quantity than the `noisy-or-v0` value the same recall reports with the embedder on, so compare a value only with others of its basis. No layer hit is lost: the window's recall reads one session and never merges a layer, since [layers](#layers) are `lambo serve`'s, and `lambo serve`, whose layers admit a hit only on its vector cosine, has no switch that turns its embedder off. The window still reads the configured embedder's identity and width (no weights), so the page's embedding-contract status stays exact. The flag can only turn the embedder off; it never turns a file's `embedder = false` back on.

### Session discovery

`discover_sessions = true` (or `lambo serve-web --discover-sessions`) is for a local store that holds several sessions, such as one SQLite file shared by several projects: a session an agent creates shows up in the window without editing `lambo.toml` or restarting `lambo serve-web`. It is off by default, and then the window serves exactly its `sessions` list, as before.

```toml
[web]
sessions = ["lambo"]      # still required: the default, served at /
discover_sessions = true
```

- **Who it reaches.** Only a caller that may already read every served session: the unauthenticated loopback window, `LAMBO_AUTH_TOKEN` / `--auth-token`, and a `[[web.credential]]` whose `sessions` include `"*"`. A credential with exact names or a `session_prefix`, and every `[[serve.credential]]` imported by `inherit_serve_credentials` (whose `"*"` is serve's sessions), reads exactly what it reads without discovery. Startup prints which credentials discovery reaches.
- **What it serves.** Every session in the store that is not erased and whose name is 1 to 128 bytes of `[A-Za-z0-9._:-]`, not starting with `.`. A session with any other name is skipped: never served, never listed, and startup does not fail. A discovered session that is erased, and a name the store does not hold, get the same empty `404` as any unknown path. A startup session (`sessions` or `--session`) is served whether or not discovery is on, so once erased it is an empty page, as without discovery; remove it from `sessions`.
- **How it reads.** A discovered session is read at `/s/<session>/` only. Each request first checks that the session exists and is not erased, then loads it on demand within `max_loaded_sessions`, like a `session_prefix` session. Nothing is loaded at startup.
- **The listing.** On a loopback bind, discovery also turns on `GET /api/sessions`, which lists the discovered sessions after the served ones, so the page's session picker offers them; reload the page to see a session created since it opened. On any other bind the listing still needs `list_sessions = true`, and startup warns that every caller discovery reaches can read every live session. Every listing comes from a store read that began after the request arrived, so a discovered session erased before the request is not listed (a startup session is always listed with the served ones). The portal issues one read at a time (a read it gave up on after a timeout may still be running in the store): requests that arrive while a read is running wait for it and share the next read, rather than take an answer the store may have given before an erase.

### Portal credentials

`[[web.credential]]` gives a bearer token its own read scope on `lambo serve-web`. It has the grammar of `[[serve.credential]]` without the write capabilities, and its tokens are separate: an agent's write token is not a window token unless you set `inherit_serve_credentials`.

```toml
[web]
sessions = ["lambo", "rustydocs", "general"]

[[web.credential]]
name = "lambo-viewers"
token_env = "LAMBO_WEB_LAMBO_TOKEN"
sessions = ["lambo"]
```

| Key | What it sets |
|---|---|
| `name` | A name for logs and refusals. `default` and `local` are reserved. |
| `token_env` | The environment variable holding the token. The token itself never goes in the file. Not `LAMBO_AUTH_TOKEN`. |
| `sessions` | Exact session names, or `"*"` for every served session. |
| `session_prefix` | Every existing session whose name starts with this and is longer, including sessions created after startup. Missing and erased ids return the uniform `404`; the reader never creates them. |

Exact names and `"*"` read only startup-served sessions in the credential's scope; an explicit `session_prefix` also reads existing sessions outside that set. This also applies to inherited explicit prefixes. The opt-in listing stays limited to startup-served exact names and never expands prefixes or cached dynamic sessions. These credentials sit beside the `default` credential from `--auth-token` or `LAMBO_AUTH_TOKEN`, which reads them all. Once any credential is configured, every request needs a bearer, on loopback too, and the `Host` check is off. `create`, `erase` and `admin` are refused by name, as is an inline `token`, a credential without `token_env` or scope, and a name or `token_env` used twice. `lambo serve-web` reads each variable at startup and exits `2`, naming the credential and never a value, when one is unset, holds a token no request could present, or holds the same token as another credential or as `LAMBO_AUTH_TOKEN`. `[embedder] api_key_env` may not name a `token_env`.

An inherited `[[serve.credential]]` keeps exact and `"*"` reads within startup-served sessions: its exact names, its prefix, and for `"*"` the `[serve] sessions` of the same `lambo.toml` plus every session under any `[[serve.credential]]` prefix. That is what `"*"` means to `lambo serve`, which attaches those sessions on demand. It never means every session `[web]` serves: with `[serve] sessions = ["lambo"]` and `[web] sessions = ["lambo", "hr-private"]`, an inherited `"*"` reads `lambo` and gets the `404` for `hr-private`. A session that `lambo serve` pins only with a `--session` flag is not in the file, so an inherited `"*"` does not reach it; name it in `[serve] sessions` or give the window its own `[[web.credential]]`. With `list_sessions`, an inherited `"*"` lists the served sessions in `[serve] sessions`, never one it reaches only through a prefix.

A browser cannot send the header itself; see [Watch a session in a browser](/cli#watch-a-session-in-a-browser).

## Features

Cargo features decide which stores and embedders exist in your binary, and `lambo.toml` (or the environment) picks among them when the process starts. Asking for a kind that was not compiled in is a startup error that names the feature to rebuild with, not a fallback to another kind, and an unknown key in the file is refused the same way. Released binaries are built with `ship` (the Metal asset adds `embed-candle-metal`), so for them choosing among those kinds is only a config change; any other kind needs a rebuild with its feature.

| Feature | What it adds |
|---|---|
| `store-memory` | The in-memory store. |
| `store-sqlite` | The SQLite store. |
| `store-cockroach` | The CockroachDB store. |
| `store-postgres` | The PostgreSQL + pgvector store (`kind = "postgres"`). |
| `recall-elastic` | The Elasticsearch recall tier (`[recall]`). |
| `embed-fixture` | The deterministic fixture embedder. |
| `embed-bge` | BGE-M3 embeddings through `llama-server`. |
| `embed-gemini` | Vertex AI Gemini embeddings (`gemini-embedding-001`), authenticated with a service account. |
| `embed-eg2` | EmbeddingGemma 2 text and image embeddings through `llama-server` (`kind = "embeddinggemma2"`). Builds on `embed-bge`. |
| `embed-elastic` | Embeddings through the Elasticsearch Inference API (`kind = "elastic"`). Builds on `embed-bge`. |
| `embed-candle` | In-process BGE-M3 through candle (`kind = "candle"`), CPU backend only. Builds anywhere. |
| `embed-candle-metal` | `embed-candle` plus the Metal GPU backend. Apple silicon only. This is what the Metal release asset adds to `ship`. |
| `embed-candle-accelerate` | `embed-candle` plus Apple's Accelerate framework for the CPU backend. macOS only. |
| `embed-candle-cuda` | `embed-candle` plus the CUDA GPU backend. Needs a CUDA toolkit at build time and an NVIDIA GPU at runtime. |
| `embed-bedrock` | Reserved for Amazon Titan embeddings through Bedrock. Not implemented: `kind = "bedrock"` fails at startup whether or not this feature is compiled. |
| `ship` | The adapter set released binaries carry: every store and embedder above except `embed-bedrock` and the `embed-candle` family, plus `recall-elastic`. |
| `fixtures` | Committed fixture graphs for tests, which also enables `store-memory`. Not in the default build. |
| `demo` | A convenience profile: the memory and CockroachDB stores, the BGE-M3 and fixture embedders, and `fixtures`. |

The default build enables `store-memory`, `embed-bge`, and `embed-fixture`.

### Embedders and model files

The default `[embedder] kind` is `bge_m3`, which speaks the OpenAI embeddings API. Its reference setup is BGE-M3 weights in GGUF form served by llama.cpp's `llama-server` on `http://127.0.0.1:8080`, the default `url`. From a checkout, `scripts/fetch-bge-m3.sh` downloads a pinned BGE-M3 GGUF from Hugging Face into `models/bge-m3/` and checks its SHA-256, and `scripts/run-llama-embed.sh` starts `llama-server` on that file. Lambo never starts `llama-server` itself. `candle` runs BGE-M3 inside the process instead (the Metal release build), and `fixture` gives deterministic vectors with no model behind them, for tests and CI that must run without a model or a network. See [Installation](/installation#set-up-real-embeddings) for the setup and [Embedder](#embedder) for every kind.

Model weights never go in the repository. `models/` is ignored by git, and the files for other models, such as the EmbeddingGemma 2 GGUF, are kept outside the checkout.

### How a process builds its backends

A process builds the store and the embedder that `lambo.toml` configures exactly once, through one of the resolvers in `src/resolve.rs`, and hands the result to the command; in the `lambo` binary, `resolve_for_command` in `src/main.rs` picks the resolver. A command that needs both the configured store and an embedder (every writer, `lambo serve` included, which loads the file once before startup and passes it in, and the embedding readers such as `lambo recall`) calls `resolve_backends`, or `resolve_from_config_path`, which first loads the file and the environment overrides. It returns one `ResolvedBackends`: the store, the embedder, their configs, the session embedding contract, and the process `Config` with the file's settings applied. A command that never embeds, such as `provision`, calls `resolve_store_only` (or `resolve_store_only_read_only`). `lambo embed` opens no store and calls `resolve_embedder_only`. `lambo session split`, `verify` and `classify` work on explicit files rather than `[store]` and have their own resolvers in the same file; `session split` and `lambo canon` also open SQLite stores over their own explicit files (a split's output, a canon run's private copy), not over `lambo.toml`'s store. The `[recall]` tier is wrapped around the store inside these resolvers and nowhere else.

A command does not call `build_store` or `build_embedder` itself and does not resolve a second time: those registries exist for the resolvers and for adapter unit tests. A Rust program does the same with `Memory::builder().backends(resolved)`; see [Library API](/api#build-a-memory).

A full resolve refuses to start, before any session is attached, when:

- the file's own settings are invalid (a degenerate `[daemon]` cadence, an unknown `promotion_policy`, a bad `[fusion]` or `[selection]`); these are checked before any adapter is built;
- a kind is not compiled in, or its adapter refuses its configuration;
- the embedder reports a width other than `[embedder] dim`;
- the store claims vector search but reports no vector width, or reports a width without claiming vector search;
- `[store] vector_dim` is set and differs from `[embedder] dim`;
- the store reports a vector width and the embedder's differs from it.

Building an adapter is kept light. The candle embedder resolves its device, its weights' identity and its width at resolve time and loads the weights in `Embedder::prepare`, which a writer awaits after it wins the session's lease, so a `lambo serve` that loses the startup election never loads them. A caller with no writer, such as `lambo embed` or a one-shot `lambo recall`, loads them on its first embed instead.

### Vector width

The width of stored vectors belongs to the store, not to the embedder factory and not to a product constant. `[embedder] dim` is the width you expect the embedder to emit. Its default, `1024`, is BGE-M3's width and applies to every kind. There is no product-wide width rule: each adapter checks only the widths its own model can emit (for example, `embeddinggemma2` accepts `768`, `512`, `256` or `128`, so it refuses the default; `gemini` accepts `768`, `1536` or `3072`; `candle` accepts only `1024`). Each store reports its width through `GraphStore::vector_dimensions()`, and the resolve compares it with the embedder's:

| Store | Width it reports | What the comparison proves |
|---|---|---|
| `memory` | None. It has no vector column and no vector search. | Nothing: any positive width is accepted. |
| `cockroach` | `n` from `VECTOR(n)` in its schema file, `migrations/cockroach/001_init.sql` (1024). | A real check: the embedder must emit 1024. |
| `postgres` | `[store] vector_dim` when set, else `[embedder] dim`, `lambo provision` creates the `vector(n)` column at `[store] vector_dim`, else `1024`; it does not read `[embedder] dim`. | At resolve, nothing: the reported width echoes the number it is compared with. The real check is the store's own: it refuses to initialize or attach when that width differs from the live `vector(n)` column. For an embedder that is not 1024 wide, set `[store] vector_dim` before you provision. |
| `sqlite` | `[store] vector_dim` when set, else `[embedder] dim`. Its vectors are stored in a column with no width of its own. | Nothing: the store reports the number it is compared with. Set `vector_dim` to make the resolve refuse a different embedder width. |

For SQLite, and for every store, what protects stored vectors from a different model is the session's embedding contract, which vector-capable stores check on every vector read.

### Embedding spaces

A process runs one embedder for every session it serves. The first writer of a session stamps it with the embedder's contract (kind, model and width), and a later writer attach whose contract differs is refused. `--allow-embedding-mismatch` overrides that refusal; it exists for a deliberate rename of the same space, not for switching models. The same width does not mean the same space: vectors from two models, or from one model behind two servers, are not comparable. To move a session to another model, run `lambo re-embed` or start a new session; never mix models in one session. See the [Embedder](#embedder) warning and [Command line](/cli).

### Adding a backend

A new store or embedder is an adapter module, a Cargo feature, a registry arm and its documentation. It is not a change to the core, and Lambo has no plugin loading: adapters are compiled in.

1. Implement `GraphStore` (see [The GraphStore trait](/api#the-graphstore-trait)) or `Embedder` (see [The Embedder trait](/api#the-embedder-trait)) in a module compiled only under the new feature.
2. Add the feature to `Cargo.toml`, with its dependencies as optional `dep:` entries. Add it to `ship` if released binaries should carry it.
3. Add the kind to `StoreKind` or `EmbedderKind` in `src/store/mod.rs` or `src/embed/mod.rs`: its spellings in `FromStr` and the accepted-kinds lists in its error messages (`STORE_KIND_EXPECTED`, or the two literal lists in `EmbedderKind::from_str`), `Display`, `feature_name`, `is_compiled`, and (embedders) `has_adapter`, plus a `#[cfg(feature = "...")]` arm in `build_store` or `build_embedder` with a `#[cfg(not(...))]` arm that returns the missing-feature error. Keep both the `is_compiled` pre-check and the `cfg` arm. The pre-check produces the "rebuild with `--features ...`" message without naming types the binary does not contain; the `cfg` arm is what actually keeps the uncompiled adapter out. The formal model in `formal/LamboProofs/Resolve/Construction.lean` mirrors both enums: a new kind needs a constructor in its `StoreKind` or `EmbedderKind` inductive. For an embedder, also add it to the `lean_ctors!` list in `src/formal_constants_tests.rs`, which checks every Rust kind against the model, and give it an `EmbedderKind.implemented` arm only if its adapter is not implemented (that table is `true` for every kind but `bedrock`). Nothing tests the `StoreKind` side, so check it by hand.
4. For an embedder: return unit-length (L2-normalized) vectors, because SQLite ranks by cosine and CockroachDB by L2 distance, and the two agree only on unit vectors. If the session's contract should carry more than the configured `model` string (an artifact hash, a prompt profile, an endpoint id), expose the adapter through `Embedder::as_any` and add its arm to the contract match in `src/resolve.rs`, as `candle`, `gemini`, `embeddinggemma2` and `elastic` do. If construction is heavy, defer it to `Embedder::prepare`.
5. For a store that keeps vectors: claim `Capabilities::VECTOR_SEARCH` and report `vector_dimensions()` together, and implement `vector_candidates_checked`, which must compare the query's contract with the session's in the same transaction as the read. The default refuses on a store that claims vector search.
6. Add any environment variable the adapter reads during resolve to `RESOLVE_ENV_VARS` in `src/resolve.rs`.
7. Document the kind and its feature in this page's [Store](#store) or [Embedder](#embedder) table and the table above, in the feature table in [Installation](/installation#build-from-source), and in `lambo.example.toml`.

## HTTP transport

The HTTP transport binds to `127.0.0.1` on port `7700` and serves Streamable HTTP. Change the address with `--bind` and `--port` on `lambo serve`.

### Authentication

On loopback the HTTP transport is unauthenticated by default, so a local client needs no token. Binding anywhere else **fails closed**: `lambo serve` refuses to start, with exit code `2` and before it builds anything, unless you configure a bearer token, either with `--auth-token` or the `LAMBO_AUTH_TOKEN` environment variable (which takes precedence over the flag), or with a [`[[serve.credential]]`](#credentials). Configuring any credential also ends the unauthenticated loopback default. When a token is configured, every request must send `Authorization: Bearer <token>`. A missing or wrong token is refused with `401`. A `LAMBO_AUTH_TOKEN` that is set but empty, or not valid UTF-8, is a usage error, not a silent allowance. The token is ignored on `--transport stdio`.

### Rate limit

The HTTP transport enforces a sustained request rate for each credential, `50` requests per second by default with a burst allowance of twice that, so one credential's flood never rate-limits another. A request over the limit is refused with `429` and `Retry-After: 1`. Adjust it with `--rate-limit-rps`; `0` turns it off. With several sessions, each session also has its own bucket, `[serve] per_session_rps`; see [Multi-session serving](#multi-session-serving).

### Concurrent sessions

The HTTP transport mints one MCP session per `initialize` and refuses to exceed a ceiling of `32` concurrently live MCP sessions by default, counted across every Lambo session the process holds. With several credentials, each may hold at most its share: the ceiling divided by the number of credentials, rounded down, at least 1. At the cap, or at a credential's share, a new `initialize` is refused with `503`, `Retry-After: 5` and a message that tells you to close an idle session or raise `--max-sessions`. An MCP session answers only the credential that opened it.

### Request body limit

A request whose declared `Content-Length` exceeds `4 MiB` is refused with `413` before its body is parsed, and so is a body that turns out longer as it arrives (a chunked one included). The whole body must arrive within 30 s of the serve starting to read it, or the request is refused with `408`; a body still arriving holds no slot of the session cap.

### The read-only window

`lambo serve-web` opens a read-only browser window onto one or more sessions on port `7710` and never takes the writer lease, so it runs safely beside the `lambo serve` writer. It shares the same auth posture: loopback is unauthenticated by default, and a non-loopback bind requires `LAMBO_AUTH_TOKEN`, `--auth-token` or a [`[[web.credential]]`](#portal-credentials) and fails closed without one; without a credential it answers only loopback `Host` names and `[web] allowed_hosts`. It reads through a short-lived per-session view bounded by [`[web]`](#read-only-window-views). See [Command line](/cli).

## Provisioning a durable store

Before you serve against SQLite or CockroachDB, create the schema.

```bash
lambo --config lambo.toml provision
```

`provision` reads the store choice from your config and does the right thing for each kind. It is idempotent, so running it again is safe, and it does not build the embedder, so it works on a machine with no embedding service. It still refuses a store kind your binary was not built with.

| Store kind | What provision does |
|---|---|
| `memory` | Nothing. It reports that the in-memory store needs no schema. |
| `sqlite` | Creates the schema in the file at `store.path`. |
| `cockroach` | Runs `scripts/provision.sh`, which also reconciles the vector index. |

<Note>
Because the CockroachDB path runs the repository's script, run it from inside a checkout of Lambo. Lambo looks for `scripts/provision.sh` next to the project's `Cargo.toml`, searching the current directory and its parents, and tells you to run from the repository if it cannot find it.
</Note>

You can also run the script directly.

```bash
./scripts/provision.sh
```

Set `LAMBO_COCKROACH_DSN` in a `.env` file first, and run `./scripts/provision.sh --check` to verify the schema without applying it.

See [Installation](/installation) and [Library API](/api).

## Canonization coverage in the library

`Config::canonization_coverage_window` is a library setting, defaulting to
fourteen days. Stage 2 divides eligible dependent origin time spread by
min(session extent, this cap), with the existing three-origin and `0.3`
coverage bars. The session extent is its about-time extent, from its
earliest to its latest interaction by event time, else creation time. When
that extent exceeds the cap, 4.2 days of spread pass at the default; a
session whose extent is fourteen days or less keeps its previous coverage. This cap does not expire
older evidence. Set a duration of at least one day, in whole milliseconds,
no larger than `i64::MAX` milliseconds, and validate the `Config` before use.
It is not a `lambo.toml` key or an environment override. The file's daemon
cadences and promotion policy retain their existing roles. See
[Library API](/api#stage-2-coverage-cap) for the store accessor contract and
custom-window evaluation and inspect helpers.
