Lambo reads a `lambo.toml` file. It looks for the file in this order: the `--config` path, then the `LAMBO_CONFIG` environment variable, then `./lambo.toml`. An environment variable always wins over the file for any key it sets.

## What lambo.toml contains

The file has `[store]`, `[embedder]` and `[daemon]` sections, an optional `[serve]` section for [multi-session serving](#multi-session-serving), plus a small number of top-level process settings. It chooses which compiled backends this process runs, the cadence the background work runs at, and the canonization policy the serving verbs run them under.

```toml
# Top-level keys must come BEFORE the first [table] header, or TOML scopes them
# into that table and the unknown-key check refuses the file.
promotion_policy = "Solo"   # optional; the default remains Swarm

[store]
kind = "sqlite"
path = "./lambo.db"

[embedder]
kind = "bge_m3"
dim = 1024
url = "http://127.0.0.1:8080"
```

<Warning>
Unknown keys are refused, so a typo fails at startup instead of silently falling back to a default. A misspelled `knd`, a misspelled `[embeder]` section, and a key that belongs to the library rather than the file all stop the process before it attaches a session.
</Warning>

Recall defaults, flush timing, canonization thresholds, and scoring weights are not `lambo.toml` keys. They are library settings you pass when you build a `Memory` in Rust, so putting one in the file stops the process rather than tuning anything. Five settings are exceptions, and none of them is a threshold: `promotion_policy` below, and the four cadence keys in [Daemon cadence](#daemon-cadence). `promotion_policy` is a selector — it sets no number. But do not read that as "the numbers stay the same": `Solo` replaces the ladder rather than re-tuning it, and the store-evidence gates stop deciding anything. See [Library API](/api) for what each policy actually measures.

```
$ lambo --config lambo.toml provision
lambo provision: failed to resolve store: config: lambo.toml: unknown field `default_top_k`, expected one of `store`, `embedder`, `daemon`, `promotion_policy`, `serve` (line 1, column 1)
```

The refusal names the line and column but never quotes the line itself, so a misspelled key next to a secret (a DSN with a password in it, say) does not print the secret into your logs. A value under the wrong key is not quoted back either: an unknown `[store] kind` or `[embedder] kind` lists the accepted kinds with `(value not shown)`, a wrong-typed value reads `invalid type: string (value not shown), expected ...` (numbers are hidden the same way), and an unknown key is named only while it looks like a key (letters, digits, `_` and `-`, up to 40 characters), so a DSN pasted as a quoted key is not printed. An unknown `promotion_policy` is quoted only when it is a short word, so a typo stays visible.

## Promotion policy

`promotion_policy` is an optional selector for how canonization promotes. Omit it to preserve the existing `Swarm` behavior. Set it to `Solo` for a single writer whose recurring evidence should be eligible for promotion.

<Warning>
It is a **top-level** key, so it has to appear before the first `[store]` or `[embedder]` header. Put it after one and TOML scopes it into *that* table, so the refusal names that table's keys and never mentions the placement. With the layout above, moving it below `[store]` gives:

```
unknown field `promotion_policy`, expected one of `kind`, `dsn`, `path`, `vector_dim`
```

A store error, about a key that was spelled correctly. Below `[embedder]` you get the same shape with the embedder's much longer key list instead. This is the mistake worth knowing about, because nothing in either message points at the line's position.
</Warning>

Accepted values are `Swarm` and `Solo`, matched after trimming and without regard to case, so `solo` and `Solo` are the same thing — the same leniency `store.kind` and `embedder.kind` already have. Anything else fails at startup and names both what you wrote and the valid set. There is no silent fallback to the default.

There is no `lambo serve --promotion-policy` flag. Set it in the file or in `LAMBO_PROMOTION_POLICY`; no `serve` flag in Lambo duplicates a `lambo.toml` key, and every backend and policy selector is chosen the same way.

`Solo` does not lower the Canonical bar — it uses a different one. Instead of the store-evidence stages, promotion is decided by a recurrence score over the concept's own supporting evidence, so `gc_survived`, blast radius, distinct interactions and coverage stop participating. Two practical consequences. Under `Solo` you do not need to lower [`[daemon] gc_interval`](#daemon-cadence): lowering it changes nothing about promotion. And on `lambo serve-web`'s inspect panel the four-gate breakdown is replaced by a line naming the policy, because those four numbers no longer explain the status — the re-promotion cooldown is still shown there, because it still applies under both policies and on the solo path it is the only store-side reason a concept that has cleared its band still waits. See [Library API](/api) for the score itself.

<Warning>
`lambo serve-web` resolves its **own** `lambo.toml` and its own environment, and nothing carries the writing process's policy to it. So what the panel describes is the *reader's* resolution: start `serve-web` where it reads the same config as the `lambo serve` writing that session, or the page will explain a policy that is not the one promoting. A `lambo serve` under a systemd unit with `Environment=LAMBO_PROMOTION_POLICY=Solo`, opened with a `serve-web` run by hand in a shell that does not export it, is the shape of the mistake. `/api/inspect` names the resolution it used in `promotion_policy` — on the response and again on the gate block — so the mismatch is visible rather than silent.
</Warning>

`lambo demo` is out of scope, but it is not unaffected. It runs a scripted *swarm* demonstration on its own compiled-in config, so it ignores the **value**: `promotion_policy = "Solo"` changes nothing about what the demo does. It still validates it, because the file is parsed before any command decides what to keep from it — which is also why an unparseable policy stops even the four commands that never resolve an embedder (`provision`, `saints`, `inspect`, `stats`), unlike a degenerate `[daemon]` cadence.

```
$ LAMBO_PROMOTION_POLICY=Bogus lambo --config lambo.toml demo
lambo demo: failed to build backends: config: LAMBO_PROMOTION_POLICY: unknown promotion policy "Bogus" (expected Swarm | Solo)
```

[`[daemon]`](#daemon-cadence) is the same bargain with a narrower scope: the demo discards the cadence you set and still refuses a degenerate one, but only the commands that resolve an embedder refuse it at all.

## Store

`[store]` selects where the graph is persisted.

| Key | Type | Default | Notes |
|---|---|---|---|
| `kind` | string | `memory` | `memory`, `sqlite`, `cockroach`, or `postgres`. |
| `path` | string | none | The SQLite file, used when `kind` is `sqlite`. |
| `dsn` | string | none | The CockroachDB or PostgreSQL connection string, used when `kind` is `cockroach` or `postgres`. Prefer the environment variable so the secret stays out of the file. |

`kind` also accepts a few spellings: `mem` and `ram` for `memory`, `crdb` for `cockroach`, `pg` for `postgres`, and `sqlite3` for `sqlite`. `"postgres"` and `"pg"` are PostgreSQL, not CockroachDB.

The in-memory store is scoped to one process. Many agents can share it through a single `lambo serve`, because they all talk to that one process. Nothing outside that process can read it, and it does not survive a restart. Use `sqlite`, `cockroach`, or `postgres` when a separate command line process has to see the same session.

The kind you choose must be compiled into your binary. If it is not, Lambo fails at startup and names the feature to rebuild with. See [Installation](/installation).

## Recall tier

`[recall]` adds an Elasticsearch index beside the store that serves the vector part of recall. It is optional, and it is not a store kind: the `[store]` you chose stays the source of truth, and leases, fencing, canonization and graph queries never touch Elasticsearch. Each flush the store commits is copied to the index, and recall asks the index for the nearest concepts instead of scanning vectors in the store.

```toml
[recall]
kind = "elastic"
url = "https://my-cluster.es.example.com"
api_key = { env = "LAMBO_ES_API_KEY" }
index_prefix = "lambo"
```

| Key | Type | Default | Notes |
|---|---|---|---|
| `kind` | string | none | `elastic`. Required. |
| `url` | string | none | The cluster's base URL, `http://` or `https://`. A URL that carries a user name, a password, a query string or a fragment is refused. |
| `api_key` | table | none | `{ env = "NAME" }`: the environment variable that holds the API key. The key itself is never accepted in the file. Omit it for a cluster with security off. |
| `index_prefix` | string | `lambo` | Lowercase letters, digits, `-`, `_` and `.`. Vectors go to `<prefix>-v-<hash>`, one index per embedding model, and a small `<prefix>-meta` index keeps one sync marker per session. Must not contain `-v-` or end in `-v`, so that `<prefix>-v-*` can never match another deployment's indices on a shared cluster. |
| `refresh` | string | `"false"` | When a write becomes searchable: `"false"` leaves it to the index refresh interval (1 second by default), `"wait_for"` waits on every write and is for tests. |
| `timeout_ms` | integer | `5000` | Per-request timeout for writes and searches. Must be greater than zero. Refreshes, deletes by query and counts, whose work grows with the session, get 300 seconds. |

`[recall]` is a top-level table, not part of `[store]`. It needs the `recall-elastic` feature; a binary built without it refuses the section and names the feature rather than ignoring it. Lambo creates each index with its mapping the first time it writes to it.

**Staleness.** A concept becomes searchable in the index up to one refresh interval after its flush, so the vector part of recall can miss a concept written in the last second or so. The keyword and recent parts of recall still find it. This is an accepted difference from a store that ranks vectors itself. Deduplication when a writer derives new concepts does not use the index: it compares against the writer's own in-memory graph, so a fact derived twice in quick succession still merges.

**Ranking.** Lambo creates each vector index with plain float HNSW (no quantization), asks it for 16 more neighbours than recall needs, and re-scores them with exact cosine from the stored vectors. Scores and order therefore match the store's exact scan for the concepts the index returns. The index only chooses which concepts are considered, and an approximate HNSW search can occasionally miss a near neighbour that an exact scan would find. This is the second accepted difference. Because every neighbour comes back with its stored vector, a query's response grows with the number of concepts asked for: at 1024 dimensions about 0.7 MB for 50, and at most about 20 MB at the largest limit (2048), where Lambo asks for no extra neighbours.

**When the index is unavailable.** A failed copy never fails the flush, because the store already has the data. The session is marked stale, and until the index is repaired recall ranks vectors in the store instead (SQLite, PostgreSQL and CockroachDB do this themselves; the in-memory store has no vector search, so recall uses only its keyword and recent parts). A failed query does the same for that one recall, and after three failed or slow (over 5 seconds) queries in a row recall stops asking the index for 30 seconds before trying again. A flush waits at most 15 seconds for its copy. The writer holding the session repairs its index in the background when it next opens the session and after a later flush, one repair at a time per session, and `lambo recall-index backfill` repairs it when no writer is running. Writes made without a session lease (seeding) are not copied: the next writer to open the session, or a backfill, copies them. See [Command line](/cli#rebuild-the-recall-index).

Erasing a session also removes it from the index, and reports success only once a search of the index finds nothing of the session. See [Command line](/cli#rebuild-the-recall-index).

## Embedder

`[embedder]` selects how text is turned into vectors.

| Key | Type | Default | Notes |
|---|---|---|---|
| `kind` | string | `bge_m3` | `bge_m3` (an OpenAI-compatible embeddings API: local `llama-server` or a hosted endpoint), `candle` (in-process BGE-M3), `gemini` (Vertex AI), `embeddinggemma2` (EmbeddingGemma 2 text and images through `llama-server`, see [EmbeddingGemma 2](#embeddinggemma-2)), or `fixture` (tests). `openai` is an alias of `bge_m3`. `bedrock` parses but is not implemented, so it fails at startup. |
| `dim` | integer | `1024` | The width you expect the embedder to emit. For `embeddinggemma2` it must be `768`, `512`, `256` or `128`, so set it: the default `1024` is refused. |
| `url` | string | none | The `llama-server` base URL, used when `kind` is `bge_m3` or `embeddinggemma2`. Also accepted as `llama_url`. |
| `model` | string | none | The model id sent to `llama-server`. Empty means the server's own default. For `embeddinggemma2` it names the weights artifact and defaults to `ggml-org/embeddinggemma-2-GGUF@bfcd2987/Q8_0`. Also accepted as `llama_model`. |
| `api_key_env` | string | none | The name of the environment variable that holds a bearer token, for a hosted OpenAI-compatible endpoint. Used when `kind` is `bge_m3` or `embeddinggemma2`; any other kind refuses it. See [Hosted endpoints](#hosted-endpoints). |
| `images` | bool | `true` | Whether `embeddinggemma2` embeds images. `false` makes it text-only: it never sends an image, and `lambo_derive_image` takes only client vectors. Any other kind refuses the key. |
| `keep_warm_secs` | integer | auto | Seconds between `lambo serve` keep-warm touches. Omitted means auto: every 10 seconds for the in-process candle embedder on a Metal device, off for everything else. `0` turns it off; any other value applies to every kind. For `gemini`, each touch is a billed Vertex AI embedding request and keeps nothing local warm, so leave it off there. On a battery-powered laptop the default wakes the GPU every 10 seconds (about 0.2% GPU duty); set `keep_warm_secs = 0` to opt out. |
| `accept_client_vectors` | bool | `false` | Accept an image vector a client computed (`lambo_derive_image` with `vector`, `lambo derive-image --vector-json`). Off by default: such a call is refused and the refusal names this key. Lambo checks that the vector's declared contract (kind, model, dim) is exactly the session's and that the vector has the right width and a real direction, but it cannot check that the vector came from that model, so turning this on trusts the client's label. One setting for the whole process: every session a `lambo serve` holds gets the same value. |

`kind` also accepts `bge`, `bge-m3` and `openai` for `bge_m3`, `vertex` for `gemini`, `titan` for `bedrock`, and `fake` for `fixture`. An alias changes nothing but the spelling: the kind is still reported and stamped as `bge_m3`.

A store that persists vectors declares its own width, and Lambo refuses to start if `dim` disagrees with it.

While `lambo serve` sits idle, the operating system can compress or swap out model weights that nothing is touching, and the next call pays to bring them back. On Apple silicon the candle embedder's weights live in unified memory, so this is where it shows. Keep-warm embeds one short fixed probe on an interval and discards the vector. It writes nothing to the store, the graph or the call ledger, and it is not part of the embedding contract, so you can change it without re-embedding. The first touch comes one interval after startup, never during it.

### Hosted endpoints

The `bge_m3` kind speaks the OpenAI embeddings API (`POST <url>/v1/embeddings`), so it also reaches a hosted OpenAI-compatible endpoint when you give it a token. Cloudflare Workers AI serves BGE-M3 at 1024 dimensions:

```toml
[embedder]
kind = "openai"   # the same adapter as bge_m3
dim = 1024
url = "https://api.cloudflare.com/client/v4/accounts/<account-id>/ai"
model = "@cf/baai/bge-m3"
api_key_env = "CLOUDFLARE_API_TOKEN"
```

`api_key_env` names a variable; the token itself never goes in `lambo.toml`. Lambo reads the variable when it resolves the embedder and sends `Authorization: Bearer <token>` with every embed request. Without `api_key_env` no `Authorization` header is sent.

- If the variable is unset or empty, startup fails and names the variable. Lambo never falls back to sending no token.
- The token is sent only over `https`, or over plain `http` to a loopback host (`localhost`, `127.0.0.0/8`, `::1`) such as a local server. Plain `http` to any other host is refused at startup, naming the host, so a token never crosses a network in clear text. Without `api_key_env`, `http` URLs work as before.
- The value must look like a variable name: upper case letters, digits and `_`, not starting with a digit, at most 64 bytes. A value that does not, or that looks like a token, is refused without being shown. So is an inline `api_key = "..."`.
- It may not name `LAMBO_AUTH_TOKEN` or any `[[serve.credential]]` `token_env`, from the file or from `LAMBO_EMBED_API_KEY_ENV`. Those variables hold `lambo serve`'s own credentials, and one variable may not hold both a serve credential and the embedder's token.
- It may not name a variable lambo reads its own credentials from either: `LAMBO_COCKROACH_DSN`, `LAMBO_POSTGRES_DSN`, `DATABASE_URL`, `GCP_LAMBO_CREDENTIALS`, `GOOGLE_APPLICATION_CREDENTIALS` or `LAMBO_GEMINI_CREDENTIALS`. The same rule applies to `[[serve.credential]] token_env`.
- Redirects are never followed. A `3xx` from the endpoint fails the write as a configuration error naming the status (not the redirect target): point `url` at the endpoint itself. A `url` with a query or fragment is refused, because the embeddings path is appended to it.
- Plain `http` to a loopback host ignores `HTTP_PROXY`, `HTTPS_PROXY` and `ALL_PROXY`, so a token meant for a local server is never handed to a proxy. `https` URLs still use them: a proxy only tunnels the TLS connection.
- When an error body from the endpoint is quoted into an error, any run of 8 or more consecutive characters of the token is replaced, whether raw, JSON-escaped or percent-encoded. Shorter fragments, case-changed copies and other encodings are not detected. Quoted bodies are cut at 8 KiB. Logs and errors show the URL as scheme, host, port and path only.
- A `401` or `403` from the endpoint fails the write as a configuration error, the same as a wrong URL.

The same model behind a different server is a different embedding contract, because the two can differ numerically. Set `model` to the hosted id (as above) so a hosted session's contract differs from a local one, and start a fresh session or run `lambo re-embed` rather than mixing the two.

### EmbeddingGemma 2

`kind = "embeddinggemma2"` embeds text and images into one space with Google's EmbeddingGemma 2, served by llama.cpp's `llama-server`. It needs llama.cpp build b11452 or later; older builds refuse the model with `unknown model architecture: 'gemma-embedding2'`. Download the Q8_0 GGUF and its vision projector from `ggml-org/embeddinggemma-2-GGUF` and start the server like this:

```bash
llama-server --host 127.0.0.1 --port 8191 \
  -m embeddinggemma-2-Q8_0.gguf \
  --mmproj mmproj-embeddinggemma-2-Q8_0.gguf \
  --embeddings --pooling mean \
  --image-min-tokens 280 --image-max-tokens 280 \
  --ctx-size 8192 --batch-size 8192 --ubatch-size 8192
```

```toml
[embedder]
kind = "embeddinggemma2"
url = "http://127.0.0.1:8191"
dim = 768
```

- Lambo adds the model card's task prefixes itself: a stored concept is embedded as `title: none | text: ...`, a recall query as `task: search result | query: ...`, and an image with no prefix. A server, or a client computing vectors, that uses other prefixes is in a different space.
- `dim` can be `768`, `512`, `256` or `128`. Lambo takes the first `dim` of the 768 values and re-normalizes them.
- The session's contract records the weights and the prompt profile, for example `ggml-org/embeddinggemma-2-GGUF@bfcd2987/Q8_0;prompts=lambo-eg2-v1`, because `llama-server` ignores the model name in a request. Set `model` to the artifact your server actually runs. A different artifact or profile is a different contract: start a fresh session or run `lambo re-embed`.
- The profile fixes every image at 280 tokens, which is what makes a small and a large render of the same picture embed alike. The two image flags set it, and the batch flags let a whole image fit: at the server's default ubatch of 512 the budget is silently cut to 256 tokens, a different space. Lambo reads the token count of every image it embeds and refuses an image embedded at any other budget, naming the flags.
- Before its first embed, Lambo asks the server's `/props` which file it loaded, its quantization and whether it has a vision projector. It refuses to embed with a file whose name does not mention EmbeddingGemma 2 or a quantization other than the one `model` names (llama.cpp's own names are matched to the file names' tokens, so `Q4_K - Medium` is `Q4_K_M` and `all F32` is `F32`), and refuses images when the server has no vision projector. A server that does not answer `/props` (a hosted endpoint, Ollama) is used without the check, and the log says so once. The answer is asked again every 60 seconds and right after an embed request fails as unavailable, so a server restarted with another model or quantization is refused before Lambo writes more vectors under the old contract. Once a server has passed the check, embeds wait (and are retried) while `/props` cannot be reached, and a server that stops answering `/props` is refused: restart Lambo if you replaced it on purpose.
- An image sent to a server started without `--mmproj` fails as a configuration error naming `--mmproj`, not as a retryable server error. Without `--mmproj`, set `images = false`.

<Warning>
Do not switch embedder models in the middle of a session without re-embedding, because vectors from different models are not comparable. The kind, the model, and the width together form the session's embedding contract.
</Warning>

## Daemon cadence

`[daemon]` is optional and sets cadence only — how often the background work runs, never what a concept must clear to be promoted. Omit the whole section for the defaults.

| Key | Default | What it sets |
|---|---|---|
| `gc_interval` | `10000` | Mutations between GC sweeps. |
| `gc_max_interval_secs` | `86400` | Seconds after the last GC sweep at which a session that is still taking writes sweeps anyway. |
| `gc_idle_floor` | `100` | Session mutations since the last sweep below which the time bound does not fire. |
| `canonization_eval_interval_secs` | `60` | Seconds between canonization evaluation passes. |

A degenerate value is refused rather than quietly clamped — `gc_interval = 0` is a mutation counter and not a period, so it stops the process:

```
$ lambo --config lambo.toml demo
lambo demo: failed to build backends: config: gc_interval must be >= 1 (a mutation counter), got 0
```

The check runs wherever the process resolves an embedder, because that is the resolution path the cadence is applied on. Four commands do not resolve one — `lambo provision`, `lambo saints`, `lambo inspect` and `lambo stats` open the store alone — so those four accept a degenerate cadence without complaint. Every other command refuses it.

That boundary is not "commands that build a session". `lambo recall` builds none — it is a lease-free reader — and is refused anyway, because the refusal is about the file, not about a lease:

```
$ lambo --config lambo.toml recall --session s --query x
lambo recall: failed to build backends: config: gc_interval must be >= 1 (a mutation counter), got 0
$ lambo --config lambo.toml saints --session s
0 canonical memories in session 's'
```

A bad `promotion_policy` has the wider scope of the two, and the difference is worth knowing: an unparseable policy is refused while the file is being read, so it stops every command, those four included. A degenerate cadence is refused later, when the backends are built. See [Promotion policy](#promotion-policy).

Under the default `Swarm` policy `gc_interval` is the one worth understanding. Stage 1 requires `gc_survived >= 3`, so at the default a concept needs roughly 30000 mutations before it can be promoted at all, which an ordinary session of a few dozen concepts never reaches — this is why `lambo demo` sets it to 1 internally. Under `Solo` it does not participate at all; see [Promotion policy](#promotion-policy). `lambo.example.toml` carries the same notes inline.

GC also sweeps on time. When `gc_max_interval_secs` has passed since a session's last sweep and the session took at least `gc_idle_floor` mutations since then, it sweeps even though it is far below `gc_interval`; whichever trigger comes first wins. An idle session never sweeps on time alone (bar the one catch-up below), so `gc_survived` keeps measuring survival under eviction pressure rather than age. The time and watermark of the last sweep are stored with the session, so a writer restart does not reset the clock and does not by itself cause a sweep: a restarted writer sweeps only if one was already due. A session that took at least `gc_idle_floor` mutations since its last sweep and whose writer was down for a week sweeps once on its first cycle back, not seven times. A session that has never swept starts its clock when a writer first attaches to it, rather than sweeping. That is a delay, not an exemption: a never-swept session counts every lifetime mutation toward `gc_idle_floor`, so one that already has at least that many sweeps once about `gc_max_interval_secs` after the clock started, even if no write has arrived since. This is a deliberate catch-up for stores that grew before sweeps ran on time. Both keys must be positive; zero is refused the same way `gc_interval = 0` is. A `gc_idle_floor` at or above `gc_interval` is accepted but makes the time bound unreachable (the mutation trigger always gets there first), so the file is accepted with a warning at startup. Neither changes what a sweep collects.

## Multi-session serving

`[serve]` configures one `lambo serve` process that holds several sessions. It is optional: omit it and `lambo serve` behaves exactly as it always has.

An HTTP `lambo serve` reads `sessions`, `default_session` and `max_attached`: it pins every session in `sessions` beside its `--session` values, serves `default_session` at `/mcp`, and refuses to start when the pinned sessions together exceed `max_attached` or `default_session` is not one of them (this release serves pinned sessions only). See [Several sessions in one serve](/cli#several-sessions-in-one-serve). A stdio serve owns one session and ignores `sessions` and `max_attached`: its `--session`, or, without one, the session `[[serve.projects]]` or `default_session` chooses ([below](#choosing-a-stdio-serves-session)).

The rest of the table is **parsed and validated only**: the credentials, `attach_concurrency`, `idle_detach_secs` and `per_session_rps` arrive in later releases, and an HTTP serve never reads `[[serve.projects]]`, which is a stdio serve's only. A malformed table is still refused when the file is read, so it stops every command, like an unknown key. When the table sets any of those keys (or, for an HTTP serve, `[[serve.projects]]`), `lambo serve` logs one warning at startup (`[serve] is parsed but not yet enforced for some keys`) that names the keys and no value from them.

```toml
[serve]
sessions = ["lambo", "rustydocs", "general"]   # pinned: attached at startup
default_session = "general"
max_attached = 16
attach_concurrency = 2
idle_detach_secs = 900
per_session_rps = 50

[[serve.projects]]
path = "~/Documents/work/lambo"
session = "lambo"

[[serve.credential]]
name = "agents"
token_env = "LAMBO_AGENTS_TOKEN"
sessions = ["lambo", "rustydocs", "general"]

[[serve.credential]]
name = "dresscode"
token_env = "LAMBO_DRESSCODE_TOKEN"
session_prefix = "dc-u-"
create = true
erase = true
```

| Key | Default | What it sets |
|---|---|---|
| `sessions` | none | Pinned sessions, attached at startup and never idle-detached. Served by an HTTP `lambo serve`, beside its `--session` values. |
| `default_session` | none | The session `/mcp` serves, and the one a stdio serve without `--session` uses when no `[[serve.projects]]` entry covers its working directory. |
| `max_attached` | `16` | Cap on attached sessions, pinned plus on-demand. At least 1, and at least the number of pinned sessions. |
| `attach_concurrency` | `2` | Sessions that may attach at once. At least 1. |
| `idle_detach_secs` | `900` | Seconds an on-demand session may sit idle before it is detached. At least 1. |
| `per_session_rps` | `--rate-limit-rps` | Request rate for each session. `0` turns the per-session limit off. |
| `[[serve.projects]]` | none | `path` and `session`: a stdio serve started without `--session` under `path` uses `session`. `path` must be absolute or start with `~/`. An HTTP serve does not read it. |
| `[[serve.credential]]` | none | A bearer credential and the sessions it may reach (below). |

Every session named in `[serve]` must be addressable by URL: 1 to 128 bytes of `A-Z`, `a-z`, `0-9`, `.`, `_`, `:` and `-`, not starting with `.`. A name outside that rule is refused here, but you can still serve it on its own with `lambo serve --session <name>`, which keeps its looser rule.

A credential never holds its token. `token_env` names the environment variable that does, and the token will be read from it when the server starts (#32 PR 5; nothing reads it in this release). An inline `token = "..."` is refused, and the refusal does not quote it. A credential reaches the sessions in `sessions` (exact names, or `"*"` for every pinned session plus every session under any credential's prefix) and those under `session_prefix` (ids that start with the prefix and are longer than it). It may carry `create` (attach a session that does not exist yet), `erase` and `admin`. The names `default` and `local` are reserved, and `token_env` may not be `LAMBO_AUTH_TOKEN`. `token_env` must be a conventional variable name (`[A-Z_][A-Z0-9_]*`, at most 64 bytes) and must not look like a token (an AWS key id, or a 20-plus character run of letters and digits with no `_`), because it is the key a token is most likely to be pasted into by mistake. A value that fails is refused without being quoted.

### Choosing a stdio serve's session

A `stdio` serve given `--session` uses it and reads none of this. Without `--session` it picks, in order:

1. The `[[serve.projects]]` entry whose `path` contains the serve's working directory. When several do, the longest path wins. Paths are compared whole directory by whole directory, so `~/work/lambo` covers `~/work/lambo/src` but not `~/work/lambo-wt`.
2. `default_session`.
3. Nothing: the serve refuses with the usual missing `--session` error and exit code 2, before it builds any backend.

A leading `~` in `path` expands to `$HOME` (`~user` is refused). The working directory and every entry are resolved to real paths first, following symlinks, `.` and `..`, so a project entered through a symlink uses the entry for the directory the link points to. An entry whose directory does not exist never matches. If the working directory itself cannot be resolved (for example, it was deleted), the map is skipped and `default_session` applies. Two entries that resolve to the same directory but name different sessions are refused rather than picked by file order, as a configuration error (exit code 1). When `HOME` is unset or is not an absolute path, every `~` entry is skipped and the rest of the map still applies; the serve logs one warning saying so. The serve logs which entry it used, by its configured `path`. Neither that line, the warning, nor any refusal quotes the working directory or `$HOME`.

The map is read from the `lambo.toml` the serve loads: `--config`, then `LAMBO_CONFIG`, then `./lambo.toml` in the working directory. So a single global map used by every project needs the client to pass `--config` or set `LAMBO_CONFIG`; otherwise each serve reads its project's own `./lambo.toml`, if any, whose `default_session` or `[[serve.projects]]` then chooses the session, just as it already chooses the store. See [Serve a session](/cli#serve-a-session).

## Features

Cargo features decide which stores and embedders exist in your binary, and `lambo.toml` picks among them at runtime. Asking for a kind that was not compiled in is a startup error, not a fallback.

| Feature | What it adds |
|---|---|
| `store-memory` | The in-memory store. |
| `store-sqlite` | The SQLite store. |
| `store-cockroach` | The CockroachDB store. |
| `store-postgres` | The PostgreSQL + pgvector store. Fail-closed until B2 lands schema init. |
| `recall-elastic` | The Elasticsearch recall tier (`[recall]`). Released binaries include it. |
| `embed-fixture` | The deterministic fixture embedder. |
| `embed-bge` | BGE-M3 embeddings through `llama-server`. |
| `embed-eg2` | EmbeddingGemma 2 text and image embeddings through `llama-server` (`kind = "embeddinggemma2"`). Builds on `embed-bge`. |
| `embed-bedrock` | Reserved for Amazon Titan embeddings through Bedrock. Not implemented yet. |
| `fixtures` | Committed fixture graphs, which also enables `store-memory`. |
| `demo` | A convenience profile covering the memory and CockroachDB stores, both local embedders, and the fixtures. |

The default build enables `store-memory`, `embed-bge`, `embed-fixture`, and `fixtures`.

## HTTP transport

The HTTP transport binds to `127.0.0.1` on port `7700` and serves Streamable HTTP. Change the address with `--bind` and `--port` on `lambo serve`.

### Authentication

On loopback the HTTP transport is unauthenticated by default, so a local client needs no token. Binding anywhere else **fails closed**: `lambo serve` refuses to start unless you configure a bearer token, either with `--auth-token` or the `LAMBO_AUTH_TOKEN` environment variable (which takes precedence over the flag). When a token is configured, every request must send `Authorization: Bearer <token>`. A missing or wrong token is refused with `401`. A set-but-empty `LAMBO_AUTH_TOKEN` is a usage error, not a silent allowance. The token is ignored on `--transport stdio`.

### Rate limit

The HTTP transport enforces a global sustained request rate, `50` requests per second by default with a burst allowance of twice that. A request over the limit is refused with `429` and `Retry-After: 1`. Adjust it with `--rate-limit-rps`.

### Concurrent sessions

The HTTP transport mints one MCP session per `initialize` and refuses to exceed a ceiling of `32` concurrently live sessions by default. At the cap, a new `initialize` is refused with a `503` that tells you to close an idle session or raise `--max-sessions`.

### Request body limit

A request whose declared `Content-Length` exceeds `4 MiB` is refused with `413` before its body is parsed. A chunked request with no `Content-Length` keeps the per-string and per-call caps plus the rate limit as its bound.

### The read-only window

`lambo serve-web` opens a read-only browser window onto a session on port `7710` and never takes the writer lease, so it runs safely beside the `lambo serve` writer. It shares the same auth posture: loopback is unauthenticated by default, and a non-loopback bind requires `LAMBO_AUTH_TOKEN` or `--auth-token` and fails closed without one. See [Command line](/cli).

## Provisioning a durable store

Before you serve against SQLite or CockroachDB, create the schema.

```bash
lambo --config lambo.toml provision
```

`provision` reads the store choice from your config and does the right thing for each kind. It is idempotent, so running it again is safe, and it does not build the embedder, so it works on a machine with no embedding service. It still refuses a store kind your binary was not built with.

| Store kind | What provision does |
|---|---|
| `memory` | Nothing. It reports that the in-memory store needs no schema. |
| `sqlite` | Creates the schema in the file at `store.path`. |
| `cockroach` | Runs `scripts/provision.sh`, which also reconciles the vector index. |

<Note>
Because the CockroachDB path runs the repository's script, run it from inside a checkout of Lambo. Lambo looks for `scripts/provision.sh` next to the project's `Cargo.toml`, searching the current directory and its parents, and tells you to run from the repository if it cannot find it.
</Note>

You can also run the script directly.

```bash
./scripts/provision.sh
```

Set `LAMBO_COCKROACH_DSN` in a `.env` file first, and run `./scripts/provision.sh --check` to verify the schema without applying it.

See [Installation](/installation) and [Library API](/api).
