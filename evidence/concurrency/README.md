## The exact SIGTERM line (quoted, verbatim from line 1712)

```
2026-08-17T20:42:33.118846Z  INFO lambo::mcp::serve: lambo serve: session closed, tail durable
```

The assertion is the **exact line** — `lambo serve: session closed, tail
durable` — not a vibe. It is present once; `tail lost on exit` is absent
(`grep -c 'tail lost on exit' stderr-*.log` → 0). Shutdown sequence from
the transcript: `shutdown signal received, winding down` (line 1711) → the
assertion line (line 1712). Note what is **not** in the transcript:
`Memory session closed (tail flushed)` — logged by `src/memory.rs` whenever
`close()` flushes a non-empty tail, and absent here, which means the
close-time tail was **empty**: the daemon's 1 s flush loop had already
drained the in-flight writes before close, so the close drain itself was a
no-op on SQLite (no `CLOSE_GRACE` pressure was exercised).
**Signal → exit: 1419 ms, exit code 0** (SIGTERM sent 5 s into the burst,
with load still in flight — 11 `ok` `record_action` responses landed after
the SIGTERM timestamp).

## The durability comparison (C3), as a table

Ledger accounting (from `durability-20260817-204139.txt`, regenerated by the
committed `check_durability.py`): 3423 calls recorded, 1311 ok (no tool
error); 841 successful write calls (468 derive + 373 record_action); derive
created / matched 555/815; record_action created / edges 911/5506; refused
at the tool layer 310; rate-limit 429s 1682 (the overdrive); transport
failures 120 (after the server exited mid-burst).

| Metric | Ledger expected | Store | Verdict |
|---|---|---|---|
| interactions (1:1 per write call; append-only, never GC'd) | 841 ok writes | 862 | **store AHEAD by 21** — in-flight calls landed after the SIGTERM timestamp (11 `ok` responses arrived after it; the rest are transport-failure calls whose mutations landed), flushed by the daemon's 1 s flush loop |
| concepts (created) | 1466 | 1359 | shortfall 107 — **fully explained**: the daemon ran one GC sweep that collected 107 concepts (spec §9 sub-threshold/orphan housekeeping; `concepts_collected=107` in the stderr). Created − store == collected exactly. A created-then-collected concept is durable work, not tail loss. |
| edges (record_action reports its adds; derive edges unreported) | ≥ 5506 | 9279 | OK — store exceeds the reported lower bound |

The GC accounting is not hand-waved: the `gc_interval = 1` control run
committed under `control-gc/` produced `concepts_collected` sums exactly
equal to the created−store gap — 11 = 11 per
`control-gc/durability-gcproof.txt` (217 ledger-created − 206 store concepts
= 11; 55 GC sweeps logged in `control-gc/gcproof.log` sum to 11). The burst
side of this run matches exactly (768 distinct burst targets + 80 unique
action nodes all present).

The durability yardstick is the interaction count — append-only, exact —
and it is AHEAD, not short.

**Verdict: tail durable — no ledger-successful write is missing from the
store.** The `CLOSE_GRACE` budget (10 s, split `CLOSE_FLUSH_GRACE` 8 s +
`LEASE_RELEASE_GRACE` 2 s) was **not** tested to its limit on SQLite: the
close-time tail was empty (no `Memory session closed (tail flushed)` line in
the transcript), so the close drain was a no-op and the 1419 ms signal→exit
was the flush loop's normal cadence, not a near-deadline drain. The honest
number to record for the C3 decision: **0 shortfall on the interaction
yardstick; 0 unexplained concept shortfall (107 = GC, accounted)**.

## Rate limit and session cap — observed, not just assumed

* **Session cap (32):** the cap probe minted sessions until the server
  refused with 503 (`at the concurrent-session cap (32/32 sessions live)`),
  then released them via `DELETE /mcp`.
* **Rate limit (50 rps, burst ×2):** the overdrive phase free-ran 12
  workers for 2 s — free-run for the first `--overdrive-calls` = 120 calls
  per worker, then paced at ~20 rps per worker for the rest of the phase —
  against the fresh server; 1682 requests were refused with 429 (`rate limit
  exceeded: slow down and retry`), 1673 of them inside the overdrive window.
  The main window, paced at 40 rps under the limit, took **zero rate-limit
  refusals**: 9 of the 429s straddle into its opening (boundary carryover
  after the overdrive exhausted the limiter's burst budget), and 21 valid
  in-window `lambo_derive` calls returned tool-level `store error` responses
  instead (the 21 `hybrid derive could not commit after 8 concurrent graph
  changes` ERROR lines at `stderr-20260817-204139.log:1689-1709`, each
  recorded as `is_error` in the ledger) — so rate-limit refusals never
  crowded out the measurement.
* **Cap refusal, not a hang:** every adversarial `record_action` at 65
  combined targets returned the exact refusal `produces + modifies +
  depends_on must total at most 64 entries (65 given)` — with 310 tool-level
  refusals total (NUL, U+202E, over-size content, unknown tool, malformed
  params all refused cleanly).

## What the run found (beyond the assertion)

* **Throughput decay under load:** aggregate call rate fell from ~40 rps to
  ~11–19 rps over the 45 s main window as the graph grew — a real
  measurement of this hardware, not a fault.
* **Hybrid derive retries exhausted under 12-way concurrency:** a handful of
  `lambo_derive` calls failed with `hybrid derive could not commit after 8
  concurrent graph changes`. Server-side detail is on stderr; the client got
  only the class — the N4 wire-hygiene property, working.
* **Hybrid matching degrades on SQLite** (no `VECTOR_SEARCH`): the server
  logged the documented fallback to `MatchStrategy::Canonical`.

## Wire hygiene (acceptance scan)

Response fields (`error`/`text`) across all 3423 ledger calls and the full
stderr were scanned for `postgres(ql)?://`, `mysql://`, `sqlite://`,
`cockroachlabs.cloud`, `sqlx`/driver text, and `https?://` internal URLs:
**zero matches**. The only loopback address anywhere is the operator-chosen
bind in the server's own startup log
(`mcp http: listening on /mcp addr=127.0.0.1:7700`) — configuration echo,
not a leak. No DSN, key, or cluster id appears in this directory; the run
metadata records the auth token as `<SCRATCH-TOKEN>` (the real token lived
in a `mktemp` file, passed via `LAMBO_AUTH_TOKEN`, deleted on exit).

## Reproduce

```bash
    --out evidence/concurrency --workers 12 --session c-load-<date> --delay 5
```

(sessions → cap-probe → overdrive → main → burst).
