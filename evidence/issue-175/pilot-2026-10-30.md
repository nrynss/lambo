# #175: fixed-candidate graph-relevance pilot, 2026-10-30

**Decision: keep production behavior unchanged and keep #175 open.** A three-arm pilot ran through the real recall assembler on the frozen Lambo-only snapshot. Development-selected propagation settings tied the zero-relevance baseline on held-out known-support coverage: **24/29 answerable questions (82.8%)**. Stronger gains admitted graph-only records but displaced known supporting records on development questions.

This is a diagnostic pilot, not the issue's adoption evaluation. **Every labelled answer was already a phase-1 candidate.** Other candidates remain unjudged, so the dataset can measure preservation of known support but cannot establish whether graph-only evidence improves answers. It does not establish precision/recall, a general negative result for propagation, or the issue's quality/latency bar.

Machine-readable aggregates: [`pilot-2026-10-30.json`](pilot-2026-10-30.json). Topology and snapshot provenance: [`README.md`](README.md) and [`census-2026-10-30.json`](census-2026-10-30.json). Protocol: [agreed first comparison](https://github.com/nrynss/lambo/issues/175#issuecomment-6199960984).

## Fixed comparison

| Arm | Relevance supplied only to graph-only BFS members |
|---|---|
| A: zero | Current zero relevance |
| B: damped | Two-hop damped propagation |
| C: degree | Same propagation, dividing each sender's outgoing mass by its traversable out-degree |

Propagation follows the existing **directed** Dependency, Causal, Hierarchical, CoOccurrence and Semantic concept edges. Typed edges to the same neighbour count once. Seeds are finite, nonnegative and normalized to sum one; sinks send no mass. Accumulation uses UUID order. Scores from both hops are summed, then max-normalized over graph-only required members and multiplied by gain. This per-arm normalization compares relative allocations and tunes their scale; it does not measure absolute mass conservation. No receiver-degree correction, symmetrization, edge-subset change or push-PPR algorithm is tested here.

Direct relevance, phase-1 provenance, daemon scores, candidate membership, current max fusion, hot-list handling, token fitting and warning rendering are held fixed within each query. Settings are depth 2, top-k 10 and a 1,000-token context budget. The frozen configuration has redundancy selection off; this experiment does not test interactions with redundancy or shared layers.

`assemble_with_graph_relevance` supplies a separate map to the real `score_of` path. It cannot overwrite direct candidates, introduce candidates, score siblings outside the required set, or make graph-only members trigger cold mode. Normal callers pass no graph relevance. Propagation and the operator runner are test-only; no runtime knob is exposed.

For each query, the runner verifies that the fixed baseline frame equals normal production recall hits, context and warnings. The zero arm also equals baseline `DetailedRecall`. Graph serialization, snapshot bytes and input-label bytes are checked unchanged. The final source replay reproduced the original per-query rankings, render flags, scores and warning counts for both splits; only debug timings vary.

## Selection and measurements

The initial development sweep used damping `{0.25, 0.5, 0.75}` and gains `{0.25, 0.5, 1, 2}`. All were inert in rendered graph-only membership. Development top-10 final-score cutoffs ranged from 3.45 to 8.09 (median 5.22), above the initial relevance scale under the existing blend. Gains `{4, 8, 16, 32}` were then added **on development only**, giving 49 settings including zero. Labels, direct relevance, fusion and all other settings stayed fixed.

Selection maximizes development known-facet coverage, then known-answer hit@10; exact ties prefer lower gain and damping nearest 0.5. Both B and C selected **gain 0.25, damping 0.5** in both sweeps. A low-gain held-out confirmation had already been computed after the initial selection; its outcomes remained unread during the expanded development sweep. Because the final settings were identical, that confirmation was then scored. The final code replay confirms the same results. No held-out setting search was performed.

Known-facet coverage credits only a fully rendered known supporting record. A truncated record is not counted as complete support. Hit@10 instead records a known positive among the first ten selected hits, before token fitting; it is neither precision@10 nor evidence that the answer appeared in context. Unjudged records are counted separately. The controls are reported separately from answerable-query denominators.

| Split / arm | Known support fully rendered | Known hit@10 | Graph-only records rendered | Hub share of rendered records |
|---|---:|---:|---:|---:|
| Dev: zero | 41/51 (80.4%) | 46/51 (90.2%) | 0 | 0.35% |
| Dev: selected B | 41/51 (80.4%) | 46/51 (90.2%) | 0 | 0.35% |
| Dev: selected C | 41/51 (80.4%) | 46/51 (90.2%) | 0 | 0.35% |
| Held-out: zero | 24/29 (82.8%) | 26/29 (89.7%) | 0 | 0.54% |
| Held-out: selected B | 24/29 (82.8%) | 26/29 (89.7%) | 0 | 0.54% |
| Held-out: selected C | 24/29 (82.8%) | 26/29 (89.7%) | 0 | 0.54% |

Selected arms produce the same selected and rendered IDs as baseline. The paired topic-cluster bootstrap (2,000 draws, seed 175) therefore gives an observed known-coverage delta of zero and interval `[0, 0]`. This reflects identical outcomes on this small, biased pilot; it is not a tight population bound on propagation's effectiveness. Held-out answerable contexts contain 24 known positive and 161 unjudged complete records. The latter cannot be treated as false positives.

Hubs use the **pre-arm census definition**: top 1% by distinct incident neighbours, including cutoff ties (25 nodes at cutoff 16). This is not the daemon's full density score. Hub share is aggregated over fully rendered records in answerable queries, not over the selected top ten or controls.

Degree normalization suppresses hubs at those stronger gains but does not preserve known answers better. This measures displacement of known support, **not overall answer quality**: a newly rendered, unjudged record could also be useful. With no labelled graph-only positives, the metric offers no demonstrated route for propagation to improve coverage. Prefer the next labelling step over selecting a different gain from these results.

All eight absent-answer controls receive context in the tested arms. That is a current-pipeline observation, not a verified abstention or calibration result for #174. The run records one debug assembly-plus-propagation timing per query/setting, excluding embedding and phase 1; no full-recall p50/p99 or adoption latency claim is made.

## Remaining evidence before an adoption decision

1. Independently review the blinded production candidate pool for useful graph-only records, alternatives and answer facets. Collect fresh real questions whose support is absent from phase 1 but reachable, including low-degree details and genuinely relevant hubs. Freeze new labels and topic splits before another outcome search; do not repurpose the inspected held-out set as fresh confirmation.
2. Evaluate useful graph-only evidence actually rendered, complete precision/recall at 10 and answer facets with paired uncertainty. Keep sparse and identifier controls, distinguish query families from seed topology, and report representative traffic separately.
3. Measure end-to-end release-build p50/p99 under the agreed budget on the chosen configuration. Preserve structural goldens and warning guarantees. Only after the fixed-direction comparison has sufficient labelled headroom should the second-stage traversal/normalization experiments follow.

The issue's +0.1 precision improvement, hub-share and p99 adoption bar remains **unmeasured**. This pilot supports no default/configuration change.

## Reproducing privately

Use a standalone frozen SQLite backup without WAL/journal sidecars. Keep all raw inputs/outputs outside the repository; the ignored runner requires absolute private output paths and refuses overwrites. Reuse the exact configuration and stored query vectors for replay. The resolver opens the explicitly supplied database read-only and validates its embedding contract; it does not reconnect to the configured serving store.

Input query JSON contains `snapshot_sha256`, RFC3339 `clock`, `queries` and `settings`. Each question has `id`, `query`, `kind` (`answerable` or `no_answer`), `topic`, `split` (`dev` or `held_out`), `family`, `facets` (`id`, `text`) and `known_relevant` (`node`, `grade` 1/2, `facets`). Settings contain `arm` (`zero`, `damped`, `degree`), `damping` and `gain`. The scorer checks hashes, topic/positive split leakage, full split membership and identical per-setting query sets.

```sh
export LAMBO175_DATABASE=/private/research/snapshot.db
export LAMBO175_CONFIG=/private/research/experiment.toml
export LAMBO175_VECTORS=/private/research/query-vectors.json
export LAMBO175_QUERIES=/private/research/queries-dev.json
export LAMBO175_OUTPUT=/private/research/dev-run.json
export LAMBO175_MODE=eval
cargo test --lib --features fixtures,store-sqlite,embed-candle-metal \
  recall::experiment175::run::frozen_graph_experiment -- --exact --ignored --nocapture

python3 scripts/eval/graph_compare.py \
  --labels /private/research/queries-dev.json --run /private/research/dev-run.json \
  --split dev --out /private/research/dev-summary.json \
  --select /private/research/selection.json --hubs /private/research/hubs.json
```

Use `LAMBO175_MODE=pool` for private pre-arm candidate pooling. For a new experiment, freeze development selections before constructing held-out settings; then run `eval` on held-out inputs and score with `--split held_out` **without `--select`**. The scorer refuses held-out selection. Generate the optional hub key with the census tool's `--hub-key /private/research/hubs.json`; its public census output remains byte-identical.

Validation: 2,903 library tests pass with `fixtures,store-sqlite` (14 intentionally ignored), six new propagation/assembly regressions cover warm/cold ordering, provenance, invalid values, direction/depth, neighbour deduplication and sender fan-out; 18 stdlib census/sampler/scorer tests pass. Clippy is clean with warnings denied. Real Metal operator runs verify production-frame parity and unchanged graph/input bytes, including a final replay of all 49 development settings and three held-out settings. Existing structural/context goldens are unchanged.
